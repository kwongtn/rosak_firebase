## Purpose

Insiden ("Incident" in Malay) is a public incident/service-disruption calendar and timeline for Malaysian public transport — a read-only status-page-style feature showing historical and ongoing disruptions (line closures, breakdowns, delays, milestones) plotted on a calendar, with a same-page detail list, per-incident chronology timelines, markdown "details" write-ups, and crowd-contributed photos. It requires no login to view. The only authenticated/write interaction available anywhere in this feature is attaching photos to an existing incident (gated behind Firebase auth + moderation, see Data & API Contracts) — there is no user-facing incident submission form; all incident content (title, brief, chronology, severity, categories, line/vehicle/station tags) is authored exclusively through the Django admin by MLPTF staff.

## Functionality & Behavior

### Calendar panel (`CalendarComponent`)

- Two view modes, toggled by ng-zorro's built-in calendar mode switcher: **month** (day grid) and **year** (month grid). `calendarMode` is bound bidirectionally with the parent.
- On init (`calendar.component.ts:108-137`) computes a filter window via `getFilters()` and calls `GetCalIncidentListMonthService.watch()`. The window logic (`calendar.component.ts:85-106`):
    - `groupBy: "DAY"` (used in month mode): `startDate` = 14 days before the 1st of the selected date's month; `endDate` = 14 days after the 1st of the _next_ month. i.e. always fetches a padded window around the visible month so adjacent-month grid cells (shown grayed out by ng-zorro) also get badge data.
    - `groupBy: "MONTH"` (used in year mode): `startDate` = Jan 1 of the selected year; `endDate` = 14 days into the month after the selected month.
    - Any other value logs `console.error` and leaves dates as `new Date()`/`new Date()` (dead branch — `groupBy` is only ever `"DAY"` or `"MONTH"` from call sites).
- Query result `calendarIncidentsBySeverityCount` is reshaped client-side into two lookup maps used by the template's day/month cell renderers:
    - `monthEvents: { [yyyy-MM-dd]: { [severity]: { count, isLongTerm } } }` — used in month mode day cells.
    - `yearEvents: { [yyyy-MM]: { [severity]: count } }` — used in year mode month cells.
- **Selecting a day** (`selectChange`, `calendar.component.ts:139-178`): emits the new date up to the parent immediately (so the event list updates right away regardless of whether a re-fetch is needed). Only re-fetches (`fetchMore`) if the computed filter window's `startDate`/`endDate` actually changed (i.e. the user picked a day in the already-loaded window vs. jumped months) — micro-optimization to avoid redundant network calls, but it means `monthEvents` is **merged/accumulated** across fetches (new severities overwrite matching date+severity keys but old dates are never cleared), so the calendar's badge cache only grows for the lifetime of the component.
- **Changing panel mode / navigating months/years** (`panelChange`, `calendar.component.ts:180-217`): logs the raw event to console (`console.log("Panel value", $event)` — leftover debug statement), emits the new mode up, and if the mode actually changed, recomputes filters with the appropriate `groupBy` and re-fetches. Note this only re-fetches on **mode** change, not on every month/year navigation within the same mode — so paging forward/backward through months while staying in month view does **not** trigger a new query in this handler (day-cell data for far-future/past months relies on `selectChange`'s window-boundary check instead, and year-mode paging across years is not re-triggered by `panelChange` at all since mode stays `"year"` — a likely gap, see Known Quirks).
- Day cell template (`calendar.component.html:7-65`): for each date, iterates `monthEvents[date]` and renders one `nz-badge` (colored via `calendarIncidentSeverity: 'color'` pipe on the uppercased severity key) per severity **that is not long-term**, then a second `<li>` for entries **that are long-term**, prefixed with a clock-circle icon + tooltip "Long-term incident". Badge count = number of incidents of that severity on that day (not a list of titles).
- Month cell template (year mode, `calendar.component.html:67-89`): renders one badge per severity present in that month, count = total incidents of that severity that month (long-term/short-term not distinguished here).
- `getMonthData()` (`calendar.component.ts:219-224`) is dead code: hardcodes a return of `1394` for September (`month === 8`) and `null` otherwise, and is not wired to any template output (ng-zorro's `nzDateFullCell`/date-number slot is not used here) — leftover from ng-zorro calendar demo boilerplate.
- Loading state: `nz-spin[nzSpinning]="showLoading"` wraps the whole calendar; `showLoading` is `true` on init and during every `fetchMore`, `false` once `valueChanges` resolves.

### Event list panel (`EventListComponent`)

- Re-derives GraphQL variables whenever `selectedDate`/`calendarMode` change (`ngOnChanges`) or on first render (`ngOnInit`), via `getVariables()` (`event-list.component.ts:85-111`):
    - **Month mode**: filter = incidents where `date.exact` equals the selected day (`CalendarIncidentFilter.date` exact lookup — see backend section for what "exact" means server-side).
    - **Year mode**: filter = incidents where `date.month.exact` (0-indexed! `getMonth()`) and `date.year.exact` match — **note**: the backend's month filter (`filters.py:69-74`) adds 1 to the month it's compared against (`start_datetime__month__lte=value.month.exact + 1`), i.e. it expects a 0-indexed month input and converts to Django's 1-indexed `__month` lookup; this is intentionally symmetric with JS's 0-indexed `getMonth()`, but only checks `__lte`, not equality — see Data & API Contracts for the exact query semantics and its bug.
    - Always orders by `startDatetime: "ASC"`.
- On response (`setResults`, `event-list.component.ts:113-143`), the flat `calendarIncidents` array is partitioned client-side into:
    - `shortTerm`: incidents where `!longTerm`, **or** `longTerm` but the incident's `startDatetime` date matches the exact currently-selected date (i.e. a long-term incident is shown in the main "short term" list on the day it started).
    - `longTerm`: incidents where `longTerm` is true **and** `startDatetime`'s date does not match the selected date (i.e. long-term incidents are shown in the collapsed panel on every day except the one they started, so that on their start day they instead surface prominently in the main list).
- `dataLength` = raw `calendarIncidents.length` (used to distinguish "no results at all" from "no short-term but has long-term" in the empty-state check).
- Header (`event-list.component.html:1-11`): shows `selectedDate` formatted `"MMM dd, yyyy (EEE)"` in month mode, or `"MMM yyyy"` in year mode.
- Short-term list: rendered unconditionally as an `nz-list` if `data.shortTerm.length > 0`, one `EventCardComponent` per item.
- Long-term section: only rendered if `data.longTerm.length > 0`. Wrapped in an `nz-collapse` with a single panel whose header text is dynamic: `"Click to Collapse "` when expanded, else `"Click to Expand (<n> incident[s])"` with correct singular/plural. Panel starts collapsed (`panelActive` defaults `false`).
- Empty state: `nz-empty` (ant design placeholder illustration hosted at `https://gw.alipayobjects.com/...empty.svg` — an external CDN image) shown only when `longTerm.length === 0 AND dataLength === 0 AND !showLoading` — i.e. genuinely zero incidents for the period, not merely zero short-term ones (if there are only long-term incidents, the collapse panel shows instead of the empty state, even with zero short-term items).
- Loading state: whole panel wrapped in `nz-spin[nzSpinning]="showLoading"`.

### Event card (`EventCardComponent`)

- On init (`event-card.component.ts:68-135`), deep-clones the input (`JSON.parse(JSON.stringify(this.data))`) into `displayData` so client-side mutations don't affect Apollo's cached object:
    - If the incident has **no chronology entries**, synthesizes two default ones: order `"0"` "Start of incident" (indicator `blue`, datetime = `startDatetime`), and — only if `endDatetime` is set — order `"1"` "Issue resolved" (indicator `green`, datetime = `endDatetime`). Ongoing incidents with no chronology thus show a single synthetic "Start of incident" entry.
    - All chronology `content` strings and the incident `brief` have literal `\r\n` sequences replaced with `<br />` and are then bound via `[innerHTML]` (i.e. the CMS-authored text is treated as trusted raw HTML — no sanitization/escaping beyond Angular's default `innerHTML` XSS sanitizer).
    - Chronologies are sorted ascending by `Number(order)` (numeric even though the GraphQL field is typed as string).
    - **Duration/elapsed-time**: if `endDatetime` is present, computes a static human-readable `duration` string once (`getReadableTimeDifference`, days/hours/minutes/seconds, comma-joined per a `CommaConfig`, default only day-separated: `"X days, Y hours Z minutes ..."`). If `endDatetime` is absent (ongoing incident), starts a `setInterval` ticking every **200ms** updating `elapsedTime` live, cleared in `ngOnDestroy`. The timeline's "pending" spinner slot (`nz-timeline[nzPending]`) shows `"Ongoing for... <elapsedTime>"` only while `endDatetime` is falsy.
    - **"Inaccurate" override**: regardless of the `inaccurate` field from the API, the client forcibly sets `displayData.inaccurate = true` if `startDatetime.getFullYear() <= 2023 && startDatetime.getMonth() <= 3` (`event-card.component.ts:128-134`) — i.e. any incident starting in Jan–Apr of 2023 or earlier is always flagged inaccurate client-side, overriding (but never un-setting) the backend's own `inaccurate` flag. Comment: "All entries before May 2023 are considered i**n**ccurate" (`getMonth() <= 3` is 0-indexed, so this is Jan(0)–Apr(3) inclusive plus all of any year ≤ 2023 — note the `getFullYear() <= 2023` combined with `getMonth() <= 3` via `&&` actually means: any year < 2023 (any month), OR year === 2023 AND month ≤ April. Years after 2023 are never auto-flagged even if month ≤ April).
- Severity ribbon (`nz-ribbon`, top of card): text = titlecased severity + `": <impactFactor>"` suffix only if `impactFactor > 0`. Color from `calendarIncidentSeverity: 'color'` pipe.
- Tag row: rendered only if the incident has ≥1 line, vehicle, or station. Renders one colored `nz-tag` per line (`displayColor`/`displayName`), then (if any vehicles) a `" | "` separator and one tag per vehicle `identificationNo`, then (if any stations) another `" | "` separator and one tag per station `displayName`. `categories` is fetched by the underlying query but **never rendered anywhere in the template** (dead field, present for a future feature or leftover).
- Body: two columns (stacks on mobile via `nzXs=24`/`nzXl`) — left = chronology timeline (only if `chronologies.length > 0`) + duration line; right = `brief` (raw HTML) + conditional `"Details"` link (only if `hasDetails` is true, computed server-side from whether `details` is non-empty) + "Last updated" timestamp footer (absolutely positioned bottom-right of the card via CSS).
- Card title: inaccurate-data icon (⚠️-style `exception` icon with tooltip "Data may be inaccurate") shown if `displayData.inaccurate`, then a clock icon with tooltip "Long term incident" if `displayData.longTerm`, then the incident `title` text.
- **Details link** click (`onDetailsClick`) opens `EventDetailsModalComponent` via `NzModalService.create()`: title = incident title, width `80vw`, no default OK/Cancel buttons (`nzOkText`/`nzCancelText: null` — modal is dismissed only via its own close (×) button), passes the whole `displayData` object as `nzData`.
- **Camera icon** (card action row) click (`onImagePanelClick`) opens `ImageDrawerComponent` via `NzDrawerService.create()`. Drawer width is responsive, recomputed on every window resize (`@HostListener("window:resize")`) and also once eagerly in the constructor: `<500px` viewport → `280px` drawer, `<1024px` → `480px`, `<1300px` → `700px`, else `905px` (comment documents these as roughly 1/2/3/4-image-wide breakpoints). Drawer title = `"🖼️ - <incident title>"`. Drawer footer template (`#drawerFooter`, defined in this component but rendered inside the drawer via `nzFooter`) has Cancel/Submit buttons:
    - **Cancel** (`close()`): just closes the drawer, discarding any staged (not-yet-queued) uploads.
    - **Submit** (`submit()`): reads `pendingUploads` off the drawer's live component instance (`drawerRef.getContentComponent()?.pendingUploads`), and for each staged file calls `ImageUploadService.addToQueue(incidentId, file, "INCIDENT_CALENDAR_INCIDENT")`, then shows an info toast ("Image upload queued. Please wait for uploads to complete before closing this tab.") if there was at least one file, and always closes the drawer. The actual network upload happens asynchronously afterward, decoupled from this component (see `ImageUploadService`, State Management below) — so images are not guaranteed uploaded by the time the drawer closes.

## Data & API Contracts

All queries are one-shot Apollo `Query` services under `/home/kwongtn/rosak_firebase/src/app/insiden/services/`, hitting `POST /graphql/` (no auth header attached — see `graphql.module.ts`, which builds a plain `HttpLink` with no auth link/interceptor). Backend root schema composition: `/home/kwongtn/rosak_backend/rosak/schema.py` merges `IncidentScalars`/`IncidentMutations` (from `/home/kwongtn/rosak_backend/incident/schema/schema.py`) into the root `Query`/`Mutation`. **`IncidentMutations` is an empty `pass` class** (`incident/schema/schema.py:41-42`) — there is no GraphQL mutation surface for incidents at all; all incident authoring happens via Django admin, and the only "write" that reaches this feature from the public app is the REST photo-upload endpoint described below.

The GraphQL endpoint has no authentication requirement at the transport layer (`rosak/urls.py:36-41`, wrapped only in `csrf_exempt`), and none of `IncidentScalars`' fields carry a `permission_classes`/`extensions` check in `schema.py`/`scalars.py`/`resolvers.py` — every query below is fully public and unfiltered by user identity.

1. **`GetCalIncidentListMonthService`** (`/home/kwongtn/rosak_firebase/src/app/insiden/services/get-cal-incident-list-month.service.ts`) — used by `CalendarComponent`.

    - Operation: `calendarIncidentsBySeverityCount(startDate: Date!, endDate: Date!, groupBy: GroupByEnum!) -> [CalendarIncidentGroupByDateSeverityScalar!]!`, fields requested: `count date isLongTerm severity`.
    - Backend: field resolver `get_calendar_incidents_by_severity_count` (`/home/kwongtn/rosak_backend/incident/schema/resolvers.py:20-138`), registered as a `strawberry.field(resolver=...)` on `IncidentScalars` (`schema.py:35-37`). `GroupByEnum` = `DAY | MONTH` (`resolvers.py:14-17`).
        - Builds a base queryset of `CalendarIncident`s whose `start_datetime` date falls in `[start_date, end_date]` AND whose `end_datetime` is null or also falls in that range (so an incident spanning outside the window on one end can still be excluded — this is a stricter filter than the `CalendarIncidentFilter.date` range lookup used elsewhere, which treats an open/ongoing incident (`end_datetime IS NULL`) as always in-range).
        - `min = MIN(start_datetime__date)` over that queryset; if there's no matching incident at all, returns `[]` immediately.
        - Builds a `pendulum` interval from `max(min, start_date)`... actually `min if start_date > min else start_date` (i.e. widen the window backward to the earliest actual incident if the requested `start_date` is later than it) through `min(today, end_date)` (never aggregates into the future).
        - **`MONTH` grouping**: for every month in that interval × every `CalendarIncidentSeverity` value (`MAJOR`, `MINOR`, `OTHERS` — see below), runs one `Count` aggregate filtering incidents whose `start_datetime` year/month `__lte` the bucket's year/month AND (`end_datetime` year/month `__lte` bucket or `end_datetime` is null) AND matching severity — i.e. this counts incidents that **started on or before** and (if ended) **ended on or before** that month, for every month from the interval start onward, which is a running/cumulative-style count rather than "incidents active in this specific month" (worth confirming this is the intended semantics — it looks like it could double count across consecutive months for anything long-running with no end date, since `end_datetime IS NULL` always satisfies the second clause). Result rows use `is_long_term: None` for month buckets (year-mode UI ignores long-term distinction, consistent with the client code).
        - **`DAY` grouping**: for every day in the interval × long/short term × severity, counts incidents matching `long_term=True AND start_datetime.date == day` (long) vs. `long_term=False AND start_datetime.date <= day <= (end_datetime.date or infinity)` (short) AND severity. So the badge counts returned per day for long-term incidents are keyed to their **start day only** (matches the frontend's day-cell rendering, which shows a clock icon + count only under the badge's day-of-appearance), while short-term/ongoing incidents count on every day they span.
        - Only non-zero counts are returned (rows with `count == 0` are filtered out before appending).
    - **Note**: the frontend's TypeScript interface (`get-cal-incident-list-month.service.ts:9`) types `severity` as `"CRITICAL" | "MINOR" | "MILESTONE"`. That is **stale/wrong** — see the model-truth note under `GetCalIncidentListMinService` below; the real values are `MAJOR | MINOR | OTHERS`.

2. **`GetCalIncidentListMinService`** (`get-cal-incident-list-min.service.ts`) — used by `EventListComponent`.

    - Operation: `calendarIncidents(filters: CalendarIncidentFilter) -> [CalendarIncidentScalar!]!`, fields: `id startDatetime endDatetime severity title brief impactFactor inaccurate longTerm hasDetails lastUpdated lines{displayName displayColor} vehicles{identificationNo} stations{displayName} categories{name} chronologies{order sourceUrl indicator datetime content}`.
    - Backend type: `CalendarIncidentScalar` (`/home/kwongtn/rosak_backend/incident/schema/scalars.py:50-97`), backed by the `strawberry_django.filters.filter`-decorated `CalendarIncidentFilter` (`/home/kwongtn/rosak_backend/incident/schema/filters.py:30-84`).
        - `hasDetails` is a computed `@strawberry.field`: `details not in [None, ""]` (`scalars.py:83-86`) — true purely based on whether the admin has typed anything into the `details` markdown box.
        - `lastUpdated` is a computed field (`scalars.py:88-97`): `max(incident.modified, latest_chronology.modified)` — i.e. editing a chronology entry (even without touching the parent incident row) bumps what the UI displays as "Last updated". Re-queries the DB directly inside the resolver rather than reusing loaded data (a per-row extra query — potential N+1, not covered by `DjangoOptimizerExtension` since it's a plain sync DB hit wrapped in `@sync_to_async`).
        - `severity` is typed as a **plain `str`**, not a strawberry enum (`scalars.py:59`) — so any value stored in the DB column passes through as-is; GraphQL does not constrain/validate it. **Ground truth for actual values**: `IncidentSeverity`/`CalendarIncidentSeverity` model enums (`/home/kwongtn/rosak_backend/incident/enums.py`) — `CalendarIncidentSeverity` = `MAJOR` ("Entire/parts of line broken, train crashes"), `MINOR` ("Single vehicle disruptions etc."), `OTHERS`. These were **renamed** from an earlier `CRITICAL`/`MINOR`/`MILESTONE` scheme by migration `0005_alter_calendarincident_severity.py` (data-migrated `CRITICAL→MAJOR`, `MILESTONE→OTHERS`) and again tweaked in `0006` (`MILESTONE→OTHERS` rename settled). The frontend's `CalendarIncidentSeverityPipe` (`/home/kwongtn/rosak_firebase/src/app/pipes/calendar-incident-severity/calendar-incident-severity.pipe.ts`) correctly maps the **current** values: `MAJOR→"error"/red`, `MINOR→"warning"/orange`, `OTHERS→"processing"/blue` (default `"default"`/`cyan` for anything unrecognized) — but several frontend TS interfaces (this service, `get-cal-incident-list-month.service.ts`) still carry the **old, incorrect** union type `"CRITICAL" | "MINOR" | "MILESTONE"`. This is type-only drift (doesn't break runtime, since the values are just `string`s end-to-end and the pipe does its own separate lookup) but should be corrected to `"MAJOR" | "MINOR" | "OTHERS"` in the rewrite.
        - `categories` field on `CalendarIncidentScalar` returns `List[CalendarIncidentCategoryScalar]` (a list), but the frontend's `GetCalendarIncidentListMinResponseElem.categories` type (`get-cal-incident-list-min.service.ts:32-34`) is typed as a **singular object** `{ name: string }`, not an array — another latent type mismatch (harmless in practice only because the field is never rendered in the template).
        - `chronologies` ordering: `CalendarIncidentChronology` is an `OrderedModel` (django-ordered-model) with `order_with_respect_to = "calendar_incident"`; the GraphQL field returns them in whatever order the underlying relation/default manager yields (model `Meta` doesn't declare an explicit `ordering`, but `OrderedModel` typically applies `ordering = ("order",)` via its base `Meta` — the frontend defensively re-sorts by numeric `order` client-side regardless, `event-card.component.ts:99-101`).
    - `CalendarIncidentFilter.date` (`filters.py:35-83`) is a **custom filter field**, not the strawberry-django default `DateFilterLookup` behavior — it interprets:
        - `range`: asserts `start`/`end` are both set and their span is `<= 60 days` (an `assert`, so violating it raises a Python `AssertionError` → GraphQL error, not a clean validation error). Semantics: incidents whose `start_datetime` date is `<= range.end`, AND whose `end_datetime` is null or `>= range.start` (when `range.start == range.end`); for a genuine range, additionally requires `start_datetime >= range.start` and (if ended) `end_datetime <= range.end`.
        - `exact`: incidents where `start_datetime.date <= exact` AND (`end_datetime` is null OR `end_datetime.date >= exact`) — i.e. "incidents active on this exact day", which is what `EventListComponent`'s month-mode query uses (`event-list.component.ts:93-97`).
        - `month`/`year`: **only `__lte` comparisons are applied, never combined into equality** — e.g. `month.exact` filters `start_datetime__month <= (exact+1)` AND (`end_datetime` null OR `end_datetime__month >= (exact+1)`); there is no upper bound tying the incident to _only_ that month, so an incident starting in an earlier month than requested with no end date, or ending in a later month, will still match. **This looks like a backend bug**: year-mode filtering (used when the calendar is in year view and a month cell is clicked) can return incidents from unrelated months as long as they're "still open" during the requested month, and offers no protection against also matching incidents that started well before the requested month/year window if they're long-running. Confirm against live site whether year-mode click-through ever shows unexpected incidents.
        - `id`, `severity`: plain equality filters (`Optional[strawberry.ID]`, `Optional[str]`) — not used by any query in this feature's frontend code (only `date` filters and, for the details/medias services, `id`).
    - `CalendarIncidentOrder` (`orderings.py`) exposes orderable fields `id`, `order`, `impactFactor`, `startDatetime`, `endDatetime`. `EventListComponent` always orders `startDatetime: ASC`.

3. **`GetCalIncidentDetailsService`** (`get-cal-incident-details.service.ts`) — used by `EventDetailsModalComponent`.

    - Operation: `calendarIncidents(filters: CalendarIncidentFilter, order: CalendarIncidentOrder) -> [CalendarIncidentScalar!]!`, fields: `id details`. Called with `filters: { id: <incidentId> }` (no `order` actually passed at the call site despite being declared in the query — `event-details-modal.component.ts:39-41`). Since `id` is a primary-key-equality filter, the result array should have 0 or 1 element; the component blindly reads `data.calendarIncidents[0].details` (`event-details-modal.component.ts:45`) — **will throw if the id doesn't resolve to any row** (no defensive check for an empty array). `details` is a plain `TextField` (admin-authored markdown, no server-side markdown validation/sanitization — rendered client-side by `ngx-markdown`, which does its own sanitization via its configured markdown-it/DOMPurify pipeline, not covered here).

4. **`GetCalIncidentMediasService`** (`get-cal-incident-medias.service.ts`) — used by `ImageDrawerComponent`.
    - Operation: `calendarIncidents(filters: CalendarIncidentFilter) -> [CalendarIncidentScalar!]!`, fields: `medias { width height file { url } }`.
    - Backend: `CalendarIncidentScalar.medias` is an **async field resolved through a DataLoader**, not a direct model field (`scalars.py:75-81`): `info.context.loaders["incident"]["medias_from_calendar_incident_loader"].load(self.id)`, backed by `batch_load_medias_from_calendar_incident` (`/home/kwongtn/rosak_backend/incident/schema/loaders.py:8-17`), which batches `CalendarIncidentMedia.objects.filter(calendar_incident_id__in=keys).select_related("media")` across all incidents requested in one GraphQL request and groups results into a `set` per incident (so **duplicate media rows for the same incident+media pair, if any existed, are silently deduplicated by the loader**, and ordering is **not guaranteed** — a plain Python `set`, no `order_by`). `media.file` is `strawberry_django.DjangoImageType` — the raw Django `ImgurField` storage URL (`/home/kwongtn/rosak_backend/common/models.py:22-31`; comment `# TODO: Deprecate in future version`).
        - **Confirmed (not just suspected) that this still resolves to a real `i.imgur.com` URL today**, despite the Discord-relay step in the upload pipeline below: `ImgurStorage._save()` (`/home/kwongtn/rosak_backend/common/imgur_storage.py:77-97`) special-cases a `ContentFile` payload by calling Imgur's upload API with `type: "url"` and the content itself as the `image` value — and `convert_temporary_media_to_media_task` (`common/tasks.py:200-202`) constructs exactly that: `Media.objects.create(file=ContentFile(temp_media.file.url, name=temp_media.file.name), ...)`, i.e. it hands Imgur the Discord CDN URL and asks Imgur to **fetch and re-host it**. `ImgurStorage.url()` (`imgur_storage.py:209-210`) then always returns `f"https://i.imgur.com/{path}"`. So the Discord webhook step is only an intermediate relay (used to get a public URL + EXIF/embed metadata for moderation logging); the durable, GraphQL-exposed `media.file.url` is a genuine Imgur URL, and the frontend's `getThumbnail()` (`@util/imgur.ts`) suffix trick is correctly targeted at the real storage backend, not stale.

### Photo submission / moderation pipeline (REST, not GraphQL)

This is the only write path reachable from the Insiden UI. Frontend: `ImageUploadService` (`/home/kwongtn/rosak_firebase/src/app/services/image-upload.service.ts`) queues files client-side and, on a 1-second interval (`setInterval`, started lazily on first `addToQueue()` call and cleared once the queue drains), runs up to `environment.upload.concurrency` uploads concurrently (`@supercharge/promise-pool`) as `POST ${environment.backendUrl}upload/` (`http://localhost:8000/upload/` in dev; **concurrency = 10** in `environment.ts:34`, **5** in `environment.prod.ts:33`), `multipart/form-data` with fields `related_id` (the `CalendarIncident` id), `upload_type: "INCIDENT_CALENDAR_INCIDENT"`, `image` (the file — pre-compressed client-side via `ImageCompressionService` if >9MB), and a custom header `Firebase-Auth-Key: <Firebase ID token>` obtained via `AuthService.getIdToken()`. Files that still need compression when their turn comes up are pushed back onto the queue rather than uploaded (`image-upload.service.ts:60-66`) and picked up on the next interval tick. On any HTTP error the file is also re-queued, forever retried every second until it succeeds (no backoff, no max-retry — a stuck/invalid file will retry indefinitely; see Known Quirks).

- Backend: `GenericUpload.as_view()` (`/home/kwongtn/rosak_backend/common/views.py:30-78`), mounted at `POST /upload/` (`rosak/urls.py:41`).
    - Rejects (`400`) if `upload_type` isn't a valid `TemporaryMediaType` choice.
    - Requires a valid Firebase user (`FirebaseUser(request).get_current_user()`); returns `401` if not resolvable from the `Firebase-Auth-Key` header — **this is the only place in the whole Insiden flow that requires authentication**; viewing incidents/photos never does.
    - For `upload_type == INCIDENT_CALENDAR_INCIDENT`: stores `metadata = { "calendar_incident_id": related_id }` with **no check that `related_id` refers to a real/existing `CalendarIncident`, and no ownership/permission check at all** — any authenticated Firebase user can attach a photo to any incident id, valid or not. (Contrast with the `SPOTTING_EVENT` branch just above it in the same view, which explicitly verifies `user.id == event.reporter_id` before accepting — this ownership check has no equivalent for incidents, presumably because incidents aren't user-authored, but it also means there's no rate-limit/spam guard specific to this upload type either.)
    - On success, creates a `common.models.TemporaryMedia` row with `status = PENDING` and returns `201` with an empty body — **the photo is not yet visible anywhere**; it must clear moderation asynchronously (Celery, `/home/kwongtn/rosak_backend/common/tasks.py`) before it becomes a queryable `Media`/`CalendarIncidentMedia`:
        1. `check_temporary_media_nsfw` — if the uploader has a `TRUSTED_MEDIA_UPLOADER` clearance, auto-approves (`TRUSTED_CLEARED`) and proceeds immediately; otherwise calls a third-party NSFW-detection API (RapidAPI) and sets `BLOCKED` (dropped forever) or `CLEARED` based on a configured probability threshold.
        2. `convert_temporary_media_to_media_task` — for cleared media, re-uploads the image to a Discord webhook channel (used as durable object storage / moderation audit log, embedding EXIF metadata as fields), creates a `common.models.Media` row referencing the Discord attachment, then (for this upload type) creates the `incident.models.CalendarIncidentMedia` join row linking it to the target `CalendarIncident` — **only at this point does the photo start showing up in `GetCalIncidentMediasService` results**. `timestamp` on the join row is populated from the image's EXIF `DateTime` tag if present.
        3. A periodic cleanup task (`cleanup_temporary_media_task`, `common/tasks.py:247-278`) re-drives any `PENDING` media older than 5 minutes with `fail_count < 5` through the conversion pipeline (safety net for missed/failed Celery dispatches), also re-drives anything an admin has manually flipped to `OVERRIDE_CLEARED` status (a manual moderation-override escape hatch for NSFW-`BLOCKED` media, presumably actioned via Django admin — not exposed anywhere in the public frontend), and hard-deletes `TO_DELETE`-status rows older than 30 days.
    - Net effect for the Insiden feature specifically: there is an **unbounded, unmoderated-until-async delay** between a visitor submitting a photo and it appearing in the incident's image drawer — no optimistic client-side display of the just-uploaded image, no polling/refresh of `ImageDrawerComponent` after submit (the drawer is simply closed), so the visitor gets no confirmation the photo actually became visible; they'd have to reopen the drawer later (this common/`TemporaryMedia` pipeline is shared with the Spotting feature's photo uploads and is documented in more depth wherever that feature's doc covers it — summarized here only to the extent it affects Insiden).

### Other browser/Firebase APIs

- No Firestore/Storage/Analytics/localStorage/sessionStorage usage anywhere under `src/app/insiden/**`. The only Firebase touchpoint is indirect: `ImageUploadService` calls `AuthService.getIdToken()` (Firebase Auth) to attach the upload header — Insiden itself never calls Firebase Auth directly.

## State Management

No NgRx/global store. All state is component-local:

- `InsidenMainComponent`: `selectedDate`/`calendarMode`, the only state shared between the calendar and event-list siblings, kept in sync purely via `@Input`/`@Output` binding (no shared service/subject).
- `CalendarComponent`: keeps its own `QueryRef` (`watchQueryOption`) alive for the component's lifetime; `monthEvents`/`yearEvents` accumulate across `fetchMore` calls and are never reset/cleared (see Known Quirks — this means switching back and forth between wide date ranges keeps growing these maps in memory for as long as the component instance lives, which for a page-level component is the whole time the user stays on `/insiden`).
- `EventListComponent`: recreates variables and calls `fetchMore` on every `ngOnChanges`; `data`/`dataLength` are fully replaced (not merged) each time, so no stale-accumulation issue here (unlike the calendar).
- `EventCardComponent`: no external service does anything with severity/incident data beyond rendering; the only cross-component "state" leak is the `pendingUploads` array read directly off the `ImageDrawerComponent` instance via `drawerRef.getContentComponent()` at submit-time (a tight coupling between drawer content and its host card, rather than an `@Output` event).
- `ImageUploadService` (app-wide singleton, `providedIn: "root"`): holds the **global** upload queue (`pendingUploads`) and progress `BehaviorSubject`s (`$pendingUploadCount`, `$totalUploadCount`, `$percentUploaded`) shared across the whole app (also used by the Spotting feature) — not reset when navigating away from `/insiden`, so an in-flight incident-photo upload queued from this page continues running (via its `setInterval`) even after the user leaves the route, until it drains or the whole app is reloaded.
- Apollo's `InMemoryCache` (see `graphql.module.ts`) is the only cross-request cache; none of these services set custom `fetchPolicy`s, so default Apollo caching/normalization applies. Cache keys are whatever Apollo infers (no explicit `id`/`__typename` key config visible in this scope) — worth verifying cache normalization actually keys `CalendarIncidentScalar` by its `id` field correctly given the multiple differently-shaped queries hitting the same `calendarIncidents` root field (min/details/medias variants each request different sub-fields for what may be the same underlying object).

## Permissions, Roles & Flags

- **Route-level**: fully public, no guard (see Path(s) & Routing).
- **Template-level**: no `*ngIf` role/claim checks anywhere in this feature's templates — every visitor sees identical UI.
- **Backend read access**: fully public/unauthenticated — no `permission_classes` on any Incident GraphQL field, and the `/graphql/` endpoint itself requires no auth (see Data & API Contracts intro).
- **Backend write access**: the sole write surface (photo upload) requires a valid Firebase-authenticated user (`401` otherwise) but **no role/claim beyond "is logged in"** — no `admin`/`betaTester` custom-claim check, and (unlike the analogous Spotting-event upload path) no ownership check tying the uploader to the incident at all. Any signed-in user can attach a photo to any `calendar_incident_id`, including nonexistent ones (silently accepted at upload time — see moderation pipeline).
- **Incident content authoring** (title/brief/severity/chronology/details/categories/line-vehicle-station tagging) is **Django-admin-only** (`/home/kwongtn/rosak_backend/incident/admin.py`) — there is no corresponding concept of "role" in the public app for this at all; it's entirely outside the Firebase-auth/custom-claims system covered by `auth-permissions.ts`.
- **Maintenance flag**: `maintenance.insiden.curentlyInMaintenance` in `app-routing.module.ts` (currently `false`) can swap the whole route to a `ConstructionComponent` placeholder — see the copy-paste bug noted in Path(s) & Routing regarding the static `component:` fallback checking the wrong flag.
- Nav badge tags "Beta" (`app.component.ts:31`) is presentational only — it does not gate access, merely flags the feature as unstable in the UI copy.
