# Component: spotting

## 📌 Purpose & Scope

- **Core Responsibility:** TranSPOT, the app's public, crowd-sourced train and rolling-stock spotting log, and the flagship feature. Anyone can browse each rail line's vehicles (current status, spotting history, incident timeline). Logged-in users submit "I saw this vehicle" reports (status, location, wheel condition, photos). The app's landing route is `home` (see `docs/components/home.md`).
- **Domain/Layer:** Angular Presentation (standalone components, signals, route-lazy-loaded). Talks to the Django/Strawberry GraphQL backend (`operation`, `spotting`, `incident` apps), plus one legacy REST endpoint for a trend chart.
- **Subcomponents** (one feature, several route and leaf components):
  - `spotting-shell/`: route shell. Hosts nav, footer, `<router-outlet>`, and the cross-page "Add a Spotting Entry" sheet, whose form is created only once the sheet opens (`@defer`).
  - `spotting-redirect.page.ts` / `spotting.routes.ts`: bare `/spotting` redirects to the first line.
  - `line-overview/`: `/spotting/:lineId`. Fleet roster (`vehicle-list`, `vehicle-heatmap-preview`), `fleet-summary` chip row, `line-status-board`, `line-switcher` (mobile line picker).
  - `line-details/`: `/spotting/:lineId/details`. Analytics: `vehicle-spotting-grid` (heatmap grid), `vehicle-status-trend` (legacy chart), `station-assets-section`. Two optional tab sections sit on the route's optional `tab` segment: `situasi-section/` (the **situasi** tab: community links and rider reports for the line) and `insiden-section/` (the **insiden** tab: the line's incident list, polling like situasi).
  - `vehicle-detail/`: `/spotting/:lineId/vehicle/:vehicleId`. `vehicle-status-board`, `spotting-history`, `incident-timeline`. A non-numeric `vehicleId` is "not found" without a request.
  - `report-form/` + `report-spotting-button/`: the submission form (with `photo-picker`) and its page-level trigger buttons, decoupled through `ReportSheetService`.
  - `data/`: route-scoped store, GraphQL documents, and pure utilities (no components), including `fleet-counts.util.ts`.

## 🔌 Interface & Data Flow

- **Route params:** `lineId` (required on `line-overview`, `line-details`, `vehicle-detail`) and `vehicleId` (required on `vehicle-detail`). Bound from the router as `input.required<string>()` (`withComponentInputBinding`).
- **`SituasiSectionComponent.lineId`** (`input.required<string>()`) is the situasi tab's only input. The panel mounts only while `line-details.page.ts`'s `activeTab()` is `"situasi"`.
  - Reads one page of `PUBLIC_SOCIAL_MEDIA_LINKS_QUERY`, filtered to the line, and sorts newest-first by the displayed instant `linkDisplayInstant(link)` (`features/insiden/data/link-day-group.util.ts`: `occurredAt ?? created`, matching the connection's `-occurredAt, -id` order). A plain string `localeCompare` is correct because both fields are naive local wall time from one serializer (backend `USE_TZ = False`).
  - Renders through the shared insiden `app-link-list` and link sheet. A `PollingSource` reloads it on an interval picker.
  - It deliberately does **not** send `collapseThreads`. Thread UI exists only on the home feed and the admin console. A per-line filter needs a flat, complete list, and collapsing would silently hide every thread member. The same rule applies to `insiden-section` and to per-incident link lists.
- **Other `input()` / `input.required()` signals** (selected):
  - `VehicleListComponent`: `vehicleType`, `statusFilter`, `sortColumn`, `sortDirection`, `stickyOffset`.
  - `VehicleSpottingGridComponent`: `lineId`, `vehicleTypes`, `months`, `statusFilter`, `stickyOffset`.
  - `FleetSummaryComponent`: `vehicleTypes`, `activeStatus`, `compact`. `StationAssetsSectionComponent`: `lineId`, `stickyOffset`. `VehicleStatusTrendComponent`: `lineId`. `LineSwitcherComponent`: `lines`, `currentLine`. `ReportSpottingButtonComponent`: `userClass` (aliased `class`).
  - Sticky-header components take a measured `stickyOffset` number (default `0` or `117`) from a parent that observes its own rendered height (`ResizeObserver` / `observeHeight`).
- **Outputs (`output()`):** `FleetSummaryComponent.statusSelected`; `VehicleListComponent.statusSelected` / `sortChanged`; `LineSwitcherComponent.lineSelected`; `ReportFormComponent.submitted` (fired on successful submit; the host closes the sheet, either `spotting-shell` or home's copy). `PhotoPickerComponent.files` is a two-way `model<ImageFile[]>()`.
- **Query params (`line-overview` only):** `LineOverviewPage` (`line-overview/line-overview.page.ts`) owns `sortColumn` / `sortDirection`. The sort is fleet-wide, shared by every `VehicleListComponent` on the page, not per vehicle type. It mirrors to `sort` / `dir` query params: read via `queryParamMap` → `toSignal`, written by browser-only `Router.navigate` with `replaceUrl: true`. Defaults (`identificationNo` / `asc`) are omitted, so an unsorted view has no query string.
  - Desktop line chips and `LineSwitcherComponent` pass `queryParamsHandling: 'preserve'` when switching to a _different_ line, so the sort carries over. Re-selecting the active line uses default navigation, which drops the query. That is the deliberate "reset to default" gesture.
  - `line-details`' `statusFilter` and `months` are **not** URL-synced.
- **GraphQL** (`data/spotting.queries.ts`; all POSTed through `graphqlResource` / `GraphQLClient` to one endpoint):
  - `LINES_QUERY`: line list. Backs the redirect and tab nav.
  - `VEHICLE_TYPES_QUERY`: per-line fleet table (status counts plus vehicle rows). Requires `DISTINCT: true` to avoid backend join duplication (a known backend quirk). `vehicle-detail` also reads it, in the browser only, for the vehicle-switcher combobox.
  - `VEHICLE_HEADER_QUERY` (`VehicleHeader`): `vehicles(filters: { id })` with the header and status-board fields of ONE vehicle (about 1 KB). `VehicleHeader` is `VehicleRow` minus `lastSpottedAt` and the input type of `VehicleStatusBoardComponent`.
  - `LINES_AND_VEHICLES_QUERY`: report-form dropdowns. `STATION_LINES_QUERY`: station options for `AT_STATION` / `BETWEEN_STATIONS`.
  - `VEHICLE_EVENTS_QUERY`: paginated (`limit` / `offset`) spotting history for one vehicle. Every field it selects is rendered by `SpottingHistoryComponent`: date, type, stations, status and notes, plus `runNumber` ("Run 12"; the API sends `""`, not null, when none was given), `wheelStatus` (`wheel-status-badge`, labelled "Wheels" so a bare "Flat" is not read as the train's status), `mediaCount` (a "3 photos" camera chip; not a link, because `medias` has no filter by spotting) and `isMine` (a "Yours" tag). Month headings are `h3`, one level under the card's `h2`. `isMine` is the one viewer-dependent field: the backend answers it only for a request that carries `firebase-auth-key`, so the history sends the signed-in viewer's token and asks for the first page again (swapped in where it stands) when they sign in or out. The server render, and a hard load before Firebase has restored the session, ask anonymously, so every row reads `isMine: false` until the token request lands. Do not drop the header, and do not let a signed-in request be answered from the SSR transfer cache (see `GraphQLClient` below). It selects no `location`: no template renders it, and the backend shows an anonymous report's position only to its reporter and admins.
  - `VEHICLE_SPOTTING_HISTORY_QUERY`: raw per-event date and type list, bucketed client-side into heatmap points. This avoids a backend aggregate field that hangs.
  - `VEHICLE_INCIDENTS_QUERY`: per-vehicle incident timeline.
  - `LINE_SPOTTING_GRID_QUERY` / `LINE_SPOTTING_BOUNDS_QUERY`: bounded-date-range vehicle × day counts for the details grid, plus a wide monthly-bucketed variant for month-nav bounds. The grid query sends `addZero: false` (a missing key reads as 0 in `spottingCountFor`; zero-filling a real line-4 window was about 10.7k rows / 690 KB against about 230 rows / 15 KB).
  - `LINE_STATION_ASSETS_QUERY`: per-station assets (`id`, `assetType`, `status`, `officialid`, `shortDescription`). Read-only. `status` is the `AssetStatus` enum (`IN_OPERATION` / `UNDER_MAINTENANCE`), maintained in the backend, not reported by riders. Never select `Asset.stations`: it errors at runtime.
  - `ADD_SPOTTING_EVENT_MUTATION` (`addEvent`): returns `{ id }` only, used to enqueue photo uploads. A LOCATION report sends `accuracy`, `latitude` and `longitude` only; the backend's other optional fields (altitude, altitudeAccuracy, speed, heading) stay unset.
  - Legacy REST: `GET {backendUrl}operation/line_vehicles_status_trend_count/:lineId/:source/:start/:end/` via `httpResource`, for `VehicleStatusTrendComponent`. No GraphQL equivalent exists.
- **Dependencies (shared services and state):**
  - `core/graphql/graphql-client.ts`: `graphqlResource()` (reactive wrapper over `httpResource`; auto-retry with backoff; SSR-safe; `data()` and `errors()` never throw and `data()` keeps the last good payload while the same request fails or retries; `retainDataIfEqual` keeps the previous `data()` reference when a refresh is structurally equal) and `GraphQLClient` (imperative `request()` for mutations and viewer-dependent reads; a request that carries `firebase-auth-key` sets `transferCache: false`, because the SSR transfer cache keys on method, URL and body, not headers, and until the app first settles it would answer a signed-in viewer with the server's anonymous render of the same query). `core/graphql/submit-failure.ts`: `toastSubmitFailure()`, called by the report form's submit `catch` for any error `GraphQLClient` did not toast.
  - `core/graphql/types.ts`: enums `LineStatus`, `VehicleStatus`, `SpottingVehicleStatus`, `AssetStatus`, `WheelStatus`, `SpottingType`, `IncidentSeverity`.
  - `AuthService` (`core/auth/auth.service.ts`): `isLoggedIn`, `login()`, `idToken()`. Gates form submission, and `SpottingHistoryComponent` reads `isLoggedIn()` and `idToken()` to send the viewer's token with the history query.
  - `core/util/web-storage.util.ts`: best-effort `sessionStorage` access for the saved draft (a failed read is `null`, a failed write is dropped), plus `readSessionDraft` and the `rosak:draft:` prefix that ties a draft to the account it was saved under.
  - `core/upload/`: `image-upload.service.ts` (app-wide photo queue, IndexedDB-persisted via `upload-queue-db.ts`, `PromisePool`-bounded concurrency; every file passes `stripGps` right before it is sent), `strip-gps.util.ts` (lossless Exif GPS removal for JPEG, TIFF and PNG; XMP GPS in TIFF/PNG and PNG "Raw profile type exif" chunks are not cleaned), `image-compression.service.ts` (client-side JPEG resize), `image-file.ts`. Used by `PhotoPickerComponent` and `ReportFormComponent`. `PhotoPickerComponent` accepts every image (`image/*`, or an empty `file.type` since some browsers give HEIC none); only non-images are skipped. Formats `stripGps` cannot clean (HEIC, WebP, AVIF, ...) upload as they are, GPS included, by the owner's choice. A photo over 9 MB that the browser cannot decode (HEIC) falls back to the original with `toCompress: false`.
  - `domain-ui/*`: `line-status-badge`, `vehicle-status-badge`, `wheel-status-badge`, `asset-status-badge`, `spotting-type-badge`, `spotting-activity-heatmap` (plus `spotting-count-tooltip`, `dateKeyOf`, `toSpottingActivityPoints`, `spottingIntensityClass`).
    - `asset-status-badge` (`status = input.required<AssetStatus>()`) reads `IN_OPERATION` as "In service" (success) and `UNDER_MAINTENANCE` as "Out of service" (destructive, the same red as the vehicle badge's "Out of Service"). The state is text, never colour alone, and a visually hidden `Status:` prefix makes a screen reader say what the bare words describe. A status its table does not list (the backend enum grew first) shows as a neutral "Unknown" rather than a blank pill.
  - `ui/*` (Spartan/Hlm): button, input, checkbox, native-select, combobox, sheet, skeleton, badge, card, table, retry-banner, toast service.
  - `core/dom/observe-height.ts`: measures a sticky bar's rendered height for stacked-sticky offset math.
  - `data/fleet-counts.util.ts`: `fleetCountChips`, shared by `FleetSummaryComponent` and the line-details mobile chip.
  - `core/methodology/`: the `fleet.in-service-share` MetricDoc supplies the mobile chip popover content (via `renderMethodologyCopy`).
  - `@angular/forms/signals` (`form`, `schema`, `required`, `validateTree`, `submit`, `FormField`): backs `ReportFormComponent`.
  - `@spartan-ng/brain/hover-card`: desktop vehicle-name hover preview in `VehicleListComponent`.

## ⚙️ Internal State & Logic

- **Line store:** `SpottingLinesStore` (`data/spotting-lines.store.ts`) is `providedIn: "root"` (home's report form uses it too). It wraps one `graphqlResource(LINES_QUERY)` and exposes `lines` (sorted by code), `firstLineId`, and `lineById()`. One fetch serves the redirect, overview, details, vehicle-detail, and the report form's line dropdown.
- **Route persistence (opt-in):** there is no app-wide normalized cache. Each `graphqlResource` stays scoped to its owner. The three page routes set `data: { reuse: true }` (`spotting.routes.ts`). `ReusableRouteStrategy` (`core/routing`; spotting is its first consumer) keeps those routes mounted, in a bounded LRU of `MAX_REUSABLE_ROUTE_HANDLES = 10`, keyed by route config and path params (the optional details-tab matcher param is excluded). `RouteScrollMemoryService` restores window scroll. On return, each data owner revalidates silently; `retainDataIfEqual` avoids needless re-renders.
  - A new data-owning section calls `revalidateOnReturn(<pattern>, () => resource.reload())` from its constructor, using the matching predicate from `data/spotting-route-patterns.ts` (`isSpottingLineRoute`, `isSpottingDetailsRoute`, `isSpottingVehicleRoute`). Keep the hook alive with its owner. It skips the first activation and same-pattern param or query navigations, and reloads only when the route is re-entered from outside.
  - `SpottingHistoryComponent` is deliberately excluded. Its imperative append pagination must not reset on return.
- **Cross-page trigger decoupling:** `ReportSheetService` (`data/report-sheet.service.ts`, root) holds `isOpen` and a `lineId` seed (`null` = start blank), with `open()`, `openFor(lineId)` and `setOpen()`. The sheet lives once in `SpottingShellPage` and once on home (see `home.md`). Trigger buttons call `.open()` and never reference the sheet or form. `openFor` is page-scoped: the form applies the seed on its closed→open edge and consumes it, so a later seedless `open()` starts blank (or from the saved draft, below). `setOpen(false)` also clears the seed, because the form is created on the first open: a seed from an abandoned open must not reach a form created later.
- **Deferred sheet form:** the shell's sheet holds `@defer (when reportSheet.isOpen(); prefetch on idle) { @if (true) { <app-report-form #reportForm> } }`, so the form's fleet-wide `LinesAndVehicles` read never runs on the server (no `LinesAndVehicles` entry in TransferState). The footer reads the form through `reportFormRef = viewChild<ReportFormComponent>("reportForm")` (a string locator, so the form's chunk stays out of the shell), null-safe, and keeps Submit disabled until it exists. `@if (true)` creates and binds the form in the block's own refresh; a cold open otherwise throws NG0950. The form focuses its first control in `afterNextRender` when its sheet is open, because the sheet's focus trap has already captured focus onto the footer by then.
- **Report form** (`report-form/`):
  - Signal Forms: `signal(emptyReportFormModel())` plus `form as createForm` over `reportFormSchema` (`report-form.schema.ts`). The schema declares `required()` field rules and one `validateTree()` cross-field validator: station requirements for `BETWEEN_STATIONS` / `AT_STATION`, and the "abnormal vehicle status" sanity gate.
  - `effect()`s keep derived fields in sync: clear the vehicle on line change, mirror `selectedVehicleStatus`, and reset the form in memory (`resetForm()`) when the sheet closes, which keeps the saved draft.
  - **Saved draft (`sessionStorage`, one slot).** A browser-only effect saves the model (no `selectedVehicleStatus`, which is derived; no photo files, no GPS position) plus the photo count under `REPORT_FORM_DRAFT_KEY` (`rosak:draft:spotting-report:v1`, `report-form-draft.util.ts`) while the sheet is open. A restored draft keeps its photo count until the form resets (the larger of the restored count and the photos on the form), so a reload after an edit still asks for the photos again. The draft belongs to an account: `AuthService` removes every `rosak:draft:` key when a different account, or nobody, is signed in, and the restore reads through `readSessionDraft`, which hides a draft saved for another account until the page knows who is signed in (`core/util/web-storage.util.ts`). A draft saved while signed out survives the sign-in. It is gated on `_draftBaseline`, which only the open edge sets, and it writes only once the model differs from what the open edge produced (or a draft was restored), so an untouched seeded open saves nothing. The open edge restores the draft BEFORE applying the seed: an unseeded open restores any draft, a line-seeded open only a draft for that line or for no line, and a draft for another line stays saved for its own open. A restore sets `_lastLineId` first, or the line-change effect would drop the restored vehicle, and re-requests the position for a `LOCATION` draft. `report-form-draft-restored` ("Draft restored.", plus "Photos aren't saved with a draft, so add them again." when it had photos) sits BELOW the Line field, because the sheet's focus trap and the form's own first-render focus take the first control. Its `report-form-draft-discard` moves focus to the Line picker, then calls `clear()`. `clear()` (Clear form, Discard, a successful submit) also forgets the saved draft; closing the sheet does not. `parseReportFormDraft` returns `null` for unknown, malformed or empty storage, checks each field on its own and never throws.
  - The line and vehicle `HlmCombobox` pickers bind `emptyValue=""`, and the station `<select>` placeholder options are not `disabled`. So clearing a picker, or re-choosing `Select a station`, really deselects. Emptying a combobox resets its `value` to the sentinel, so the shared `_syncSearchToValue` cannot resurrect the old label (see `MISTAKES.md`). Enter commits only a row the user reached with ArrowUp/ArrowDown or a non-empty query's highlighted match. Clearing a field and pressing Enter is a no-op, not a re-commit of the stale item.
  - The station `graphqlResource` reads two projected computeds (`_stationLineId` / `_stationType`), not the whole model. Only a line or type change re-issues `STATION_LINES_QUERY` (`StationLinesByLine`), not every Notes keystroke (see `MISTAKES.md`).
  - Vehicle picker order: A→Z by identification number, numeric-aware (`Set 2` before `Set 10`), with `MARRIED` / `DECOMMISSIONED` vehicles demoted to the bottom. `sortVehiclesForPicker` (`data/vehicle-search.util.ts`) does this after the response's vehicle types are flattened. It is deliberately not in the shared `LinesAndVehicles` resolver, since the fleet tables keep type grouping.
  - The selected vehicle's status badge renders in the combobox's `trailingTemplate` slot (right-aligned, `pointer-events-none`). The abnormal-status sanity check sits directly below the vehicle field.
  - The Location (GPS) helper text is ONE persistent `<p role="status">` (a swapped `<p>` would not be announced) and says the spotted position is shown publicly with the report, and that with "Submit anonymously" only the reporter and admins see it. There is no "Location accessed" toast. A submit failure that `GraphQLClient` did not toast (offline, 429, 5xx) gets `toastSubmitFailure()` and is rethrown to Sentry.
  - Field wrappers are plain `<div>`s, not `<label>`s, so clicking visible text never focuses or opens a picker. Accessible names live on the controls as `aria-label`. The two checkbox rows keep real `<label>`s so their text still toggles the box.
- **Vehicle detail data flow** (`vehicle-detail/vehicle-detail.page.ts`): the header and status board come from `VEHICLE_HEADER_QUERY` (`vehicleResource`); the incident timeline, spotting history and activity heatmap need only `vehicleId()`, so all of them request in parallel. The line roster (`VEHICLE_TYPES_QUERY`) loads in the browser only and feeds just the switcher combobox, which offers only the current vehicle until the roster arrives and sits OUTSIDE the header's `@if`, so it stays mounted (and keeps keyboard focus) while the next vehicle loads. A non-numeric `vehicleId` sends no request and is "not found" (`_hasNumericId`). `_isNotFound` is an answered-and-empty header (`data()` is `undefined` while a request is in flight, including right after `vehicleId` changes, and `hasError()` covers a failed one; `isLoading()` is first-fetch-only, so neither reads as not found); its toast and redirect run in `untracked()`, or the toast list's read-then-write re-runs the effect forever. `_showDetails` (no error, not not-found) mounts the timeline, history and the ad slot, which stay `display:none` until the header exists so they appear in the same frame and no ad is requested early. `LineOverviewPage`'s unknown-line fallback follows the same `untracked()` rule.
- **Per-component local signals:** status filters (`statusFilter`), expand/collapse (`isExpanded`, `collapsedTypes`), pagination (`SpottingHistoryComponent._eventsByVehicle`, keyed by vehicle id; a request counter drops an answer that a newer request has replaced, and the first page, asked again for a new viewer, replaces the list in place), and hover state (`VehicleSpottingGridComponent.hoveredCell`). The exception is `VehicleListComponent`'s sort. It is owned by `LineOverviewPage` (URL-synced, above) and passed down as `input()`s, so every vehicle-type table on the line sorts in lockstep.
- **Line-details grid** (`vehicle-spotting-grid/`):
  - Pure logic lives in `vehicle-spotting-grid.data.util.ts` (section, month and count builders, layout constants) and `vehicle-spotting-grid.layout.util.ts` (`monthLabelShift`, day-cell class builders). `vehicle-spotting-grid-{date-row,day-mirror,mobile-pinned,name-row,mobile-name-row}.component.ts` are presentational children.
  - The parent keeps the sticky-pin and hydration core, plus the template refs (`#bodyScroll`, `#gridContainer`, `#namesTbody`, `#sectionAnchor`, `#monthLabel`) that the scroll and measure effects read.
  - Below 768px (Tailwind `md`) each vehicle and vehicle type is a full-width NAME/TYPE row, directly above its own horizontally scrolling date/totals row. Name and type stay pinned left as dates scroll. Desktop is unchanged.
- **Sticky layout** (`line-overview`, `line-details`, grid): sticky headers stack (nav → line bar → section header → column header), so components measure rendered heights (`ResizeObserver`, `IntersectionObserver`, scroll listeners) instead of hardcoding pixels. This is presentational, not domain state.
  - On `/spotting/:lineId/details`, the title bar (`#titleBar`) sticks on md+ and on the mobile Spotting tab (it anchors on scroll; on other mobile tabs it is `static`). Once the Key Line Data chips scroll away (`_scrolled`), it hands off (`titleBarHandedOff()`). It slides up behind the nav (`-translate-y-full` plus `inert` / `aria-hidden`), and the "Spotting Activity" bar (`#activityControls`) becomes the pinned header. That bar shows the merged identity: title `{line.code} - Spotting Activity`, `line-status-badge`, an in-service chip, and a `<` back chevron that replaces the scrolled-away back link. The month nav right-aligns when it wraps.
  - Offsets: on desktop, the activity bar top and grid `stickyOffset` = `61 + titleBarHeight [+ activityControlsHeight for the grid]`. On mobile the same formulas apply until the handoff, after which the title height drops out (`61 [+ activityControlsHeight]`). The assets section pins at 61 on mobile.
  - Trap: the chevron binds its display classes as an `inline-flex` / `hidden` pair, because the compiled stylesheet orders `.inline-flex` after `.hidden`.
  - The in-service chip is an `app-info-popover` (`align="start"`, no icon). Its hover and tap content comes from the methodology registry (`fleet.in-service-share` via `renderMethodologyCopy(metricDoc(...).definition)`), plus a `popoverExtra` breakdown (Total and each non-zero status as `<ul>/<li>` with `tabular-nums`). It links to `/methodology#line-status`.
  - Grid viewport: `isNarrow` is initialised synchronously from `window.matchMedia("(min-width: 768px)")`, so the first render picks the right branch. A `change` listener keeps it live and is torn down via `DestroyRef`. SSR has no viewport, so the server always renders the desktop branch, and since `REQUESTS_CONTRIBUTE_TO_STABILITY` defaults to `true` it awaits the GraphQL POST and renders that desktop grid with real data. A viewport-conditional `@if` would mismatch hydration on mobile. The grid therefore sets `host: { ngSkipHydration: "" }` (Angular's documented remedy, same as `app-info-popover`) and re-renders on the client.
  - Neither layout uses `position: sticky` inside the `overflow-x-auto` body. Sticky is inert inside an ancestor that never scrolls vertically, so the desktop mirror and the mobile 2-row pinned overlay are page-sticky siblings of that body. Each pinned name or type cell is an inner `<div class="sticky left-0">` inside a full-width `colspan` `<td>`, never the `<td>` itself.
  - Month labels in the translated header table hand-roll their own two-edge sticky (`monthLabelShift`). Both clamps are bounded by the label's own month box, so it rides the leading edge in and out on the right as it rides the trailing edge on the left, and rests centred once clear. It never leaves its `<th>`, which only clips it as a backstop.

## 🧩 Extension Points & Hooks

- **`ReportSheetService`:** the seam for new triggers. Inject it and call `.open()` (or `.openFor(lineId)` for a line-scoped trigger). No wiring in `spotting-shell` is needed. A host of the sheet must put the form behind the same `@defer` block.
- **`report-form.schema.ts`:** declarative validation. New field rules or cross-field constraints are additive `required()` / `validateTree()` calls, not component logic.
- **`spotting.queries.ts`:** the single seam for all GraphQL contracts in this feature. New fields and queries go here with paired TS interfaces, keeping query strings out of components.
- **`vehicle-search.util.ts`** (`numberSeenToSetNumbers`, `allowRunNumber`): an isolated, line-keyed table for "run number painted on the train" → internal vehicle ID heuristics. New lines or classes are added as table entries.
- **`HlmCombobox`** (`ui/combobox/combobox.ts`): an optional `trailingTemplate` input renders right-aligned before the chevron. While present, the input's right padding grows (`pr-36` instead of `pr-6`) so typed text never runs under it. Its `ariaLabel` input (alias `aria-label`) forwards to the inner `<input>` and the listbox (the vehicle switcher is "Switch vehicle", the calendar's pickers "Month" and "Year"). It follows the ARIA editable-combobox pattern: the input is the `role="combobox"` and keeps DOM focus (`aria-expanded`, `aria-controls` a per-instance listbox id, `aria-activedescendant`); the list is `role="listbox"` of `role="option"` rows (`aria-selected` on the highlighted one, scrolled into view by the arrow keys); a visually hidden `role="status"` line announces the result count. Escape closes an open list and stops propagating, so it does not also close the enclosing sheet; a closed combobox lets Escape through.
- **`StationAssetsSectionComponent`:** read-only listing with each asset's `asset-status-badge` and a note (outside the sticky header, so the pinned bar stays one line on a phone, and shown only while at least one asset is listed) that the MLPTF team sets the status, it is not reported live by riders, so it can lag behind a breakdown. Its doc comment flags it as the first half of a "volunteers report station asset breakages" feature; the reporting half has no backend yet.
- **`VehicleStatusTrendComponent.DATA_SOURCES`:** reserves a disabled `"prasarana"` source beside the live `MLPTF` and `MTREC`. Enabling a third source is a config-table change plus a real backend endpoint, not a UI rewrite.
- **`graphqlResource()`:** a generic wrapper (auto-retry, SSR TransferState, loading and error semantics). Any new query in this or other features plugs into it.

## 💡 Potential Feature Opportunities

- **URL-synced filters on `line-details`.** `line-overview`'s sort already uses the pattern to copy: `toSignal(route.queryParamMap)` to read, browser-only `router.navigate` with `replaceUrl: true` to write, defaults omitted from the query string. `VehicleSpottingGridComponent`'s `statusFilter` and `months` (owned by `line-details.page.ts`) are still plain local signals. Ready to implement by lifting that pattern. `months` is a computed date range rather than a flat enum, so it needs its own encoding (e.g. an ISO month key).
- **Station asset breakage reporting.** Not ready. Showing the team-maintained `Asset.status` is done (above); rider reporting is not. The backend has no asset mutation (the Django admin is the only writer), and no rule for turning rider reports into a status without overwriting the team's. A backend mutation (shaped like `ADD_SPOTTING_EVENT_MUTATION`: login required, rate-limited per user and asset) and that rule must land first. The local database has no assets, so seed some before building the report button. Once they exist, add a "Report a problem" button per row (the report-sheet pattern) and register the rule in the methodology registry.
- **Enabling the "Prasarana" source.** Not ready. Flipping `disabled: false` today would call the legacy REST endpoint for a source with no real backend data. It is purely a backend-data gap. Once that endpoint serves real `prasarana` data, enabling it is a one-line config change.
- **Infinite scroll on vehicle history.** Ready. `SpottingHistoryComponent` (`vehicle-detail/`) already does offset/limit append (`PAGE_SIZE = 20`, `hasMore` from a full-page check) behind a "Load more" button. The shared sentinel directive `appInfiniteScroll` (`ui/infinite-scroll/`; emits `loadMore`, takes `appInfiniteScrollLoading`) is already used by insiden's incident card. Swapping the button for it is a small, self-contained UI change with no new queries. The same change could be replicated in profile (`MySpottingsComponent`) and console for consistency. The button was chosen to avoid scroll listeners bound to table markup; a sentinel below the list does not need that.

## 💡 Potential AI Feature Opportunities

- **Vehicle identification from photos.** `numberSeenToSetNumbers` is a hand-maintained heuristic mapping a photographed run number to a probable vehicle ID. An OCR or vision step on `PhotoPickerComponent`'s photos could pre-fill the vehicle combobox from a photo of the train's painted number.
- **Anomaly / incident triage.** `IncidentTimelineComponent` and `VehicleStatusTrendComponent` already expose structured per-vehicle status and incident history. A model could flag unusual transitions (e.g. a vehicle reported `OUT_OF_SERVICE` then `IN_SERVICE` repeatedly in a short window), or draft an incident `title` / `brief` from a cluster of recent free-text `notes`.
- **Conversational report entry.** The form's progressive disclosure (line → vehicle → type → conditional station or location fields) and its schema validation map onto an assistant that fills the same `ReportFormModel` from a free-text or voice description ("saw train 4123 at KLCC heading to Gombak, wheels look worn"). The existing validators still gate submit.
