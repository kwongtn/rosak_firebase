# Component: console

## 📌 Purpose & Scope

- **Core Responsibility:** Admin-only moderation queues under `/console`:
  - **Spotting queue** (`/console/spotting`) — filters the crowd-submitted vehicle "spotting" event backlog (status, spotting type, date ranges, anonymity, read/notes flags, free text), pages through it, and bulk-marks a selection as read.
  - **Incident approval queue** (`/console/insiden/pending`) — see its sub-section.
  - **Social-media link triage** (`/console/links`) — see its sub-section.
- **Domain/Layer:** Angular Presentation (standalone, lazy-loaded routed pages) over the Django/Strawberry GraphQL backend (`rosak_backend`) via HTTP; no SSR data beyond auth/token resolution.
- **Location:** `src/app/features/console/`
  - Spotting queue: `console.page.{ts,html}`, `console.routes.ts`, `data/console.queries.ts` (GraphQL documents + DTOs). `console-nav.component.ts` is the section switcher every console page renders.
  - Incident + link pages live under `insiden/` (`pending/*`, `links/*`, `data/*.queries.ts` / `*.util.ts`). The folder name stays `insiden/` even though the links URL is `/console/links`.
  - Both big pages are **shells over colocated pure utils plus presentational children** (attribute-selector hosts such as `tr[app-pending-row]`). The parent keeps every stateful handler because its spec drives them directly off the component instance.
- **Lineage:** Ported from the legacy `src/app/console/`, deliberately not 1:1. The old app built its filter with flat `statusIn`/`typeIn` keys that don't exist on the backend `EventFilter`, so Status/Spotting-Type silently no-opped. This version sends `status: { inList }` / `type: { inList }`.

## 🔌 Interface & Data Flow

- **Routes** (`CONSOLE_ROUTES`):

  | path                                  | target                                               | guard            |
  | ------------------------------------- | ---------------------------------------------------- | ---------------- |
  | `""` (`pathMatch: "full"`)            | `redirectTo: "spotting"`                             | none (redirect)  |
  | `spotting`                            | `ConsolePage`                                        | `adminOnlyGuard` |
  | `insiden/pending`                     | `PendingIncidentsComponent`                          | `adminOnlyGuard` |
  | `links`                               | `SocialMediaLinksComponent`                          | `adminOnlyGuard` |
  | `insiden/links` (`pathMatch: "full"`) | `redirectTo: "links"` (legacy bookmark / shared URL) | none (redirect)  |
  - `pathMatch: "full"` on the bare redirect is **mandatory**, or it would also swallow `/console/insiden/*` and `/console/links`.
  - Angular rejects `canActivate` on a redirect route. Both redirect targets are guarded, so `/console` and `/console/insiden/links` are guarded transitively.
  - `adminOnlyGuard` (`core/auth/admin-only.guard.ts`) awaits `auth.whenReady` and redirects non-admins to `/spotting`. It is **not** a stub — do not "re-fix" it (see AGENTS.md).
  - Nav: `shell/nav-config.ts::CONSOLE_LINKS` is the one list of console sections (`console-nav.component.ts` renders it; `<app-nav>` and `<app-compact-nav>` read it too). It points at `/console/links` (never the legacy path) so `RouterLinkActive` follows the real URL, and the switcher marks the active pill with `aria-current="page"`.

- **Spotting page state** (`ConsolePage`; no `@Input`s or route params, all `signal`/`computed`):
  - `filterForm: Signal<FilterFormModel>` — draft filter: status[], spottingType[], created/spotted date ranges, four tri-state booleans (`isVehicleStatusDifferent`, `isAnonymous`, `isRead`, `hasNotes`), `freeSearch`. Default: `isRead: false`, everything else empty/`undefined`.
  - `events`, `totalCount`, `isLoading`, `hasMore` (default `true`).
  - `checkedIds` (`Set<string>`), `checkedCount`, plus the range anchor inside `useBulkActions()`.
  - `appliedFilters` — plain field, not a signal: the filter set actually sent; replaced only on **Search**.
- **GraphQL** (`data/console.queries.ts`):
  - `CONSOLE_EVENTS_QUERY` (`ConsoleEvents`) — vars `eventFilters: EventFilter`, `eventPagination: {limit, offset}`, `eventOrder: { created: "DESC" }`; returns `{ eventsCount, events: ConsoleEvent[] }`. Fetched with imperative `GraphQLClient.request()`, not `graphqlResource()`, because pagination is append-driven ("Load more") rather than a dependent-signal refetch.
  - `MARK_AS_READ_MUTATION` (`MarkAsRead`) — `{ input: { eventIds } }` → `{ markAsRead: { ok } }`. On `ok`, rows are spliced out of `events`, the selection clears and a success toast fires. An exception fires an error toast.
  - No `@Output()`s; side effects are toasts or local signal mutation.
- **Dependencies:**
  - `GraphQLClient` (`core/graphql/graphql-client.ts`) — POST wrapper over `environment.backendGraphqlUrl`; throws `GraphQLRequestError` when a response carries a top-level `errors` array (even next to partial `data`) or has no `data` at all, and toasts and reports it to Sentry in the browser only.
  - `AuthService` — `idToken()` goes in the `firebase-auth-key` header of every console request.
  - `ReCaptchaV3Service` (`ng-recaptcha-2`, provided in `app.config.ts`) — `markAsRead` sends `g-recaptcha-response` because the backend enforces `IsRecaptchaChallengePassed` on it. `firstValueFrom` bridges the Observable into the async handler. (Profile's `deleteSpottingEntry` also sends a token, through the separate `core/recaptcha/recaptcha.service.ts`.)
  - `ToastService`, `RouterLink` (row vehicle → `/spotting/:lineId/vehicle/:vehicleId`), `AppNavComponent`/`AppFooterComponent` (`src/app/shell/*`), `VehicleStatusBadge`/`SpottingTypeBadge` (`src/app/domain-ui/*`), Helm UI kit (`src/app/ui/*`).
  - `environment.backendUrl` — deep links into the Django admin for an event / reporter.
  - Types mirrored from the backend: `SpottingType`, `SpottingVehicleStatus` (all 7 schema values), `VehicleStatus`, `WheelStatus` (`core/graphql/types.ts`).

## ⚙️ Internal State & Logic

- Signals only (no RxJS subjects/store/local DB).
- **Pagination is offset-based and additive:** `load()` requests `PAGE_SIZE = 100` at `events().length` and appends; `hasMore = (page length === PAGE_SIZE)`. **Search** resets `events`, `hasMore`, `checkedIds` and reloads from offset 0.
- **Two-phase filters:** `filterForm` (draft) vs `appliedFilters` (committed on Search), so editing never triggers a request. `buildFilters()` maps the flat model to the nested `ConsoleEventFilters` shape of the backend `EventFilter` input, omitting fields at their "don't filter" default.
- **Tri-state booleans** are `boolean | undefined`, rendered through native `<select>` (strings only); `triState()` / `onTriStateChange()` round-trip `"any" | "yes" | "no"`.
- **Selection** (`core/composables/use-bulk-actions.ts`, `useBulkActions()`; `ConsolePage` is its only consumer):
  - Always live — no mode toggle; the checkbox column, row highlight and "Mark N as read" need no enabling.
  - Clicking **anywhere** on a row body toggles it. The row's own checkbox is the same toggle via its native `click` (only a `click` carries `shiftKey`, not `checkedChange`) and stops propagation so the row handler can't fire twice.
  - The event-id and reporter deep links and the vehicle `routerLink` call `stopPropagation()` so activating them doesn't select the row. The row `<tr>` is not a focus target; keyboard selection goes through the checkbox's inner `<button role="checkbox">`, which carries modifiers into the same handler.
  - **Shift-click range:** `anchorId` is the last row clicked _without_ shift. A shift-click applies the clicked row's **new** state to the inclusive span anchor→row, resolved against rendered order (`events().map(e => e.id)`) — so shift-clicking a checked row un-checks the range. The anchor is deliberately **not** moved by a shift-click, so a second shift-click can retarget or undo the same range.
  - Pure core: exported `toggleCheckedRange(checked, orderedIds, anchorId, targetId, targetState)`; composable method `toggleCheckedInRange(orderedIds, targetId, targetState)`. No anchor, or an anchor/target no longer in the list, degrades to a single-row toggle (never throws).
  - Anchor is cleared by `clearSelection()` (also run on `search()` and a successful `markAsRead()`), whenever the selection empties, and on **every** `load()` (`resetAnchor()`): a search reset or appended page changes which ids sit at which index, so a stale anchor would sweep an arbitrary span.

## 🧩 Extension Points & Hooks

- **Filter model is additively extensible:** add a field to `FilterFormModel`, the default factory, the template and one `if` in `buildFilters()`; existing filters are untouched.
- **Query/mutation isolation:** all documents and DTOs live in `data/console.queries.ts`; new per-event actions are added there.
- **Bulk-action pattern is reusable:** `checkedIds` + a conditional action button is generic "select rows, then act" plumbing (bulk-delete/flag need only a new mutation). Any list that renders a row order can pass it to `toggleCheckedInRange(orderedIds, …)` for shift-click ranges.
- **`GraphQLClient.request()` vs `graphqlResource()`:** console uses the imperative API for append/pagination semantics; an infinite-scroll or virtualized rewrite could revisit that.

## 💡 Potential Feature Opportunities

- **Shareable/saved filter views:** `filterForm`/`appliedFilters` is a plain `FilterFormModel`, so it could serialize to route query params (e.g. "unread depot spottings with notes"). `ConsolePage` doesn't inject `ActivatedRoute` yet; build on `core/url-state/query-param.util.ts` (browser-gated merge/replace writes, pure SSR-safe reads) layered over `buildFilters()`. No backend change.
- **Bulk actions beyond mark-as-read:** small frontend change, but `console.queries.ts` only defines `MARK_AS_READ_MUTATION`, so a bulk-delete/flag mutation must land in the Strawberry schema first.
- **Sortable results table:** `eventOrder` is already wired and hardcoded to `{ created: "DESC" }`. The backend `EventOrder` (`spotting/schema/orderings.py`) exposes `id`, `spottingDate`, `created` only — no status/type sort without a backend change.
- **Client-side export of the current queue:** `events` holds the fetched set; a "Export CSV" button over `core/export/csv.util.ts` (`toCsv`/`downloadCsv`) needs no new query or backend change.
- **Select-all + tri-state header checkbox:** the header cell is still an empty `<th class="w-10">`. Needs a decision first: "all loaded rows" (a `setAll` on the composable) vs the whole `totalCount()` result (needs a new backend query), because "Load more" is append-only.

## 💡 Potential AI Feature Opportunities

- **Smart triage / auto-prioritization:** free-text `notes`, media counts and the "vehicle status differs" flag could drive an urgency/data-quality score instead of pure `created DESC`.
- **Natural-language filter input:** an LLM parser could turn "unread depot spottings from last week with notes" into the structured filter fields (alongside `freeSearch`).
- **Automated moderation assist:** an AI summarizer/anomaly detector over `notes`, `isAnonymous` and `mediaCount` could pre-flag spam/duplicate/suspicious submissions before human review.

## 🗂️ Sub-page: Incident Approval Queue (`/console/insiden/pending`)

- `PendingIncidentsComponent` (`insiden/pending/pending.component.*`, selector `app-console-pending-incidents`): lists `PENDING_APPROVAL` incidents (`pendingCalendarIncidents(search)`, oldest-first) with a debounced server-side text search (title/brief/details/chronology source URLs; `SEARCH_DEBOUNCE_MS`). The queue also carries `LIVE` incidents with a `PENDING_DELETION` chronology row (deletion requests: `APPROVE_/REJECT_CHRONOLOGY_DELETION_MUTATION`).
- Row **Approve** is immediate; **Reject** needs a reason entered in a modal sheet. Both remove the row locally on success.
- Row click opens a full editor (same field set as "Report an Incident", incl. the chronology editor with per-entry AI Extract — `EXTRACT_TIMEOUT_MS = 15_000` front-end cap over the 20 s function timeout; an answer inside the cap (data or `null`) resets the row's extract state, so the row is editable again — and Summarize). Save calls the `IsAdmin` `updateCalendarIncident`, which replaces the M2M sets and chronologies verbatim, so the payload is the complete form state; row and detail card are then patched locally.
- Hosts `app-incident-card` with `[editActionEnabled]="false"` (it has its own panel editing; see `insiden.md`).
- Children: `tr[app-pending-row]` (row + Approve/Reject), `section[app-pending-chronology-editor]` (presentational: every edit, field edits included, is emitted — `patch` carries a `ChronologyPatch` `{ key, field, value }` and the parent replaces that draft in a new list with `chronologies.update`, never an in-place write; the content textarea reports on `input`, the other fields on `change`), `section[app-pending-deletion-requests]`; pure `pending-incident.util.ts` (`severityBadgeVariant`, `severityLabelText`, `asCalendarIncident`, `isIncidentFormSaveable`, `buildUpdatedIncidentRow`, `ChronologyExtractState`).

## 🗂️ Sub-page: Social Media Links Triage (`/console/links`)

`SocialMediaLinksComponent` (selector `app-console-social-media-links`) is a separate lazy component with its own data layer, not a mode of `ConsolePage`.

### 📌 Purpose & Scope

- **Core Responsibility:** the admin triage queue for crowd-submitted social-media links — a moderation table over `socialMediaLinks` rendered as an **accordion over the ordered link tree** (collapsed by default, one row per link, children revealed beneath their parent). Server-side filters; per-row Approve / Unhide / Hide / Mark completed / Delete; a full editable detail panel; and the conversation hierarchy as both a moderation tool (multi-select → Group; per-row Nest under / Ungroup / Move up / Move down) and a display mode (chevron, one **rail** per ancestor level, a child-row tint, the `N links` chip).
- **Location:** `insiden/links/links.component.{ts,html}`; documents/DTOs in `../data/insiden-console.queries.ts`; pure helpers `../data/{date-range,link-status-input,search-debounce,same-minute}.util.ts`; shared insiden utils `insiden/data/link-occurred-at.util.ts` and `link-thread-selection.util.ts`. Colocated seams in `insiden/links/`:
  - `link-tree.util.ts` — `compareStoredSequence`, `computeDepths` (`depthOf`), `depthRailsFor` (`depthRails`), `groupRunsByParentId` (`_runsByParentId`), `childCountOf`, `siblingsOf`, `runOrderIsKnown`, `siblingIndexOf`, `canMoveUp`/`canMoveDown`/`moveBlockedReason`, `canNestUnder`/`nestBlockedReason`, `renderedLinksOf` (`renderedLinks`), `DEPTH_INDENT_PX`.
  - `link-reference.util.ts` — reference option builders (line/vehicle/station/category options, filter variants, vehicle parent-code indexing).
  - `link-queue-filter.util.ts` — `CompletedFilter`/`COMPLETED_LABEL`, `VisibilityFilter`/`VISIBILITY_LABEL`, `appliedFiltersAreUnfiltered`, `queueQueryVars`.
  - Children: `link-queue-row.component.*` (`tr[app-link-queue-row]`), `link-url-cell.component.*` (`td[app-link-url-cell]`: rails/elbow/chevron/chip), `links-filter-bar.component.*`, `links-selection-toolbar.component.*`. Templates in this folder and in `pending/` read `$event.target.value` through `core/util/dom-event.util.ts::eventValue` (a `protected readonly eventValue = eventValue` member), never `$any`.
- **Two clocks, on purpose:** the queue is **sorted** on the event instant (`occurredAt`; `-occurredAt, -id`) and the range filter windows the same column, but an admin _moderates_ against the report instant (`created`) — "how long un-reviewed" is a `created` question, "is this back-dated" an `occurredAt` one. The **Submitted** cell shows `created`, plus a quieter `Occurred {date}` second line (`data-testid="link-occurred"`) only when the two differ across **minutes**. The filter is labelled "Occurred between". The instants stay separate in the **payload** (`linkStatusInput`, the `occurredAt` note in `saveLinkEdit`): a save must not silently rewrite one as the other.
- **Permissions:** the route is admin-gated (see Routes above); the backend additionally refuses a non-admin status change, so row actions carry no second check.

### 🔌 Interface & Data Flow

- **Filters** (card above the table; `appliedX` plain fields hold what was last committed, so editing a control doesn't refetch until its own trigger fires):
  - Free-text search is **debounced**; Category, Status and Visibility selects refetch **immediately**; Line/Vehicle/Station and the date range refetch through the same trailing debounce; **Reset** clears everything.
  - Defaults: Status **Pending** (not-completed); Visibility **All links** (hidden rows included).

  | control                                                                                                 | backend argument                                   |
  | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
  | Search (URL, title)                                                                                     | `search: String`                                   |
  | Category                                                                                                | `categoryId: ID`                                   |
  | Status (All / Pending / Completed)                                                                      | `completed: Boolean` (omitted for "any")           |
  | Visibility (All links / Visible only / Hidden only; `data-testid="links-visibility-filter"`)            | `hidden: Boolean` (omitted for "All links")        |
  | Line / Vehicle / Station                                                                                | `lineId` / `vehicleId` / `stationId`               |
  | **Occurred between** (two `<input type="date">`, aria-labels "Occurred from date" / "Occurred to date") | **`occurredAfter` / `occurredBefore`: `DateTime`** |
  | (sorting, not a control)                                                                                | fixed `-occurredAt, -id`                           |
  - ⚠️ The date args were **renamed** from `createdAfter`/`createdBefore` with **no alias**: an alias would window one column while the rows are sorted by another. A stale `createdAfter` is a loud GraphQL "Unknown argument" — the intended failure. See `MISTAKES.md`.
  - `date-range.util.ts` (`dateInputToIsoStart` / `dateInputToIsoEnd`) builds bounds from the browser's **local** day (`T00:00:00` / `T23:59:59.999`) then `.toISOString()` — correct **here** only, because the bound is an _aware_ instant; the naive wall-time `occurredAt` field is the opposite case (documented in both files).

- **Query:** `SOCIAL_MEDIA_LINKS_QUERY` (console-scoped `socialMediaLinks`), fetched imperatively with a freshly minted `firebase-auth-key`.
  - Selects `occurredAt` and the four conversation scalars `parentId` / `isThreadRoot` / `sublinkCount` / `position`, all **required** on `SocialMediaLinkRow` (optional on the structural `LinkCardItem`), so document and row type can't drift.
  - `sublinks` is deliberately **not** selected: the accordion derives the hierarchy from `parentId` client-side over the flat array, and a nested list would let a HIDDEN row's URL/title travel inside an admin-gated query for nothing.
- **Mutations** (all send `firebase-auth-key`; all reload the list on success):
  - `updateSocialMediaLink` (**`IsLoggedIn`**, not `IsAdmin`) — Approve and Unhide (`status: "LIVE"`) and Hide (`"HIDDEN"`) build their payload through the single `linkStatusInput(link, status)`, which re-sends the row's `url`, `title`, all four M2M id lists **and `occurredAt` verbatim**. Both halves are load-bearing: `SocialMediaLinkInput` is replace-not-patch (otherwise the title blanks and every tag strips), and `occurredAt` is tri-state with a destructive `null` (reset to submission time), so `?? null` would rewrite every row's event time on every click and re-sort the public feed. Omit the key only when the row has no event time.
    - Why `IsLoggedIn` is safe on an admin page: authority lives in the route guard and the backend **service layer**, which forces a non-admin's edit back to `PENDING_APPROVAL`. Read a permission class from the mutation's `permission_classes`, never from the page that calls it.
  - `markSocialMediaLinkCompleted` (`IsAdmin`) — id-only mutation, builds no payload.
  - `deleteSocialMediaLink` (`IsAdmin`) — hard delete behind a native `confirm()`, then a local row drop and panel close.
  - `groupSocialMediaLinks`, `ungroupSocialMediaLinks`, `reorderSocialMediaLinks` (all `IsLoggedIn`; documents in `insiden/data/social-links.queries.ts`) — see the hierarchy bullets below.
- **Table:** eight columns — select-all checkbox (`data-testid="select-all"`; per-row `link-select`) · URL · Title · Submitter · Categories · Status · **Submitted** (`link-submitted`) · Actions. `min-w-[1280px]`; skeleton rows and both `colspan`s are 8.
  - Submitter carries the Official chip (`data-testid="link-official"`) and, on a hidden row, a neutral **Hidden** chip (`link-hidden`).
  - **Status vs approval:** the "Status" column and filter are about the admin's `completed` handled flag (`Completed` / warning `Pending` badge, `completed: Boolean`), **not** the link's approval `status` (`LIVE`/`PENDING_APPROVAL`/`HIDDEN`), which shows only as the action verbs and the Hidden chip. The two axes are independent, so a `LIVE` row can read "Pending" (see `MISTAKES.md`).
  - **Merged columns:** `Thread` lives inside the URL cell as its second line; `Occurred` merges into Submitted as a second line gated on `!isSameMinute(link.created, link.occurredAt)`.
  - **`isSameMinute`** (`../data/same-minute.util.ts`, pure and total; re-exposed on the class so the rule can't be re-invented in a template):
    - The gate is the **minute** because that is the rendered precision (`MMM d, y HH:mm`): an exact-instant test would print two identical-looking lines when clocks differ only below the minute.
    - **Exact-string fast path first.** The backend's `USE_TZ = False` columns send naive wall time with no offset, and `Date.parse` resolves those in the viewer's zone; byte-identical strings are the answer whatever that parse did, and equal strings are how the backend spells "no event time stated" (most rows) — so those rows never depend on the host TZ.
    - **Truncation, not rounding:** `Math.floor(ms / 60_000)`, so `09:00:59` and `09:01:00` are different minutes.
    - **Any unparseable side returns `false`** (except identical strings): a stale payload or fixture can hand the comparison two unparseable values, and `NaN !== NaN` would report different instants as the same and print `Invalid Date`. `false` can only add a redundant line, never suppress a real one.
  - The Submitted cell keeps `whitespace-nowrap` (a wrapped `Aug 1, 2026 08:30` reads as two values).
  - **Long URLs/titles wrap, never clip:** URL anchor `break-all` (a URL is one unbroken token; clipped tails can't be judged), title `break-words`. Neither cell may gain `truncate` / `whitespace-nowrap` / `overflow-hidden`.
- **Depth is drawn as rails plus a tint, not as padding:**
  - The URL cell wrapper is `data-testid="link-depth"` with `[attr.data-depth]="depthOf(link)"` (the number the rail count derives from, so specs assert hierarchy without measuring pixels). `depthRails(link)` returns one entry per ancestor level (only the length is read); `@for … track $index` draws that many `link-rail` spans (`border-border/60 shrink-0 self-stretch border-l`), width **style-bound** `[style.width.px]="depthIndentPx"`. A `w-5` class would render identically but make a second place to change the geometry that no grep for the constant finds.
  - `DEPTH_INDENT_PX = 20` is the rail/elbow width (and the elbow's `-depthIndentPx` pull-back); flat scale via `@for`, never a class ladder, so a hand-edited row deeper than any ladder still draws a rail per level.
  - The rails **replaced** `padding-left`, and the wrapper has **no `gap`** (a gap would fall between rails and break the line followed downward; every gap is an explicit `ml-1`).
  - An `aria-hidden` **elbow** (`link-elbow`: `border-border/60 h-6 shrink-0 self-start border-t`, `margin-left: -depthIndentPx`) is emitted on the **last** rail only: it is what says the row hangs off that rail; one per level would draw ticks with nothing to attach to.
  - Rails are `aria-hidden`, so the chevron's reserved width carries `data-testid="chevron-placeholder"` for specs.
  - A **child row is tinted**: `[class.bg-muted/40]="depthOf(link) > 0"` on the `<tr>`, over `hover:bg-muted` (hover still wins: stronger value of the same token, later in the class list). Rails say _which_ ancestor; the tint says "not a root".
  - `depthOf` walks the `parentId` chain **inside the loaded set**, bounded and cycle-safe. A row whose parent isn't loaded counts as depth 0 — exactly what a filter causes; rendering it flush is honest, whereas an indent the payload can't support would make a filtered queue look corrupted.
- **Row actions** (the cell is `flex-wrap`, so more verbs degrade to a taller row, never an unreachable control):
  - **Approve** (`status === "PENDING_APPROVAL"` only), **Unhide** (`HIDDEN` only — a single `LIVE` write with **no** completion), **Hide** (every row not `HIDDEN`), **Mark completed** (when not `completed`), **Ungroup** (`ungroup-link`, **sublinks only**), **Delete**, and the icon-only tree verbs **Move up** / **Move down** / **Nest under…** (`move-link-up` / `move-link-down` / `nest-under`).
  - **Precondition verbs are not drawn until it holds** (a render gate; the logic gates are unchanged because a programmatic caller reaches past the template): Move up/down inside `@if (queueIsComplete())`, Nest under… inside `@if (nestSelectionReady())`. Otherwise the default Pending queue would show a permanently greyed pair on every row, which reads as a broken table. Once drawn they are fully informative: Move up/down disabled at the two ends of the stored run with the reason on hover; Nest under… disabled on every row that can't be the target (the ticked rows themselves: nesting a selection under its own link is a cycle the server rejects as a unit).
  - **Icon-only, meaning stated twice from one source:** each button binds `[attr.aria-label]` and `[attr.title]` to the same class field (`moveUpHelp` / `moveDownHelp` / `nestHelp`, the `??` fallback of the title). Title is the blocked reason (`moveBlockedReason` / `nestBlockedReason`) when there is one, else the help copy. These return `null` when live, so the template must use **`attr.title`**: a property binding (`[title]="… ?? null"`) coerces null to the string `"null"` (see `MISTAKES.md`: "`[title]="… ?? null"` is not an absent title"). `attr.title` stays even though both branches are now non-null, so it survives whoever widens the type. Each `<svg>` is `aria-hidden`.
  - `size="icon-sm"` (`size-7` square) keeps row height identical to neighbours; glyphs are inline feather-style strokes (`viewBox="0 0 24 24"`, `stroke="currentColor"`, `size-4`) so they inherit the button colour.
  - Every action calls `$event.stopPropagation()` so it doesn't also open the detail panel. Row click / `Enter` opens the panel; the row checkbox stops propagation on `(click)`, not `(change)` (`change` fires after the click has bubbled).
- **Detail panel** (row click): URL, title, the **"When did this happen?"** control (`edit-occurred-at`; hint "Clear it to fall back to the report time. This is the column the public feed sorts on."), the bulk tag block (lines/vehicles/stations/categories), the `detail-occurred-at` line, submitter, completion metadata (`completedAt` + `completedBy`), and the same field set as "Submit a link".
  - Footer: **Approve** (`panel-approve`, only while `PENDING_APPROVAL`), **Unhide** (`panel-unhide`, only while `HIDDEN`), **Hide** (`panel-hide`, every other row) — the _same_ `approveLink` / `unhideLink` / `hideLink` the row calls, so the surfaces can't disagree.
  - Save calls `updateSocialMediaLink` with the **complete** form state (the backend replaces the M2M sets) and patches the row locally, mirroring the server's tri-state with `occurredAtInputToIso(...) ?? link.created` so a cleared box optimistically shows the fallback.
- **Conversation hierarchy = accordion over the loaded tree**, collapsed by default (matches the public feed's `app-link-thread`). Every link keeps its own row, checkbox and action cell; nothing nests inside a cell.
  - The `@for` iterates `renderedLinks()`, not `links()`. A row is drawn iff it has no loaded parent or every loaded ancestor is expanded.
  - A **parent** is a row with **loaded children** (`childCountOf`); it carries the chevron (`data-testid="thread-toggle"`, `aria-expanded`, rotating icon, `(click)` with `$event.stopPropagation()`) inside the URL cell. A childless row draws an equal-width `size-4` placeholder so open/close never shifts the URL and the columns after it.
  - Expanding reveals direct children beneath the row in the **stored** order (`position` ASC, `id` tie-break), recursively; each level expands independently at any depth. **Root order is unchanged** (`occurredAt DESC, id DESC`); only children's placement changes.
  - **The chevron gates on `childCountOf`, never `sublinkCount`:** on a filtered page `sublinkCount > 0` describes descendants not in the result (chevron would expand to nothing); `sublinkCount: 0` with a loaded child is hand-edited data and must not strand a row. `sublinkCount` still owns the **chip** (a statement about the whole conversation).
  - **A row the walk can't place is still rendered:** hand-edited cyclic data (`a → b → a`) has no root, so unplaced rows are appended at the end in arrival order. The net separates **unreachable** from **merely hidden behind a closed ancestor** by asking whether a _rendered_ ancestor is closed, so closing a conversation never feeds its children back into the net. Ancestor walk and recursion are both cycle-safe.
  - ⚠️ **Diverges from a `MISTAKES.md` rule** (2026-09-30 `collapseThreads`: client-side grouping of a flat page is unsound, so collapsing must be backend-decided). It is safe here because the console resolver has **no pagination or row cap**, so an unfiltered queue's loaded set **is** the whole table (the `queueIsComplete` precondition); every structural action is refused when completeness can't be proven; a parent missing from a filtered result makes its child a root; the accordion only chooses which rows of a complete set are drawn.
- **Select-all reads the RENDERED rows; grouping mutations scope to the LOADED ones.**
  - `renderedLinkIds` (what the accordion shows) drives `toggleSelectAll` / `allVisibleSelected` — "select all" must not tick hidden rows, or the checkbox reads fully selected while conversations sit closed and a second press clears those ticks.
  - `visibleLinkIds` (every loaded row, collapsed children included) is the scope of `scopedSelection`: collapsing is a view gesture, not an intent to forget (tick root, open, tick two children, close, Group must still move all three).
- **Selection toolbar** renders **always** (discoverability; a blocked action is a disabled button with a stated reason): `group-selected`, `selection-count`, `Clear selection` once something is ticked, and `selection-hint` while fewer than two rows are ticked.
  - The hint has **two spellings** because the verbs have different minimums: nothing ticked → "tick a link to nest it under another, or tick two or more to group…"; exactly one → points at the enabled Nest-under rows and offers a second tick. It spells "Nest under…" **out in words on purpose** — the only place naming the icon-only glyph; don't tidy it.
  - A `reorder-hint` paragraph renders whenever the queue is filtered, with the one-click `reorder-show-all` ("Show all links"). The button is **never disabled** (not even mid-load) and right-aligned (`ml-auto shrink-0` against a `flex w-full` hint whose sentence is `flex-1 min-w-0`) because it resolves the sentence beside it. A never-disabled button is only honest because `load()` queues a mid-flight arrival as `reloadQueued` and `finishLoading()` replays it, so a click during the first load really yields the unfiltered queue.
- **Chip, grouping, nesting, ungrouping:**
  - A node with descendants gets a chip (`data-testid="link-thread"`, `hlmBadge variant="special"`) whose visible text is just `threadLabel(link.sublinkCount + 1)` (e.g. `2 links`), with a `title` stating the coupling and whether the row is the root. It sits under the URL anchor; a `""` label renders **nothing** (not an em dash — most rows are lone links). The `+ 1` is load-bearing: `threadLabel` takes a **conversation size** and answers `""` for `<= 1`, so the raw count would delete the chip on a root with exactly one sublink. `confirmThreadCoupling` owes the same `+ 1`. The gate is `sublinkCount > 0`, **never** `isThreadRoot` (true of every ungrouped row).
  - **Group** sends `groupSocialMediaLinks(linkIds)` with `parentId` **omitted** (backend elects the root: earliest `(occurredAt, id)` of the selection). **Nest** is the same mutation with `parentId` = the clicked row — a **row action, not a target picker**, since the row is the target and the ticks are the payload.
  - **The two verbs have different minimums, and must not be merged:** Group needs two ticks (`canGroup`; an untargeted one-link call elects it as its own root — a no-op), Nest needs **one** (`canNest`; with a `parentId` the ticked rows become that row's children, the only way to give an existing link its first child). The backend enforces only the non-empty list (`_normalize_ids`).
  - **Ungroup** sends `ungroupSocialMediaLinks` for one row, offered on sublinks only: ungrouping a root is inert, and a promoted node **keeps its own children** (a middle node detaches a whole subtree to root level; no cascade, no re-root election — both server-side and deliberate). The copy stays about the one row.
  - The returned root `id` of group/nest is unused: it is a GraphQL **`Int`**, unlike every other id, and the list reloads wholesale (see `MISTAKES.md`).
- **The order the table shows is not the order it writes — by design.** The queue is sorted `occurredAt DESC, id DESC` (triage: "what happened most recently"); the stored sibling sequence is `position` ASC with `id` as the required tie-break, which is how a conversation reads. `reorderSocialMediaLinks` is a **permutation** of one existing sibling set, so every payload is built from the STORED run with one row moved. A successful move can leave the table looking unchanged; the toast reports the write. A conversation the backend assembled oldest-first arrives newest-first, so the move buttons answer from the stored run, not from what's on screen.

### ⚙️ Internal State & Logic

- **Signals only, no RxJS.** `selectedIds = signal<string[]>([])` is built **only** through `link-thread-selection.util.ts` (shared with the profile's "My Submitted Links", so the two can't drift on "may I group/nest this?", "is Select-all checked?", "does this row show a chip?"). The helpers are immutable by contract: results are written straight back into the signal, and an in-place mutation yields the same reference, so change detection never fires and the checkbox stops updating.
- **Selection survives a refetch** (narrowing a filter isn't an intent to forget), so every mutation scopes it through `selectedWithin(selectedIds(), visibleLinkIds())` and filters blanks: `linkIds` is `[ID!]!` and the backend rejects a repeated id outright. Without scoping, ticking three rows, narrowing and hitting Group would post ids the admin can't see, and the all-or-nothing rejection would read as a plain "grouping failed".
- **Grouping is all-or-nothing server-side** (one link outside the permission gate rejects the whole selection): nothing to roll back. Failure toasts and leaves list and selection as they were (ticks kept so the admin can retry). Success reloads and clears the selection; **Nest clears it too** (membership changed); **reorder keeps it** (no membership change).
- **`_runsByParentId` is the one map a sibling run is built from.** It groups loaded rows by `parentId ?? null` (roots are the `null` run) and sorts each group with `compareStoredSequence`. Three readers share it — the accordion's child runs, `childCountOf`, `siblingsOf` (a row's siblings _are_ its parent's children) — so the reorder payload, the move index, the "already first/last" reason and what the accordion expands cannot disagree. Groups are built fresh (the in-place `sort` can't touch the `links` signal's array) and are **memoised and shared**: a caller that reorders a run must copy first (`reorderSiblings` does). The run is **not** the order the table renders.
- **`expandedIds` is a `signal<ReadonlySet<string>>` and immutability is load-bearing** (same reference-equality reason); `toggleExpanded` copies every call. It is keyed by id and **survives a refetch** (ids are stable, so a conversation stays open through the reload a grouping/reorder triggers; a vanished id is inert).
- **`compareStoredSequence` = `position` ASC, then `id` ASC**, mirroring the backend `(position, pk)` in `batch_load_sublink_subtrees` so ties resolve the way the nested list is drawn (`"10"` must not sort before `"9"`; non-decimal ids fall back to code-unit compare — total, deterministic). `id` is a **required** second key: every structural write renumbers a run to `10, 20, 30, …` **except ungrouping**, which promotes links to roots without renumbering, so a promoted link keeps its number and can tie with a root already holding it (all roots share `parentId: null`, so the root run is where the collision shows). `position` alone leaves that to sort stability, i.e. arrival order.
- **Two gates stand in front of every reorder**, both refusals rather than fallbacks:
  - **`queueIsComplete`** — a **signal**, not a `computed` over the filter dials (a dial changes up to a debounce before the refetch, so a `computed` would re-enable the action over a still-filtered page). `fetchLinks` writes it from the same applied-filter snapshot that built the query. "Complete" is strict: no search, category, line/vehicle/station, date window **and** Status on All (the default Pending already hides completed rows). The console resolver has no pagination/row cap, so an unfiltered queue is every link.
    - The default Pending view is itself a filter, and `Reset` restores it, so a raw gate would make reordering unreachable. Hence the gate is a **render** gate (above), and `reorder-show-all` (`showAllLinks()`) cancels the debounce, clears every live control and applied field, sets Status to All and reloads — the only sequence that makes the flag true from the default view. `resetFilters()` and `showAllLinks()` share one `applyQueueFilters(completed)` snapshot writer so they can't drift.
    - **Snapshot the completeness answer BEFORE the first `await`; never read it back after.** The applied fields are mutable plain properties, and `showAllLinks` rewrites them to the unfiltered snapshot while a **filtered** request is still in flight; reading `appliedFiltersAreUnfiltered()` after it resolves would claim a whole queue over a partial page and light up sequence buttons over unloaded siblings. The captured answer is written only on success, so a failed query can't claim completeness over rows it never replaced.
    - `moveBlockedReason`'s `!queueIsComplete()` branch is **defensive only** (not rendered under a filtered queue); it stays so the function is total — a future template wanting the disabled button back gets an honest reason, not a `null` title.
    - Why it matters: `reorderSocialMediaLinks` permutes ONE sibling set and **tolerates a short list** — the server writes the ids it was sent and appends the rest — so a filtered page would silently shove a row the admin can't see to the end. Membership _is_ validated (an id not already a child of the named parent is rejected); only **absence** is tolerated, which is why a short list slips through.
  - **`runOrderIsKnown`** — false once **any** sibling arrived without `position`. A missing `position` is **not zero**: the column is gap-spaced, `0` is only the model default for a row written outside `save()`, and a `?? 0` fallback would float the row to the head and then WRITE that as the stored sequence. The comparators keep a `typeof` coercion only to stay antisymmetric (no `NaN` from a dropped key); no decision rests on it.
  - `moveBlockedReason(link, direction)` returns the reason as copy for the disabled button's title (or `null` when available), so the template binds it straight through and never restates a condition. It is **direction-agnostic** for an unreadable order ("already first" would itself claim an order the queue can't read).
- **`isLoading` drops in exactly ONE place — `finishLoading()`.** Every verb that occupies the queue hands off to it from its own `finally`: `load()` plus all six mutations (`sendGrouping`, `ungroupLink`, `reorderSiblings`, `approveLink`, `setLinkStatus`, `markCompleted`). `load()`'s re-entrancy guard parks a second arrival as `reloadQueued`; `finishLoading()` drains it with a fire-and-forget `void this.load()`, so a mutation's own success/failure return value isn't overwritten by the follow-up query's outcome.
  - The drain isn't in `load()`'s `finally` because six of the seven verbs never pass through `load()` (they set the flag and call `fetchLinks()` directly): a click parked during a mutation's post-write refetch would sit unclaimed until some later `load()` — dials reading "All" over Pending rows, the click apparently doing nothing.
  - It is a method rather than inline code so the rule holds for the _next_ verb: an eighth site clearing the flag directly would compile, pass every spec and strand the next parked reload.
  - **Not** for `isSaving` / `isDeleting` (the detail sheet's flags with their own lifecycles): routing them here would make a save replay a queued "Show all links" nobody clicked.
- **A reorder reloads and doesn't patch optimistically:** nothing on screen could confirm a new stored sequence, and the reload makes the next move a real swap against the stored order. `parentId` is **always** in the payload (`link.parentId ?? null`): an id for that parent's sublinks, `null` for the roots. The backend argument is nullable (`strawberry.Maybe`, default `UNSET`); omission is refused by the **resolver's own guard** in `reorder_social_media_links` (`incident/schema/mutations/interactions.py`), not by GraphQL validation (a nullable arg can't enforce its own presence), deliberately so that `null` can mean "reorder the roots". The `?? null` turns an accidental omission into a loud, specific error instead of a silent "reorder every root in the system" (see `MISTAKES.md`).
- **Approve is a two-write sequence, and the only verb that is** (publish, then retire): `approveLink` sends `updateSocialMediaLink(status: "LIVE")` then `markSocialMediaLinkCompleted(linkId:)` and reloads **once** at the end. Approving is the queue's "handled it" gesture; `status` (feed visibility) and `completed`/`completedAt`/`completedBy` (the global triage flag) are **orthogonal axes** the backend keeps both of. The standalone **Mark completed** action stays for an already-`LIVE` row that needs retiring on its own.
  - **Order is the contract:** the status write goes first because it can fail on its own; completing a still-`PENDING_APPROVAL` row would retire a link nobody can see.
  - **A partial failure is never silent and never rolls back.** Publish fails → error toast, **no** completion, **no** reload. Publish succeeds but completion fails → the row IS live and pending, so the error toast's _title_ says so ("Link approved, but not marked completed") and the reload **still** happens so the admin sees server truth. The return value is the **publish** outcome, which `approveFromPanel` reads to decide whether to close the sheet.
  - **Hide and Unhide deliberately do NOT complete:** `completed` is the triage flag while both are FEED decisions (auto-completing on Hide would retire a row because it left the feed; on Unhide because it went back). Unhide is a single `updateSocialMediaLink(status: "LIVE")`. Both asymmetries are spec-asserted.
  - Shape: `sendLinkStatus` / `sendMarkCompleted` are request-only helpers that **reject** on failure and never catch; `setLinkStatus` / `markCompleted` are the toast-and-reload wrappers. Approve composes the helpers directly (hence one reload); the wrappers stay the path for every single-request verb, so the replace-not-patch payload keeps exactly one builder.
- **Hide asks before hiding a node with links below it — recursively.** `confirmThreadCoupling(link)` shows a native `confirm()` naming the count, only when `threadLabel(link.sublinkCount + 1)` is non-empty (so ordinary Hide on a leaf/ungrouped row stays one click). `sublinkCount` counts descendants **at any depth** (a root whose only sublink has two more reports a conversation of four, and hiding it removes all four), and a **mid-tree** node is asked about too: hiding the middle takes the rest with it. Same `+ 1` as the chip; the two must never diverge. A static chip tooltip isn't enough (hidden until hover, absent on touch). Reuses the same native-`confirm` idiom as Delete.
- `threadLabel` is re-exposed on the class (`protected readonly threadLabel = threadLabel`), not re-implemented — a template can only read members off the component, and re-deriving it is how surfaces end up saying "1 links" and "2 link". Its callers: this table, the profile list (`profile/my-links`) and the shared `app-link-card`'s in-card indicator; re-derive that list from the code (see `insiden.md`).

### 🧩 Extension Points & Hooks

- **Filters are additive:** each control is a draft signal, one branch in `fetchLinks()` and one row in the filter card. Unset optional keys are **omitted**, never sent as `null`.
- **Grouping decisions are delegated:** anything adding a selection affordance must call `link-thread-selection.util.ts`. Link-conversation pluralisation is decided in exactly one place (`threadLabel`); this chip, the profile badge and `app-link-card`'s indicator each pass `sublinkCount + 1`. Where a surface places the chip is a layout question, and all three differ.
- **Tree-only questions are answered locally:** selection questions are shared, but **depth, the sibling run and the reorder/nest block reasons are not** — they assume a flat, filtered, un-paginated table, and the same three rules are re-derived (same wording) in the profile surface. A third surface must copy the rule explicitly: a module shared across features for a _presentation_ question would have to import a component's row type.
- **`siblingsOf` + `compareStoredSequence` are the sequence seam.** Any new ordering affordance (drag-and-drop, bulk "reverse this conversation") must derive its run from `siblingsOf` and re-check both gates (`queueIsComplete`, `runOrderIsKnown`) rather than read `this.links()` — that direct read is the exact bug the stored-order rule prevents.
- **`linkStatusInput` is the single builder for status-only verbs** (Approve, Hide, Unhide), and `sendLinkStatus` the single request they issue. A further verb (Reject, say) should reuse both: the replace-not-patch and `occurredAt` tri-state traps are both live here (see `MISTAKES.md`).
- **The edit panel is a full `SocialMediaLinkInput`:** every future editable field is one signal, one control, one payload key and one optimistic-patch key. It is driven by the console's own signals, not `LinkSheetService`, so the admin sheet is independent of the public form's open/close lifecycle.
- **Rules for anything added under the accordion:** (1) the queue shows HIDDEN rows too, so a node's `sublinkCount` counts only publicly visible descendants and the gap against the raw count is exactly the hidden ones — hence chip on `sublinkCount`, chevron on `childCountOf`. (2) The tree is arbitrarily deep, so no state may assume "a root and its members": any tree-walking affordance ("Expand all", bulk sequence, per-level action) must go through `renderedLinks` / `_runsByParentId`. An "Expand all" should write `expandedIds` for every row with loaded children in ONE `set` (a loop of `toggleExpanded` is correct but re-renders per iteration).
