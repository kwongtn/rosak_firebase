# Component: insiden

## 📌 Purpose & Scope

- **Core Responsibility:** Community incident reporting for line/vehicle/station-level service disruptions (signal failures, breakdowns, train crashes, etc.). A month calendar (severity dots per day) drives a day-scoped incident list, plus an always-visible "Ongoing & Long-Running" section regardless of the selected day. Logged-in users report and edit incidents through the full approval lifecycle (create → pending → admin approve), vote on incidents and individual chronology rows, request chronology deletions, attach photos and submit per-incident social links. Admins moderate through the console queues (see `console.md`). Direct Angular port of the legacy `src/app/insiden/` feature (ng-zorro calendar + event list), rebuilt on signals and the new design system.
- **Domain/Layer:** Angular Presentation (standalone, lazy-loaded routed feature): one routed page (`InsidenPage`), presentational children (`IncidentCalendarComponent`, `IncidentCardComponent`, `IncidentFormComponent`, `IncidentHistoryComponent`, `LinkFormComponent`, `LinksSectionComponent`, `LinkCardComponent`, `LinkThreadComponent`, `VoteButtonComponent`, `AssetMultiSelectComponent`), a `data/` layer of pure query/util modules, and two sheet services (`IncidentSheetService`, `LinkSheetService`). No state store of its own.
- **Shared link primitives:** this feature **owns** the link components other features render — `app-link-card` (every link row in the app), `app-link-thread` (collapsible thread wrapper), `app-link-list`, `app-link-sheet` — plus the pure utils the link forms and grouping UIs read (`link-occurred-at.util.ts`, `link-thread-selection.util.ts`). It hosts them but renders no thread UI itself: `/insiden` stays a flat, complete list.

## 🔌 Interface & Data Flow

- **Inputs / Props / Signals:**
  - `InsidenPage` — routes `/insiden` and `/insiden/:date` via `pathWithOptionalParamMatcher("insiden", "date")` (`app.routes.ts`). `dateParam = input<string | undefined>(undefined, { alias: "date" })`; absent on bare `/insiden`, which defaults to "today" instead of redirecting. "Today" is the Asia/Kuala_Lumpur date from `klDateKey()` (`core/time/kl-date.ts`), never the UTC date: the incident filter compares naive Kuala Lumpur wall dates, and a UTC "today" is yesterday for the first eight hours of every Malaysian day. The calendar's today ring and Today button use the same helper. The page also reads three **query params** (`?lines=3,10`, `?severity=major|minor`, `?mine=1`) through `core/url-state`; see Internal State for the filter they drive. Every day pick preserves them (`queryParamsHandling: "preserve"`).
  - `IncidentCalendarComponent` (`calendar/calendar.component.ts`) — `incidents = input.required<CalendarIncident[]>()`, `selectedDate = input.required<string>()` (`YYYY-MM-DD` key), `exportCount = input(0)` (how many incidents "Export month" would write: approved ones only; `0` disables both buttons; an `InfoPopover` beside the count states the rule from the `incidents.month-export` metric). The page binds the already-filtered list, so the dots follow the filter.
  - `IncidentHistoryComponent` (`incident-history/incident-history.component.ts`, `app-incident-history`) — `endMonth = input.required<string>()` (`YYYY-MM`, the page's `selectedMonth`). Self-contained: owns its collapsed/expanded toggle, its read and its chart (see Internal State).
  - `IncidentCardComponent` — `incident = input.required<CalendarIncident>()`, `editActionEnabled = input(true)` (the console's pending queue sets `false`: it has its own panel editing, so the edit / request-deletion / add-link affordances are hidden there).
  - `IncidentFormComponent` — hydrates from `IncidentSheetService.editTarget` (`signal<CalendarIncident | null>`); no-arg `open()` is create-only.
  - `LinkFormComponent` — reads `LinkSheetService.context` (`{ incidentId, incidentTitle? }`) to target a submission at an incident; no-arg open is the just-dumping flow. Edit target is the structural `LinkEditTarget` (vehicles/stations optional), so the home feed's node — which selects neither — hydrates as an empty selection. A create-mode open applies the sheet's one-shot URL prefill (home's "Advanced Input") once; edit mode never does.
  - `LinkCardComponent` (`app-link-card`) — `link = input.required<LinkCardItem>()` (the structural contract both `PublicSocialMediaLink` and the home feed's `FeedLink` satisfy with no host mapping), `userVote = input(0)` (host overlay), `editable = input(false)` (host-gated with `canEditLink`: author or admin), and the **conversation** inputs `sublinkCount = input(0)`, `sublinksExpanded = input(false)` with `sublinkToggle = output<void>()` (see Internal State for why the count is an INPUT, not read off `link`).
  - `LinkThreadComponent` (`app-link-thread`, the **recursive** conversation wrapper):

    | member        | kind             | meaning                                                                                                                                                                                                         |
    | ------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | `link`        | `input.required` | the node THIS instance renders — a host's conversation root, or a direct child reached through the recursion. `LinkCardItem`, so every host node binds straight in.                                             |
    | `userVote`    | `input`, `null`  | scalar optimistic-overlay vote, for a **host-rendered** root only. `null` (default) = "not supplied", so a `0` cannot masquerade as "the host removed my vote". **Not forwarded to nested levels** (see below). |
    | `voteValues`  | `input`, `{}`    | the host's per-link vote overlay keyed by id. Forwarded to **every** card at **every** depth — a sublink is votable too.                                                                                        |
    | `editable`    | `input`, `false` | show the edit pencil — forwarded down the recursion, so a sublink gets one too.                                                                                                                                 |
    | `voteChanged` | `output`         | `{ id, value }` — the **voted** node's own id, at any depth.                                                                                                                                                    |
    | `edit`        | `output`         | the clicked **descendant's** own `LinkCardItem`, never the root's.                                                                                                                                              |

    **Recursion, not a branch component:** the component lists **itself** in `imports` (`[LinkCardComponent, LinkThreadComponent]`), which Angular supports for standalone components (class binding exists when the decorator runs; AOT resolves the self-reference statically; verified under the vitest builder and `npm run build`). An extracted sibling `app-link-branch` would leave two definitions of "a node plus its children" free to drift. **No depth parameter exists:** the write side caps at `MAX_THREAD_DEPTH = 3` (backend `incident/services/social_link_threads.py`) and the read side is bounded by what the query fetched, so a leaf is simply a node with no `sublinks`.

  - `VoteButtonComponent` — `targetType = input<"incident" | "chronology" | "link">("incident")`; one button drives incident, chronology and link votes.
    - **Displayed state is three layers, not a `linkedSignal`:** `optimistic` (in-flight projection from `nextVoteState`) → `confirmed` (snapshot the mutation acknowledged with) → `hostState` (the inputs). A `linkedSignal` re-seeds from inputs on ANY change, and the host writes the acknowledged `userVote` straight back down as its overlay — so the control reset to the PRE-CLICK `netScore` and the arrow stayed lit (see `MISTAKES.md`: "a `linkedSignal` display re-seeds from EVERY input").
    - `confirmed` is honoured only while `voteStatsKey(hostState())` still matches the triple it was computed against; the key deliberately **excludes `userVote`** (the host echoing our own value is not new data), while a real refetch (the home feed polls) moves the counters and correctly supersedes the snapshot.
    - All six vote mutations acknowledge with the same `VoteMutationPayload` (`userVote`/`voteScore`/`upvotes`/`downvotes`; `ok` is sent but never read — a rejected request is the failure signal). `voteStateFromAcknowledgement` degrades any non-finite field to the fallback, so a partial payload keeps the projection rather than painting `undefined`.
- **Outputs / Events / API Responses:**
  - `IncidentCalendarComponent.daySelected = output<string>()` — emits a `dateKey` on day click, "Today", month/year jump commit or prev/next navigation. `InsidenPage` calls `router.navigate(["/insiden", dateKey], { queryParamsHandling: "preserve" })`, so the viewed day is a real, shareable URL that keeps the filters.
  - `IncidentCalendarComponent.exportMonth = output<"csv" | "ics">()` — the reader picked a format on the header's "Export month (N)" control. The calendar only reports it: the page builds the file from the filtered, approved incidents and downloads it.
  - `LinkCardComponent`: `voteChanged = output<{ value: number }>()` after a successful vote; `edit = output<LinkCardItem>()` (the pencil); `sublinkToggle = output<void>()` (the card only reports the click — it has no idea what will be revealed). `LinkListComponent.voteChanged` re-emits with the id as `{ id: string; value: number }`.
  - `LinkThreadComponent`: `voteChanged = output<{ id; value }>()` (one thread renders N votable cards) and `edit = output<LinkCardItem>()` re-emitted with the clicked **descendant's own** `LinkCardItem` at any depth — that object is what the host's edit sheet hydrates from, and a wrong one would open the wrong link.
  - **`INSIDEN_INCIDENTS_QUERY`** (`data/insiden.queries.ts`) takes optional filters. `/insiden` fetches incidents overlapping the selected month ±14 days (`calendarMonthRange()` in `calendar-date.util.ts`) **OR** unresolved ones (`OR: { ongoing: true }`, for the pinned section). Changing months reloads the window; another day in the same month reuses it. The situasi consumer keeps its unfiltered query. The page filters the loaded window **client-side** (line, severity) and the read itself is unchanged. Sub-selects carry the full lifecycle surface: `status`, `version`, `user { shortId }`, `categories`, chronology `status` + vote fields, per-incident `links(first: 10)` (first page of the connection) and `medias` with `id` + `uploader { nickname }` (`uploader` is null for a photo on an anonymous spotting unless the viewer is the uploader or an admin; the viewer then shows the photo with no name).
  - **`INSIDEN_MONTHLY_HISTORY_QUERY`** (`data/insiden-history.queries.ts`) is the "Last 12 months" read: `calendarIncidentsBySeverityCount(startDate: $startDate, endDate: $endDate, groupBy: MONTH)`, selecting `severity date count`. The server does the counting: one row per (calendar month, severity) holding the number of **`LIVE`** incidents whose start falls in that month, each incident once, in its start month, however long it lasted (drafts, pending and rejected reports never count; `rosak_backend` `incident/schema/resolvers.py`, its `docs/components/incident.md` -> Aggregation). `date` is the first of the month (`YYYY-MM-01`), `severity` is a plain `String` (`MAJOR`/`MINOR`/`OTHERS`) and `isLongTerm` is always null in this mode, so it is not selected. A month with no `LIVE` incident has **no row**, so the client zero-fills its axis. `$startDate`/`$endDate` are declared `Date!`: the schema types them as nullable `Date`, but the resolver raises "start_date and end_date required" without both. `groupBy` must be sent, because it defaults to `DAY`, which builds one SQL aggregate per day and fails for a window of 278 days or more. `data/insiden-history.queries.spec.ts` pins all of this, since a GraphQL document is a string that nothing checks against `SeverityCountRow`.
    - **The window, and the deploy order.** The bounds are 1 January of the first month's year and 31 December of the last month's year (`historyDateBounds`): the calendar years of the window's first and last month, read whole. Both sit on month edges, which matters because the resolver counts only the incidents inside the exact bounds: a bound inside a month would give that month a partial count. **The read needs `rosak_backend` `9832a3d` deployed first.** Before it the MONTH grouping compared the month **number** across years (`start year <= Y AND start month <= M`) and counted every status, so its rows were a running total that reset each January: against the local data, window 2024-01..2024-12 returned MAJOR 1, 8, 12, 18, 26, 30 for months whose true counts are 1, 7, 4, 6, 8, 4. An older API would draw those figures as bars, and nothing client-side can tell. The payload is at most three rows a month (up to 72 for the two years) whatever the number of incidents; the two aliased `calendarIncidents` year reads it replaced grew with every incident, ongoing ones included.
  - **`CalendarIncident`:** id, start/end datetime, `severity` (`MAJOR`/`MINOR`/`OTHERS`), `status` (`DRAFT`/`PENDING_APPROVAL`/`LIVE`/`REJECTED`), title, brief, details, `hasDetails`, `impactFactor`, `version`, `longTerm`, `inaccurate`, `lastUpdated`, author `user`, `lines`/`vehicles`/`stations`, `categories`, `chronologies[]` (ordered timeline entries with `status`, `voteScore`, `voteBreakdown`, `userVote`), `links` (connection), `medias[]`, and the incident's own `voteScore`/`voteBreakdown`/`userVote`.
  - **Mutations** (`data/insiden.queries.ts`): `CREATE_CALENDAR_INCIDENT_MUTATION`; `UPDATE_CALENDAR_INCIDENT_MUTATION` (sends `version` for OCC; returns the revision `id` when a non-admin LIVE edit created a draft, which the form chains into `SUBMIT_CALENDAR_INCIDENT_MUTATION`); `UPVOTE`/`DOWNVOTE`/`REMOVE_VOTE` (incident + chronology variants); `REQUEST_CHRONOLOGY_DELETION_MUTATION`; `SUBMIT_SOCIAL_MEDIA_LINK_MUTATION` (carries `incidentId` when targeted).
  - **A social-media link has TWO time axes; never conflate them.** `created` is "when someone _reported_ it" (moderation provenance). `occurredAt` is "when it _happened_": NOT NULL on the backend, indexed, backfilled from `COALESCE(posted_at, created)`, and the leading key of **every** ordering, window and keyset cursor (`-occurredAt, -id`; the feed's `currentServiceDayOnly` / `lastWeekOnly` / `alignPageToDay` windows; the console queue; the per-incident `links` connection). Both are **naive local wall time with no offset** (backend `USE_TZ = False`, `TIME_ZONE = Asia/Kuala_Lumpur`, often with microseconds) — never re-format through UTC (see `MISTAKES.md`: naive wall-time datetime vs `toISOString()`).
    - Types: `LinkCardItem.occurredAt` and `PublicSocialMediaLink.occurredAt` are **optional** (selected per document); `created` stays **required** — it is the display fallback `occurredAt ?? created` and the tooltip's absolute stamp, so a document that selects `occurredAt` but drops `created` renders a blank time.
  - **`occurredAt` on inputs is TRI-STATE, and one state is destructive** (backend `SocialMediaLinkInput.occurred_at: Maybe[datetime | None] = UNSET`):

    | sent                | `updateSocialMediaLink` does                                              |
    | ------------------- | ------------------------------------------------------------------------- |
    | key **omitted**     | leave the event time untouched                                            |
    | a datetime string   | set it                                                                    |
    | explicit **`null`** | **RESET** the row to its `created` ("this happened when it was reported") |

    An editor that **hydrates a visible control** must send the key **always** — never `?? undefined` (makes "cleared" unreachable) and never `row.occurredAt ?? null` (resets the timestamp on every save). The **console's** status-only verbs own no control, so they re-send the row's value **verbatim** (`linkStatusInput`) and omit the key only when the row has no event time. On the **create** path omitted and `null` are identical server-side (both stamp the submission instant), so the submit path omits the key — which is why `LinkFormComponent.submit` and the console's `saveLinkEdit` branch differently.

  - **The conversation TREE on `LinkCardItem`** (backend `SocialMediaLinkScalar`; a link is a root or a sublink of another link, to any depth). No server-side alias exists for the old names, so a stale spelling is a hard "Unknown field" on the whole query:

    | `LinkCardItem` field        | replaced         | meaning                                                                                                                                                                                                         |
    | --------------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | `parentId?: string \| null` | `threadId`       | the link this one hangs under; `null` **exactly** when it IS a root                                                                                                                                             |
    | `isThreadRoot?: boolean`    | (unchanged name) | a **ROOT MARKER**, true of every ordinary ungrouped link too — never an affordance gate                                                                                                                         |
    | `sublinkCount?: number`     | `threadSize`     | this node's OWN publicly-visible descendants **at any depth**; `0` for a leaf. **NOT** the conversation size                                                                                                    |
    | `sublinks?: LinkCardItem[]` | `threadLinks`    | this node's **direct** children, in stored sibling `position` order. **Recursive**: the element type is the interface itself                                                                                    |
    | (row types only)            | —                | `position?: number` on `PublicSocialMediaLink` / `SocialMediaLinkRow`: the gap-spaced `10, 20, 30, …` sibling rank, selected by both flat documents so a reorder permutation can be built from the STORED order |

    Four properties a caller gets wrong at least once:
    - **Optional by design:** all four are optional on `LinkCardItem` because flat surfaces don't select them and a narrower host selection must still satisfy the contract. `created` stays **required** alongside them: a nested child is itself a `LinkCardItem`, so a document that forgets `created` at depth 2 fails the same contract the root does (the point of the recursive type). The console's `SocialMediaLinkRow` selects all four, so there they are **required**.
    - **`sublinkCount` is not a conversation size.** Read the ROOT's count to size a conversation; never sum the column level by level — every node answers for itself, so a sum double-counts by exactly the depth (root 2, child 1, leaf 0 → 3 for a 3-link tree).
    - **`sublinks` order ≠ every other link list's order:** it is `position` ASC (author-chosen, not a timeline); every other list is `occurredAt DESC, id DESC`. Group members need not be contiguous in time.
    - **A conversation is public iff its ROOT is**, with time windows resolved across the whole subtree — so `sublinkCount`/`sublinks` count and list only **publicly-visible** descendants, and a hidden sublink isn't listed even on your OWN `mine` page. Moderation is root-only: hiding a middle node leaves it attached but takes it (and its descendants) out of both count and list.

  - **Photo upload is fire-and-forget:** `IncidentCardComponent.uploadPhotos()` pushes each pending file to `ImageUploadService.addToQueue(incidentId, file, "INCIDENT_CALENDAR_INCIDENT")`; the component awaits nothing (the service owns its queue/retries). Thumbnails open an in-page `MediaViewerComponent` overlay (same mechanism as `/gallery`), not a new tab.

## ⚙️ Internal State & Logic

No RxJS subjects, no store — Angular signals, computed at several levels.

- **`InsidenPage`:**
  - `selectedDate`/`selectedDateObj` computed from the route param (or today). `incidentsResource` is the single source of truth: `loadedIncidents` is what it returned, `allIncidents` is that list **narrowed by the filter** (the very same array when no filter is active), and `_sorted` (newest-first by `startDatetime`), `dayIncidents` (incidents covering the selected day, multi-day ones on every day they span) and `pinned` are `computed()`s over `allIncidents`, so a filter applies uniformly to the calendar dots, the day list and the pinned section.
  - **Filters (`data/incident-filter.util.ts`, pure).** The URL is the ONLY state: `queryParamMap` is a `toSignal` of `route.queryParamMap` **seeded from the snapshot** (so a deep link renders filtered on the first paint), `filterUrlState` parses it, and `filterCriteria` (`{ lineIds, severity }`) resolves it against `PreferencesService.pinnedLineIds()`. Every control (`toggleMine`, `toggleLine`, `setSeverity`, `clearFilters`) computes the next URL state with a pure transition (`withMineToggled`, `withLineToggled`, ...) and writes it through browser-gated `writeQueryParams` (merge + replace; a default is `null`, which removes the key). There is no second writable copy to drift.
    - **Keys:** `?lines=3,10` (explicit, shareable selection), `?severity=major|minor`, `?mine=1`. An explicit `lines` wins over `mine`; `mine` resolves against the reader's own pins, live, so the same link means "my lines" to each reader. `mine` with nothing pinned is **no line filter** (an empty page would claim "no incidents on your lines"), and the bar says so. Pressing a chip while `mine` is on edits a copy of the pins and turns `mine` off. `PreferencesService` hydrates from localStorage after first render, so a `?mine=1` deep link is unfiltered on the server and in the first client render and narrows once the pins load (no hydration mismatch).
    - **Scope is the loaded window, and the bar says so:** the shown month, `CALENDAR_WINDOW_PAD_DAYS` (14, exported by `calendar-date.util.ts` and interpolated into the copy, so the words cannot drift from the read) days either side and ongoing incidents, not all history. "Showing N of M" counts against `loadedIncidents`, in an `aria-live="polite"` span that is **always in the DOM** (a live region created together with its text is not announced) and filled only once `hasLoaded()` (`data()` is dropped the moment the month changes, so "Showing 0 of 0" and "no incident in this window" would otherwise be announced for the length of the request).
    - **The bar sits outside the loading/error branch** (a `@if (activeTab() === "incidents")` sibling of the skeleton/banner/calendar), so it never unmounts. `lineOptions` is a `linkedSignal` that **holds the previous chips while `incidentsResource.isFetching()`**: without it the strip emptied and every chip remounted on each month change. "Clear filters" removes itself when the URL empties, so its handler moves focus to the "My lines" chip (`#mineChip`) first. The "You have not pinned any lines yet" hint waits for `PreferencesService.hydrated()` (false on the server and the first client render, so no mismatch), or a rider WITH pins would see it flash on a `?mine=1` link.
    - **Chips** (`incidentLineOptions`) are the lines the loaded incidents reference, pinned first then by code (numeric-aware), taken from `loadedIncidents` so narrowing never removes another line's chip. A pinned line no loaded incident references has **no chip** (its label would need a lines lookup this page does not make); it stays part of the "My lines" selection, and selected lines without a chip are counted in the bar (`unlistedLineIds`) so an active filter is never invisible.
    - `OTHERS` is not offered as a severity filter; an incident with no lines never matches a line filter.
    - **Severity is three pressed-state chips (All / Major / Minor), not a native `<select>`:** the incident e2e flow picks the report form's severity with `page.locator("select").first()`, so a page-level `<select>` would become the first one in the DOM. Both chip rows sit in labelled `role="group"`s ("Lines", "Severity").
  - **Export (`data/incident-export.util.ts`, pure).** `exportIncidents` = `incidentsForMonthExport(allIncidents, month)`: the filtered, **approved (`LIVE`) incidents that started** in the shown month, oldest first; `onExportMonth("csv" | "ics")` builds the file and downloads it (a no-op on the server or when empty).
    - **Approved only, on purpose.** `calendarIncidents` returns every status unless the caller sends the opt-in `status` filter (backend `07c8289`), and the calendar needs the unapproved ones, so drafts, pending and rejected reports reach every reader of the page; the page tucks them behind "Pending Approval", but a file leaves that framing behind and would pass community text nobody vetted on as the record. So the count on the button, the rows in the file and the "Last 12 months" bar for the month (no filter on) are the same number. If researchers ever need unapproved rows, that is an explicit option, not the default. (The single-incident "Add to calendar" on a card is the reader's own pick of a card they can see, so it keeps `TENTATIVE`/`CANCELLED` for a pending/rejected one.) The rule is the `incidents.month-export` metric, surfaced by an `InfoPopover` beside "Export month (N)".
    - **Start-based** so every row's `date` falls inside the month and an incident is exported once across months.
    - **Filename names the filter** (`exportFilterTokens` + `monthExportFilename`): `insiden-2026-10.csv` unfiltered, `insiden-2026-10-kjl-major.csv` for KJL's Major incidents (each selected line's code, `line<id>` when no chip names it, then the severity; lower-cased letters and digits only). A CSV has nowhere to say which filter produced it, and a filtered file named like the whole month reads as the whole month once it has left the page.
    - **CSV columns:** `date` (start date), `title`, `severity`, `lines` (codes, `; `-joined), `stations` (names, `; `-joined), `status` (the API's approval state, upper-cased; always `LIVE` for a month export, kept so the schema survives an "include unapproved" option) and `url`. No end time or duration column. User-written cells go through `neutralizeSpreadsheetFormula` (leading `=`/`+`/`-`/`@`/tab/CR gets an apostrophe), **exported from `core/export/csv.util.ts`** for any future export of user text: `toCsv` serialises, it does not know which cells are user text, and applying it to every cell would also prefix a negative number. (The home Pro widget writes admin-managed line names and numbers, so it does not need it.)
    - **iCalendar:** one `VEVENT` per incident: UID `incident-<id>@community.mlptf.org.my` (stable, so re-importing updates), `DTSTAMP`, `DTSTART;TZID=Asia/Kuala_Lumpur` from the offset-free API value, **no `DTEND` while ongoing** (and none if the end is not after the start), `SUMMARY` (title), `DESCRIPTION` (brief), `URL` (`https://community.mlptf.org.my/insiden/<start date>`, production on purpose) and `STATUS` (`LIVE` → `CONFIRMED`, `DRAFT`/`PENDING_APPROVAL` → `TENTATIVE`, `REJECTED` → `CANCELLED`, so a calendar never presents an unvetted report as a fact).
  - `pinned` gates on `endDatetime === null` **alone** and excludes incidents already in `dayIncidents`. `longTerm` is an independent admin classification (its own badge), not a synonym for "unresolved": a long-term incident given an end date is resolved and must drop out.
  - Both lists split approved-first, with pending ones behind a collapsed-by-default "Pending Approval (N)" toggle (one signal per list; "approved" = not pending, status may be `LIVE` or missing).

Mirrors the incident form's `isoToDateTimeLocal` but lives in its own module so no link surface reaches into the incident form to format a timestamp.
  - **`link-thread-selection.util.ts`** (`toggleSelection`, `areAllSelected`, `canGroup`, `canNest`, `selectedWithin`, `threadLabel`) — selection mechanics of the two grouping surfaces (the console triage table and the profile's "My Submitted Links"). Every function is total and immutable (no Angular/`signal`/RxJS) and returns a NEW array, because results are fed straight back into a signal: in-place mutation yields the same reference, change detection never fires and the checkbox silently stops updating. The two minimums are separate on purpose: `canGroup` needs two (an untargeted one-link call elects that link as its own root), `canNest` needs one (with a target it becomes a real child).
    - **`threadLabel` is the single place pluralisation is decided for a link conversation anywhere in the app.** Consumers: (1) the console triage chip (`/console/links`; inside the URL cell, renders nothing on `""`) plus `confirmThreadCoupling`; (2) the "My Submitted Links" badge on the profile page; (3) `app-link-card`'s indicator (`conversationLabel = threadLabel(sublinkCount() + 1)`). `app-link-thread` is **not** a consumer (the card owns the chip; the wrapper just renders cards). The helper's docstring says to **re-derive the list from the code**, not from memory.
    - No consumer may grow its own `` `${n} link${n === 1 ? "" : "s"}` `` — that is how one surface says "1 links" and another "2 link", which no type or test catches. A new conversation count joins the helper; what legitimately differs between sites is the **gate** deciding whether a count shows, not the string.
    - **Its parameter is a CONVERSATION SIZE (`sublinkCount + 1`), not a descendant count.** It answers `""` for `<= 1`, so a raw `sublinkCount` **silently deletes the chip on a root with exactly ONE sublink** (`1` → `""`) while leaves stay correctly chip-less (`0` → `""`) — which is why the bug hides. Don't "tighten" the `""` branch either (`1` → `"1 link"`): a chip would sprout on every ordinary row in the app (see `MISTAKES.md`: "two counts, one question").

## 🧩 Extension Points & Hooks

- **`RetryableResource`** (`ui/retry-banner/retry-banner.component.ts`) is a structural interface: any resource-like object (another fetch wrapper, a test mock) can drive `RetryBannerComponent` without coupling to `graphqlResource()`.
- **Lookup tables:** `SEVERITY_DOT` (private `Record` in `calendar/calendar.component.ts`) and `SEVERITY_VARIANT` / `SEVERITY_LABEL` / `CHRONOLOGY_DOT` (private `Record`s in `incident-card/incident-card.component.ts`) — a new severity or indicator value is a one-line addition per table, not a scattered conditional.
- **Filters, exports and history are pure seams, not page logic.** A new filter axis (a station, a vehicle) is one field on `IncidentFilterCriteria` + `IncidentFilterUrlState`, one branch in `filterIncidents`, one key in `incidentFilterQueryPatch`/`readIncidentFilterUrlState`, one control in the bar. A new export column is one entry in `INCIDENT_CSV_COLUMNS` + `incidentToCsvRow`. A new calendar property is one field on `IcsEvent` + `eventLines` in `core/export/ics.util.ts`, whose escaping and 75-octet folding are applied for you. The history read is one document (`insiden-history.queries.ts`) feeding one function (`bucketSeverityCountsByMonth`).
- **`defaultChronology()`** (`data/incident-chronology.util.ts`) is the seam for adjusting the no-chronology fallback timeline without touching rendering.
- **`INSIDEN_INCIDENTS_QUERY` is a single flat string constant:** extending the fetched fields is a local, additive edit to `insiden.queries.ts` plus a `CalendarIncident` interface change. New fields follow the optional-field + DEPLOY-ORDER comment pattern.
- **Pure utils are the gate/label/format seams** (`canEditIncident()`, `canEditLink()`, `chronologyStatusLabel()`, `incidentLinkLine()`, `incidentToForm()`, `groupLinksByDay()`, `incidentMediaToViewerNode()`): tested, isolated, reusable without touching markup.
- **`app-link-thread` is the named extension point for any grouped link row, and it is recursive.** It takes the same structural `LinkCardItem` the card takes, so a new host binds a `FeedLink`, a `PublicSocialMediaLink` or a fixture straight in at any depth; its internals (per-level `expanded`, the `sublinkCount > 0` gate, the `sublinks` recursion) mean a host can't re-decide them.
  - **Keep the self-reference** (see Interface; don't extract an `app-link-branch`).
  - **The card owns the chip, the wrapper owns the state:** the wrapper passes the count through and never reads `isThreadRoot` or pluralises. A host must not bind `[sublinkCount]` on `app-link-list` unless it has a nesting to reveal — that is what keeps `/insiden`, the situasi tab and the incident cards flat.
  - **`editable` is forwarded to every level on purpose;** the cosmetic over-permission and the per-link-predicate trade-off are described under Internal State.
  - **Don't "improve" the root's presentation** (byte-identical DOM to a plain row apart from the rail chip).
  - **`MAX_THREAD_DEPTH` (server write-side cap) is not mirrored here:** the read side is bounded by what the query fetched, so a host asking for deeper nesting just gets `[]`; a client that mirrors the cap silently loses a level the day the cap moves. A host wanting conversations open by default (or one specific one open) adds an input rather than re-deriving the toggle.
- **Single seams for the link feature** (contracts described under Pure helper modules above): `link-occurred-at.util.ts` for datetime-local ↔ API (offset-free, never `toISOString()` on naive wall time, shape-mismatch passed through **unchanged** because `null` on update is a destructive reset); `linkDisplayInstant(link)` for which instant a link displays (a new surface that groups, sorts or labels links must key on it, not `created`, or a back-dated report scatters one day under two headers and orders differently from the feed above it; the home feed's `groupFeedLinksByDay` applies the same fallback inline, the situasi section sorts on it); `link-thread-selection.util.ts` for any future grouping surface (so admin and submitter experiences can't drift).
- **Details/photos use an in-place expand/collapse idiom** (matching `vehicle-list.component.ts`) rather than a modal/drawer; build new expandable sections the same way.
- **The photo-attach path is additive:** `PhotoPickerComponent`, `ImageUploadService` and `MediaViewerComponent` are shared, feature-agnostic primitives (already reused by `features/spotting` and `features/gallery`), so any "attach evidence" flow can plug into the same picker/queue/viewer.
- **`InfiniteScrollDirective`** is a reusable sentinel (IntersectionObserver + coalescing) for any cursor-paginated list.

## 💡 Potential Feature Opportunities

- **Extend thread UI to the flat surfaces — still open.** `app-link-thread` ships on the **home feed** (today + Last Week); the two management surfaces roll their own (the console triage table is an accordion over the ordered tree with rails + child tint; My Submitted Links shows hierarchy as an indent). `/insiden`'s Submitted Links tab, the situasi tab and the per-incident cards stay flat and complete: a reader browsing "everything submitted" would lose rows, and a per-line filter wants a complete list of reports about that line. The component is host-agnostic and recursive, but adopting it is **not** a one-line swap; the remaining work is **selections**:
  1. `PUBLIC_SOCIAL_MEDIA_LINKS_QUERY` (Submitted Links, situasi, My Links, incident-card continuations) selects `parentId` / `isThreadRoot` / `sublinkCount` / `position` but **deliberately not `sublinks`**, which the wrapper expands from.
  2. The per-incident `links(first: 10)` sub-select selects **no** tree field (only `id url title occurredAt created status completed`), and the incident card builds ONE list from that sub-select **plus** continuation pages from the document above — page 1 would arrive with no tree fields while the rest had them (the same two-document hazard as `occurredAt`/`created`; pinned by `incident-card.component.spec.ts` on both documents).

  Real work: add nested `sublinks` to both documents (to the depth shown), keep the two selection sets in agreement, set `collapseThreads: true` on the first page **and every continuation**, and decide deliberately about `mine`, which the backend never collapses (a submitter must never lose their own sublinks behind a root). Each flat host's spec currently **fails** if the tree leaks in, so closing this is a deliberate, spec-visible product change, not a refactor.

- **Vehicle and station filters:** the bar filters by line and severity (client-side, loaded window only; see Internal State). Vehicles and stations are already on every `CalendarIncident`, so a further axis is the small additive change described under Extension Points. Stations carry their `displayName`, so labels are not the problem lines have, but a month can reference many distinct stations, so a combobox would suit better than chips.
- **Subscribable calendar feed:** "Add to calendar" and "Export month" are one-off downloads of what the page has loaded. A feed a calendar app can subscribe to and refresh needs a backend `/incidents.ics` endpoint (the data and `buildIcs`'s rules are the template); it is not a frontend-only change.
- **Incident alerts beyond the first slice:** line alerts exist (audit F294). A rider turns them on with the bell of a pinned line on the front page and manages them on the own profile (`core/push/`, see `docs/COMPONENTS.md`). The backend pushes a newly approved MAJOR incident to the subscribers of its lines, at most once per line in 30 minutes, and the notification opens `/insiden/<start date>`: this page, on the day the incident starts. Still open here: the link names the day, not the incident, so a rider lands on the calendar and has to find it. An incident id in the link (a backend change) and a handler here that scrolls to and expands its card would land them on it; `pinned` and `IncidentCardComponent.isOngoing()` already isolate active incidents. A "follow these lines" control on an incident card could call `PushService.subscribe()` with the bell's pre-prompt. Backend work, not built: quiet hours, a push for an incident an admin creates directly or raises to MAJOR, a push when an incident ends, and official-post triggers.
- **Shareable/deep-linkable incident state:** partially ready — day selection and the line/severity/"My lines" filters already round-trip through the URL (`?lines=`, `?severity=`, `?mine=`), but per-incident UI state (`detailsExpanded`, `photosExpanded`) is local signals. Syncing an incident-id fragment/query param to them is a moderate change confined to `InsidenPage`/`IncidentCardComponent`; `core/url-state/query-param.util.ts` provides the read/write helpers.

## 💡 Potential AI Feature Opportunities

- **Automated incident summarization/triage:** `brief`, `details` and ordered `chronologies[]` are structured, timestamped text — a fit for an LLM plain-language "what happened and current status" summary, or auto-classifying `severity`/`impactFactor` at creation. The form already ships Gemini extract/summarize flows (`IncidentAiService` → Firebase function endpoints), so the plumbing exists.
- **Anomaly/pattern detection over incidents:** lines, vehicles, stations, severity and duration of the loaded window are resident client-side — a substrate for recurring-disruption or "this line has had N incidents this month" insights beside the calendar. The "Last 12 months" section now gives severity counts per month, but the aggregate it reads carries no lines or stations and takes no argument to narrow by them, so a per-line or per-station recurrence view would need a backend argument on `calendarIncidentsBySeverityCount`, or a `calendarIncidents` read that selects those fields (the page itself still loads only the selected month ±14 days plus ongoing).
- **Smart photo/evidence assistance:** the photo pipeline (`PhotoPickerComponent` → `ImageUploadService` → `MediaViewerComponent`) is a ready hook for AI captioning, duplicate/blur detection or auto-tagging before upload, reusing the queue/compression flow.
