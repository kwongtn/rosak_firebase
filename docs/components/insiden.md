# Component: insiden

## 📌 Purpose & Scope

- **Core Responsibility:** Community incident reporting for line/vehicle/station-level service disruptions (signal failures, breakdowns, train crashes, etc.). A month calendar (severity dots per day) drives a day-scoped incident list, plus an always-visible "Ongoing & Long-Running" section regardless of the selected day. Logged-in users report and edit incidents through the full approval lifecycle (create → pending → admin approve), vote on incidents and individual chronology rows, request chronology deletions, attach photos and submit per-incident social links. Admins moderate through the console queues (see `console.md`). Direct Angular port of the legacy `src/app/insiden/` feature (ng-zorro calendar + event list), rebuilt on signals and the new design system.
- **Domain/Layer:** Angular Presentation (standalone, lazy-loaded routed feature): one routed page (`InsidenPage`), presentational children (`IncidentCalendarComponent`, `IncidentCardComponent`, `IncidentFormComponent`, `LinkFormComponent`, `LinksSectionComponent`, `LinkCardComponent`, `LinkThreadComponent`, `VoteButtonComponent`, `AssetMultiSelectComponent`), a `data/` layer of pure query/util modules, and two sheet services (`IncidentSheetService`, `LinkSheetService`). No state store of its own.
- **Shared link primitives:** this feature **owns** the link components other features render — `app-link-card` (every link row in the app), `app-link-thread` (collapsible thread wrapper), `app-link-list`, `app-link-sheet` — plus the pure utils the link forms and grouping UIs read (`link-occurred-at.util.ts`, `link-thread-selection.util.ts`). It hosts them but renders no thread UI itself: `/insiden` stays a flat, complete list.

## 🔌 Interface & Data Flow

- **Inputs / Props / Signals:**
  - `InsidenPage` — routes `/insiden` and `/insiden/:date` via `pathWithOptionalParamMatcher("insiden", "date")` (`app.routes.ts`). `dateParam = input<string | undefined>(undefined, { alias: "date" })`; absent on bare `/insiden`, which defaults to "today" instead of redirecting.
  - `IncidentCalendarComponent` (`calendar/calendar.component.ts`) — `incidents = input.required<CalendarIncident[]>()`, `selectedDate = input.required<string>()` (`YYYY-MM-DD` key).
  - `IncidentCardComponent` — `incident = input.required<CalendarIncident>()`, `editActionEnabled = input(true)` (the console's pending queue sets `false`: it has its own panel editing, so the edit / request-deletion / add-link affordances are hidden there).
  - `IncidentFormComponent` — hydrates from `IncidentSheetService.editTarget` (`signal<CalendarIncident | null>`); no-arg `open()` is create-only.
  - `LinkFormComponent` — reads `LinkSheetService.context` (`{ incidentId, incidentTitle? }`) to target a submission at an incident; no-arg open is the just-dumping flow. Edit target is the structural `LinkEditTarget` (vehicles/stations optional), so the home feed's node — which selects neither — hydrates as an empty selection. A create-mode open applies the sheet's one-shot URL prefill (home's "Advanced Input") once; edit mode never does.
  - `LinkCardComponent` (`app-link-card`) — `link = input.required<LinkCardItem>()` (the structural contract both `PublicSocialMediaLink` and the home feed's `FeedLink` satisfy with no host mapping), `userVote = input(0)` (host overlay), `editable = input(false)` (host-gated with `canEditLink`: author or admin), and the **conversation** inputs `sublinkCount = input(0)`, `sublinksExpanded = input(false)` with `sublinkToggle = output<void>()` (see Internal State for why the count is an INPUT, not read off `link`).
  - `LinkThreadComponent` (`app-link-thread`, the **recursive** conversation wrapper):

    | member        | kind             | meaning                                                                                                                                                                                                         |
    | ------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | `link`        | `input.required` | the node THIS instance renders — a host's conversation root, or a direct child reached through the recursion. `LinkCardItem`, so every host node binds straight in.                                             |
    | `userVote`    | `input`, `null`  | scalar optimistic-overlay vote, for a **host-rendered** root only. `null` (default) = "not supplied", so a `0` cannot masquerade as "the host removed my vote". **Not forwarded to nested levels** (see below). |
    | `voteValues`  | `input`, `{}`    | the host's per-link vote overlay keyed by id. Forwarded to **every** card at **every** depth — a sublink is votable too.                                                                                        |
    | `editable`    | `input`, `false` | show the edit pencil — forwarded down the recursion, so a sublink gets one too.                                                                                                                                 |
    | `voteChanged` | `output`         | `{ id, value }` — the **voted** node's own id, at any depth.                                                                                                                                                    |
    | `edit`        | `output`         | the clicked **descendant's** own `LinkCardItem`, never the root's.                                                                                                                                              |

    **Recursion, not a branch component:** the component lists **itself** in `imports` (`[LinkCardComponent, LinkThreadComponent]`), which Angular supports for standalone components (class binding exists when the decorator runs; AOT resolves the self-reference statically; verified under the vitest builder and `npm run build`). An extracted sibling `app-link-branch` would leave two definitions of "a node plus its children" free to drift. **No depth parameter exists:** the write side caps at `MAX_THREAD_DEPTH = 3` (backend `incident/services/social_link_threads.py`) and the read side is bounded by what the query fetched, so a leaf is simply a node with no `sublinks`.

  - `VoteButtonComponent` — `targetType = input<"incident" | "chronology" | "link">("incident")`; one button drives incident, chronology and link votes.
    - **Displayed state is three layers, not a `linkedSignal`:** `optimistic` (in-flight projection from `nextVoteState`) → `confirmed` (snapshot the mutation acknowledged with) → `hostState` (the inputs). A `linkedSignal` re-seeds from inputs on ANY change, and the host writes the acknowledged `userVote` straight back down as its overlay — so the control reset to the PRE-CLICK `netScore` and the arrow stayed lit (see `MISTAKES.md`: "a `linkedSignal` display re-seeds from EVERY input").
    - `confirmed` is honoured only while `voteStatsKey(hostState())` still matches the triple it was computed against; the key deliberately **excludes `userVote`** (the host echoing our own value is not new data), while a real refetch (the home feed polls) moves the counters and correctly supersedes the snapshot.
    - All six vote mutations acknowledge with the same `VoteMutationPayload` (`userVote`/`voteScore`/`upvotes`/`downvotes`; `ok` is sent but never read — a rejected request is the failure signal). `voteStateFromAcknowledgement` degrades any non-finite field to the fallback, so a partial payload keeps the projection rather than painting `undefined`.
- **Outputs / Events / API Responses:**
  - `IncidentCalendarComponent.daySelected = output<string>()` — emits a `dateKey` on day click, "Today", month/year jump commit or prev/next navigation. `InsidenPage` calls `router.navigate(["/insiden", dateKey])`, so the viewed day is a real, shareable URL.
  - `LinkCardComponent`: `voteChanged = output<{ value: number }>()` after a successful vote; `edit = output<LinkCardItem>()` (the pencil); `sublinkToggle = output<void>()` (the card only reports the click — it has no idea what will be revealed). `LinkListComponent.voteChanged` re-emits with the id as `{ id: string; value: number }`.
  - `LinkThreadComponent`: `voteChanged = output<{ id; value }>()` (one thread renders N votable cards) and `edit = output<LinkCardItem>()` re-emitted with the clicked **descendant's own** `LinkCardItem` at any depth — that object is what the host's edit sheet hydrates from, and a wrong one would open the wrong link.
  - **`INSIDEN_INCIDENTS_QUERY`** (`data/insiden.queries.ts`) takes optional filters. `/insiden` fetches incidents overlapping the selected month ±14 days (`calendarMonthRange()` in `calendar-date.util.ts`) **OR** unresolved ones (`OR: { ongoing: true }`, for the pinned section). Changing months reloads the window; another day in the same month reuses it. The situasi consumer keeps its unfiltered query. Sub-selects carry the full lifecycle surface: `status`, `version`, `user { shortId }`, `categories`, chronology `status` + vote fields, per-incident `links(first: 10)` (first page of the connection) and `medias` with `id` + `uploader { nickname }`.
  - **`CalendarIncident`:** id, start/end datetime, `severity` (`MAJOR`/`MINOR`/`OTHERS`), `status` (`DRAFT`/`PENDING_APPROVAL`/`LIVE`/`REJECTED`), title, brief, details, `hasDetails`, `impactFactor`, `version`, `longTerm`, `inaccurate`, `lastUpdated`, author `user`, `lines`/`vehicles`/`stations`, `categories`, `chronologies[]` (ordered timeline entries with `status`, `voteScore`, `voteBreakdown`, `userVote`), `links` (connection), `medias[]`, and the incident's own `voteScore`/`voteBreakdown`/`userVote`.
  - **Mutations** (`data/insiden.queries.ts`): `CREATE_CALENDAR_INCIDENT_MUTATION`; `UPDATE_CALENDAR_INCIDENT_MUTATION` (sends `version` for OCC; returns the revision `id` when a non-admin LIVE edit created a draft, which the form chains into `SUBMIT_CALENDAR_INCIDENT_MUTATION`); `UPVOTE`/`DOWNVOTE`/`REMOVE_VOTE` (incident + chronology variants); `REQUEST_CHRONOLOGY_DELETION_MUTATION`; `SUBMIT_SOCIAL_MEDIA_LINK_MUTATION` (carries `incidentId` when targeted).
  - **A social-media link has TWO time axes; never conflate them.** `created` is "when someone _reported_ it" (moderation provenance). `occurredAt` is "when it _happened_": NOT NULL on the backend, indexed, backfilled from `COALESCE(posted_at, created)`, and the leading key of **every** ordering, window and keyset cursor (`-occurredAt, -id`; the feed's `currentServiceDayOnly` / `lastWeekOnly` / `alignPageToDay` windows; the console queue; the per-incident `links` connection). Both are **naive local wall time with no offset** (backend `USE_TZ = False`, `TIME_ZONE = Asia/Kuala_Lumpur`, often with microseconds) — never re-format through UTC (see `MISTAKES.md`: naive wall-time datetime vs `toISOString()`).
    - Types: `LinkCardItem.occurredAt` and `PublicSocialMediaLink.occurredAt` are **optional** (selected per document); `created` stays **required** — it is the display fallback `occurredAt ?? created` and the tooltip's absolute stamp, so a document that selects `occurredAt` but drops `created` renders a blank time.
  - **`occurredAt` on inputs is TRI-STATE, and one state is destructive** (backend `SocialMediaLinkInput.occurred_at: Maybe[datetime | None] = UNSET`):

    | sent                | `updateSocialMediaLink` does                                              |
    | ------------------- | ------------------------------------------------------------------------- |
    | key **omitted**     | leave the event time untouched                                            |
    | a datetime string   | set it                                                                    |
    | explicit **`null`** | **RESET** the row to its `created` ("this happened when it was reported") |

    An editor that **hydrates a visible control** must send the key **always** — never `?? undefined` (makes "cleared" unreachable) and never `row.occurredAt ?? null` (resets the timestamp on every save). The **console's** status-only verbs own no control, so they re-send the row's value **verbatim** (`linkStatusInput`) and omit the key only when the row has no event time. On the **create** path omitted and `null` are identical server-side (both stamp the submission instant), so the submit path omits the key — which is why `LinkFormComponent.submit` and the console's `saveLinkEdit` branch differently.

  - **The conversation TREE on `LinkCardItem`** (backend `SocialMediaLinkScalar`; a link is a root or a sublink of another link, to any depth). No server-side alias exists for the old names, so a stale spelling is a hard "Unknown field" on the whole query:

    | `LinkCardItem` field        | replaced         | meaning                                                                                                                                                                                                         |
    | --------------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | `parentId?: string \| null` | `threadId`       | the link this one hangs under; `null` **exactly** when it IS a root                                                                                                                                             |
    | `isThreadRoot?: boolean`    | (unchanged name) | a **ROOT MARKER**, true of every ordinary ungrouped link too — never an affordance gate                                                                                                                         |
    | `sublinkCount?: number`     | `threadSize`     | this node's OWN publicly-visible descendants **at any depth**; `0` for a leaf. **NOT** the conversation size                                                                                                    |
    | `sublinks?: LinkCardItem[]` | `threadLinks`    | this node's **direct** children, in stored sibling `position` order. **Recursive**: the element type is the interface itself                                                                                    |
    | (row types only)            | —                | `position?: number` on `PublicSocialMediaLink` / `SocialMediaLinkRow`: the gap-spaced `10, 20, 30, …` sibling rank, selected by both flat documents so a reorder permutation can be built from the STORED order |

    Four properties a caller gets wrong at least once:
    - **Optional by design:** all four are optional on `LinkCardItem` because flat surfaces don't select them and a narrower host selection must still satisfy the contract. `created` stays **required** alongside them: a nested child is itself a `LinkCardItem`, so a document that forgets `created` at depth 2 fails the same contract the root does (the point of the recursive type). The console's `SocialMediaLinkRow` selects all four, so there they are **required**.
    - **`sublinkCount` is not a conversation size.** Read the ROOT's count to size a conversation; never sum the column level by level — every node answers for itself, so a sum double-counts by exactly the depth (root 2, child 1, leaf 0 → 3 for a 3-link tree).
    - **`sublinks` order ≠ every other link list's order:** it is `position` ASC (author-chosen, not a timeline); every other list is `occurredAt DESC, id DESC`. Group members need not be contiguous in time.
    - **A conversation is public iff its ROOT is**, with time windows resolved across the whole subtree — so `sublinkCount`/`sublinks` count and list only **publicly-visible** descendants, and a hidden sublink isn't listed even on your OWN `mine` page. Moderation is root-only: hiding a middle node leaves it attached but takes it (and its descendants) out of both count and list.

  - **Photo upload is fire-and-forget:** `IncidentCardComponent.uploadPhotos()` pushes each pending file to `ImageUploadService.addToQueue(incidentId, file, "INCIDENT_CALENDAR_INCIDENT")`; the component awaits nothing (the service owns its queue/retries). Thumbnails open an in-page `MediaViewerComponent` overlay (same mechanism as `/gallery`), not a new tab.
- **Dependencies:**
  - `graphqlResource()` (`core/graphql/graphql-client.ts`) — reactive query wrapper over `httpResource`: SSR TransferState hydration, background retry with exponential backoff, `isLoading`/`hasError`/`retryCountdownSec`/`retryNow`. `GraphQLClient.request` is used directly for continuation pages (link infinite scroll).
  - `AuthService` — login state for the edit/vote/link gates and the author check (`user.shortId` vs `uid.slice(0, 8)`).
  - `ImageUploadService` (`core/upload/image-upload.service.ts`) — app-wide, IndexedDB-persisted upload queue (`AuthService` token, `upload-queue-db.ts`); `ImageFile` (`core/upload/image-file.ts`) is the shared candidate model.
  - `MediaViewerComponent` (`features/gallery/media-viewer/`) — `incidentMediaToViewerNode()` maps `MediaScalar` to its `MediaNode` input.
  - `PhotoPickerComponent` (`features/spotting/report-form/photo-picker/`) — `model<ImageFile[]>` `files` binding and an `isCompressing` computed.
  - `RetryBannerComponent` (`ui/retry-banner/`) — consumes any object matching the structural `RetryableResource` (`retryCountdownSec`, `retryNow`).
  - `InfiniteScrollDirective` (`ui/infinite-scroll/`) — IntersectionObserver sentinel for cursor-paginated link lists (Submitted Links tab, per-card link sections).
  - `ToastService`; `HlmSkeleton`/`HlmButton`/`HlmBadge`/`HlmCardImports`/`HlmCombobox`/`HlmSheet` (`src/app/ui/*`); `AppNavComponent`/`AppFooterComponent` (`shell/`); `MarkdownComponent` (`ngx-markdown`, renders `details`); `Router`.

## ⚙️ Internal State & Logic

No RxJS subjects, no store — Angular signals, computed at several levels.

- **`InsidenPage`:**
  - `selectedDate`/`selectedDateObj` computed from the route param (or today). `incidentsResource` is the single source of truth; `allIncidents`, `_sorted` (newest-first by `startDatetime`), `dayIncidents` (incidents covering the selected day, multi-day ones on every day they span) and `pinned` are `computed()`s over it.
  - `pinned` gates on `endDatetime === null` **alone** and excludes incidents already in `dayIncidents`. `longTerm` is an independent admin classification (its own badge), not a synonym for "unresolved": a long-term incident given an end date is resolved and must drop out.
  - Both lists split approved-first, with pending ones behind a collapsed-by-default "Pending Approval (N)" toggle (one signal per list; "approved" = not pending, status may be `LIVE` or missing).
  - An `effect` on `IncidentSheetService.isOpen()` (true→false) reloads the resource: the form is the only success-knower, so sheet close is the tightest signal (cancel reloads harmlessly; a failed submit keeps the sheet open and doesn't reload).
  - `activeTab` (`"incidents" | "links"`) is client-only state, no URL sync.
  - Ads: each card reports its details toggle via `detailsExpandedChange`; while ANY is expanded `insidenFeedSlotId` resolves `undefined` (renders zero DOM), keeping footerEnd + (feed OR expanded details) within the 2-ad-per-page cap.
- **`IncidentCalendarComponent`:** `viewedMonth` is a `linkedSignal` seeded from `selectedDate` (deep links land on the right month) but writable by navigation; `weeks()` and `_countsByDate()` derive the 42-cell grid and per-day severity-dot counts. A local state machine (`pendingMonth`/`pendingYear`, `jumpCounting`/`jumpProgress`, `setTimeout`/`setInterval`) implements a 3-second "commit window" after a month/year combobox pick, cleaned up in `ngOnDestroy`.
- **`IncidentCardComponent`:**
  - Local UI signals (`detailsExpanded`, `photosExpanded`, `pendingPhotos`, `viewerMedia`, `deletionOverride`); `chronology`, `duration`, `isOngoing`, `isInaccurate`, `severityVariant`/`severityLabel` and `canEdit` (pure `canEditIncident()`) are computed from the input. A live elapsed-time ticker (`elapsedTime` + `setInterval`, started in `afterNextRender`) runs only while `isOngoing()`, torn down via `DestroyRef`/`ngOnDestroy`.
  - Renders: the chronology timeline (per-row status tags via `chronologyStatusLabel()`, vote buttons, a "Request deletion" ghost button on LIVE rows that flips the row to `PENDING_DELETION` locally on success), a Links section, the latest history entry line (`calendarIncidentHistory`) and the in-page photo viewer.
  - **Links section:** compact spec-format rows `[yyyy-mm-dd hh:mm] [favicon] [bold domain + paler rest]` (not `app-link-card`). The label is the **displayed** instant `occurredAt ?? created` inside `incidentLinkLine`, matching the `-occurred_at, -id` order; both the nested `links(first: 10)` sub-select and the continuation query select `occurredAt`, or one list would label its first 10 rows by submission time and the rest by event time. Pending rows get an amber clock icon + "Pending approval" tooltip. Continuation pages use the root `publicSocialMediaLinks(incidentId, first, after)` — the same keyset the nested connection mints, so the cursor is forwarded verbatim and never decoded.
  - **Both documents must stay tree-free**, which keeps the conversation chip off this surface (no host to render it in; no tree field is selected). Keeping page 1 and continuations in agreement is the same two-document hazard as `occurredAt`/`created`; `incident-card.component.spec.ts` pins both.
  - Chronology synthesis: `defaultChronology()` (module-private in `data/incident-chronology.util.ts`, used by `buildChronologyEntries`) supplies a Start (+ "Issue resolved" if ended) timeline when the backend has no entries, and `buildChronologyEntries` appends a synthetic RED "Ongoing" tail row for an unresolved incident.
- **`IncidentFormComponent`:** `hydrate(incident)` consumes the pure `incidentToForm()` (model + chronologies + four id arrays); `isEditing` derives from `editTarget` and switches labels and the submit branch. Edit submit sends all fields + `version` (OCC) + `impactFactor`; a returned revision `id` chains `SUBMIT_CALENDAR_INCIDENT_MUTATION`. GraphQL rejections (one-open-draft / version-mismatch) toast verbatim and keep the sheet open.
  - Chronology section: per-row collapse plus "Collapse all / Expand all" (`setAllCollapsed()`), up/down reorder, Gemini extract/summarize flows (`IncidentAiService` → Firebase function endpoints), indicator status dots (pure `indicatorLabel()`/`indicatorDotClass()` in `chronology-list.util.ts`); on desktop the colour picker and datetime share a row.
  - Categories are a mandatory single dropdown defaulting to "Just Reporting" on new reports (mirrors the link form; `selectedCategoryId` signal + derived array). In edit mode the footer button reads "Undo All" and re-hydrates from the edit target instead of clearing.
- **`LinksSectionComponent`:** first page through `graphqlResource` (retry banner kept), continuation via `GraphQLClient.request` + the infinite-scroll sentinel; rendering is delegated to the shared `LinkListComponent`, so this host owns only pagination and reload-on-sheet-close (dropping appended continuation pages of the stale dataset).
  - **Deliberately flat, conversation-free:** neither the first-page resource nor `loadMore` sends `collapseThreads`, so every sublink is a row of its own. Nested-conversation UI is scoped to the home feed and the two management surfaces; this tab is "everything submitted", where hiding sublinks behind a root would lose rows the reader came for. The key is **omitted** (not an explicit `false`) to take the schema default — an explicit `null` is fatal on a `Boolean!` argument.
  - **No card here ever shows an "N links" chip — two independent facts, either sufficient, both pinned by this host's spec:** (1) `PUBLIC_SOCIAL_MEDIA_LINKS_QUERY` doesn't select `sublinks`, so there is nothing to reveal; (2) `app-link-list` renders `app-link-card` **without binding `[sublinkCount]`**, and the card gates on that INPUT, never on `link.sublinkCount` (which this document _does_ select as a plain fact). Adding tree fields to the shared list is a product change, and the spec fails the moment it happens.
- **`LinkCardComponent`** (`app-link-card`): the single link-row element for every surface (home feed, `/insiden` links tab, situasi).
  - Renders: favicon (Google S2, plain-link SVG fallback), domain/path colour split (`linkUrlPartsOf`), title, line badges, the **Pending** pill (only while `LinkCardItem.status === "PENDING_APPROVAL"`; `status?: string | null` is kept loose so both source node types satisfy it; `completed` is the console's separate "mark handled" flag and never drives it), the **Official** chip (only when `LinkCardItem.isAutomated === true`; selected by the home `FEED_QUERY` and the console's `SOCIAL_MEDIA_LINKS_QUERY`, left undefined by every other host, hence optional), and a right rail with the vote button, relative time and edit pencil. The conversation chip sits in the chip row beside the line/Official chips. The Pending/Official/line explanations are `sr-only` text, not `title` tooltips (see the overlay costs below).
  - **Two time axes:** the card _displays_ `occurredAt` ("when did this happen", the instant every feed/queue orders on) via `occurredAt = computed(() => link().occurredAt ?? link().created)` and `occurredLabel = humanizeSince(occurredAt())`. The fallback is load-bearing, not defensive: `occurredAt` is optional per document and `strictNullChecks` is OFF, so a host that omits the field would render nothing. `data-testid="link-created"` is deliberately **not** renamed (the stable hook host specs assert on) while its value is the event time; the tooltip's absolute stamp follows the same instant. `submittedAt` adds a second tooltip line (`link-submitted`, "Submitted MMM d, y HH:mm") **only when the two parsed instants differ**, compared by `Date.getTime()` not by string (the backend serialises microseconds; `created` may lack a fractional part).
  - **Stretched link:** the `<a>` (`link-anchor`) is an `absolute inset-0 z-0` overlay across the left column; the visible body and chip row are `pointer-events-none relative z-10` layers above it. Every interactive control (vote, conversation toggle, edit pencil) is a **sibling** of the anchor (a `<button>` inside a link is invalid HTML and its click also navigates); the toggle opts back in with `pointer-events-auto`, and clicks on the non-interactive chips fall through to the anchor. See `MISTAKES.md` (2026-10-01 `insiden/link-card`; 2026-09-22 → 10-01 interactive controls outside the `<a>`). Two deliberate costs: an element under the overlay can't have a hover tooltip (chip `title`s became `sr-only` text), and the title isn't drag-selectable (same trade as Bootstrap `.stretched-link`). The anchor's accessible name is explicit (`anchorLabel()`: title, then raw URL) because it no longer wraps visible text.
  - **Conversation affordance** (chevron + readable "N links" button: `link-thread-toggle` / `link-thread-size`, `aria-expanded`, action-naming `aria-label` "Show/Hide the other links in this thread (N links)"):
    - The gate is `sublinkCount > 0` (`hasSublinks`), never `isThreadRoot`.
    - **`sublinkCount` is an INPUT, not read off `link`:** `LinkCardItem.sublinkCount` is optional because flat hosts don't select it, and they must not grow a chip. The input defaults to `0`, so a flat host passing nothing gets no affordance even when its nodes carry a count. `NaN > 0` is `false`, so a bad fixture degrades to "no chip", not "NaN links".
    - The label is `conversationLabel = threadLabel(sublinkCount() + 1)` (the `+ 1` is load-bearing, see `threadLabel` below); the visible chip and the toggle's `aria-label` both read it.
    - The card does **not** own expansion state or children: `app-link-thread` holds one `expanded` signal per level and renders the nested cards. That is what lets one card serve a flat host (no input bound → no chip, no wiring) and every depth of a tree.
  - Test ids: `link-anchor`, `link-url-domain` / `link-url-path`, `link-tags`, `link-pending`, `link-official`, `link-meta-rail`, `link-thread-toggle` / `link-thread-size`, `link-time` / `link-created` / `link-submitted` / `link-submitter`, `link-edit`. The host passes `userVote` (its authenticated overlay wins over the anonymous feed value) and `editable`; the card re-emits votes as `voteChanged` and the pencil as `edit`.
- **`LinkThreadComponent`** (`app-link-thread`): the **recursive** wrapper and the **named extension point for any grouped row**. Structure: one `<app-link-card>` for this node, then — only when `expanded() && children().length > 0` — a `link-thread-members` container (`border-l pl-3`: indent plus left rule) holding one nested `<app-link-thread>` per child (`track child.id`). The container renders only when non-empty, so a host supplying a count without the nested selection (or a leaf) leaves no empty rule behind. The wrapper root carries `data-testid="link-thread"` (not the console chip's `link-thread` testid — different component). SSR-safe: no browser APIs.
  - `children = computed(() => link().sublinks ?? [])` (direct children, stored `position` order; `?? []` because `sublinks` is optional and `strictNullChecks` is OFF). `sublinkCount = computed(() => link().sublinkCount ?? 0)` is handed to the card (absent = "host didn't select it" = no chip).
  - `expanded = signal(false)` — **collapsed by default, per level and independently** (one signal per component _instance_). Same pattern as `app-link-list`'s "Pending (N)" section.
  - `voteFor(link)`: host's keyed `voteValues[id]` → the root's scalar `userVote` (**this node only**, when supplied) → `link.userVote ?? 0` — identical to `app-link-list`, so a link can move between a flat list and a conversation without changing how its vote renders. `userVote` is **not forwarded** to nested levels: it is an unkeyed number for "this row", and a nested instance would apply it to ITSELF (`voteFor` matches `link.id === this.link().id`), painting the root's optimistic vote on a child. `voteValues` is keyed and safe at every depth.
  - `editable` **is** forwarded to every level, and `edit` re-emits the clicked descendant's own `LinkCardItem`: a conversation is a set of ordinary, individually-approvable links, and a rider who timestamped the follow-up photo should be able to fix its wording. `editable` is ONE boolean per conversation, so a host computing it from the ROOT (home does, `canEditLink(root)`) also grants a pencil on a sublink someone else submitted. That is a **cosmetic over-permission only** (as `canEditLink`'s docstring says, the backend re-checks the target link and rejects the write); per-link authorship would need a predicate input no host asks for.
  - **Appearance rule:** the root renders through the same `app-link-card` with the SAME inputs as a plain list row — no wrapper class, bold, badge or size change — and the spec asserts `outerHTML` parity between a threaded and an unthreaded root. The only legitimate difference is the card's own rail chip. A distinct first link would grow a second visual hierarchy in the feed for no gain (a product decision).
- **`LinkFormComponent`:** the model carries `occurredAt` (a `datetime-local` value; `""` = unset, deliberately unvalidated — blank is the common, correct answer). The control is last in the "Link" section (after Title, before the Tags block): a rider fills in story order — what it is (URL) → what it's called (Title) → when → where/what it concerns (tags); the tag block is a bulk-assignment panel, so a clock at its bottom would read like another filter. It renders **empty** by default (no `new Date()` default: server/client clock or timezone skew would emit two different `value=` attributes for one request, and the server decides the report instant). Edit mode hydrates from `isoToOccurredAtInput(target.occurredAt)` — the **event** time, never `created`, because hydrating the wrong column would rewrite it on the next save. `submit()` branches on the tri-state: edit always sends `occurredAt: occurredAtInputToIso(m.occurredAt)` (a cleared box is the deliberate reset); create spreads `...(occurredAt ? { occurredAt } : {})`. `clear()` resets it with the model, so an edit-mode clear followed by a create-mode open can't carry the edited row's event time into a new submission.
- **`LinkListComponent`** (`app-link-list`): host-agnostic list taking an ordered `links` input, a host-specific `emptyMessage` and a `voteValues` overlay (`Record<id, number>`). Owns the approval-axis split (approved = `status !== "PENDING_APPROVAL"`, pending = `=== "PENDING_APPROVAL"`; the `completed` flag never groups rows), the UTC day-group headers (Today/Yesterday/`MMMM d, y` via `groupLinksByDay()` — UTC so SSR and browser agree on buckets), the collapsible pending section, and the edit pencil gated by pure `canEditLink()` (author `shortId` match or admin), which opens the shared sheet via `LinkSheetService.openEdit()`. Re-emits each vote as `voteChanged = output<{ id; value }>()` and emits `sheetClosed` on the sheet's open→closed edge so the host reloads (an edit submit or cancel changed server data).
- **`LinkSheetComponent`** (`app-link-sheet`): hosts the HlmSheet + `LinkFormComponent` pair with edit-aware labels ("Edit link"/"Save" vs "Submit a link"/"Submit"), an optional `defaultLineIds` input (line-prefilled submissions on the situasi tab) and `data-testid="submit-link"` on the submit button.
- **`LinkSheetService`** (root, `data/link-sheet.service.ts`): `open(context?, prefill?)` opens create mode; the optional `{ url? }` seeds a one-shot URL prefill (home's "Advanced Input"). `openEdit(link)` opens edit mode and never prefills. `close()`/`setOpen(false)` clear the pending prefill. The form consumes it through consume-once `takePrefillUrl()` (returns and clears), so a later reopen without a new prefill starts blank.
- **Pure helper modules** (`data/` unless noted) carry the non-trivial domain logic:
  - `calendar-date.util.ts` (`dateKeyOf`, `incidentCoversDate`, `calendarMonthRange`), `elapsed-time.util.ts` (`getReadableTimeDifference`), `incident-to-form.util.ts` (`incident-form/`; edit hydration), `can-edit.incident.util.ts` / `can-edit.link.util.ts` (edit-button gate matrices), `chronology-status.util.ts` (status labels + deletion predicates), `incident-chronology.util.ts`, `incident-status.util.ts`, `incident-history-line.util.ts`, `incident-media-viewer.util.ts` (photo → viewer node), `social-link.util.ts`, `link-url.util.ts`.
  - `link-day-group.util.ts` (`linkDisplayInstant`, `linkDateKey`, `linkDayLabel`, `groupLinksByDay`): `linkDisplayInstant(link)` is the ONE rule for "which instant does a link display" — `occurredAt ?? created` — and `groupLinksByDay` buckets on it (UTC frame).
  - `incident-link-line.util.ts` (spec link-line formatting; `toLocalDateTimeLabel` and `datetimeLabel` read `input.occurredAt ?? input.created`).
  - **`link-occurred-at.util.ts`** (`isoToOccurredAtInput`, `occurredAtInputToIso`) — the `datetime-local` ↔ API conversion; Angular-free, spec-covered in isolation. Contract: offset-free in and out, never `toISOString()` on a naive wall-time field (shifts it 8 hours), and a value not matching the control's shape passes through **unchanged** rather than becoming `null` (`null` on update is a destructive reset, so guessing would turn a typo into silent data loss). Consumed by the link form, the console edit sheet and anything hydrating a `datetime-local` from `occurredAt`. Mirrors the incident form's `isoToDateTimeLocal` but lives in its own module so no link surface reaches into the incident form to format a timestamp.
  - **`link-thread-selection.util.ts`** (`toggleSelection`, `areAllSelected`, `canGroup`, `canNest`, `selectedWithin`, `threadLabel`) — selection mechanics of the two grouping surfaces (the console triage table and the profile's "My Submitted Links"). Every function is total and immutable (no Angular/`signal`/RxJS) and returns a NEW array, because results are fed straight back into a signal: in-place mutation yields the same reference, change detection never fires and the checkbox silently stops updating. The two minimums are separate on purpose: `canGroup` needs two (an untargeted one-link call elects that link as its own root), `canNest` needs one (with a target it becomes a real child).
    - **`threadLabel` is the single place pluralisation is decided for a link conversation anywhere in the app.** Consumers: (1) the console triage chip (`/console/links`; inside the URL cell, renders nothing on `""`) plus `confirmThreadCoupling`; (2) the "My Submitted Links" badge on the profile page; (3) `app-link-card`'s indicator (`conversationLabel = threadLabel(sublinkCount() + 1)`). `app-link-thread` is **not** a consumer (the card owns the chip; the wrapper just renders cards). The helper's docstring says to **re-derive the list from the code**, not from memory.
    - No consumer may grow its own `` `${n} link${n === 1 ? "" : "s"}` `` — that is how one surface says "1 links" and another "2 link", which no type or test catches. A new conversation count joins the helper; what legitimately differs between sites is the **gate** deciding whether a count shows, not the string.
    - **Its parameter is a CONVERSATION SIZE (`sublinkCount + 1`), not a descendant count.** It answers `""` for `<= 1`, so a raw `sublinkCount` **silently deletes the chip on a root with exactly ONE sublink** (`1` → `""`) while leaves stay correctly chip-less (`0` → `""`) — which is why the bug hides. Don't "tighten" the `""` branch either (`1` → `"1 link"`): a chip would sprout on every ordinary row in the app (see `MISTAKES.md`: "two counts, one question").

## 🧩 Extension Points & Hooks

- **`RetryableResource`** (`ui/retry-banner/retry-banner.component.ts`) is a structural interface: any resource-like object (another fetch wrapper, a test mock) can drive `RetryBannerComponent` without coupling to `graphqlResource()`.
- **Lookup tables:** `SEVERITY_DOT` (private `Record` in `calendar/calendar.component.ts`) and `SEVERITY_VARIANT` / `SEVERITY_LABEL` / `CHRONOLOGY_DOT` (private `Record`s in `incident-card/incident-card.component.ts`) — a new severity or indicator value is a one-line addition per table, not a scattered conditional.
- **`defaultChronology()`** (`data/incident-chronology.util.ts`) is the seam for adjusting the no-chronology fallback timeline without touching rendering.
- **`INSIDEN_INCIDENTS_QUERY` is a single flat string constant:** extending the fetched fields is a local, additive edit to `insiden.queries.ts` plus a `CalendarIncident` interface change. New fields follow the optional-field + DEPLOY-ORDER comment pattern.
- **Pure utils are the gate/label/format seams** (`canEditIncident()`, `canEditLink()`, `chronologyStatusLabel()`, `incidentLinkLine()`, `incidentToForm()`, `groupLinksByDay()`, `incidentMediaToViewerNode()`): tested, isolated, reusable without touching markup.
- **`app-link-thread` is the named extension point for any grouped link row, and it is recursive.** It takes the same structural `LinkCardItem` the card takes, so a new host binds a `FeedLink`, a `PublicSocialMediaLink` or a fixture straight in at any depth; its internals (per-level `expanded`, the `sublinkCount > 0` gate, the `sublinks` recursion) mean a host can't re-decide them.
  - **Keep the self-reference** (see Interface; don't extract an `app-link-branch`).
  - **The card owns the chip, the wrapper owns the state:** the wrapper passes the count through and never reads `isThreadRoot` or pluralises. A host must not bind `[sublinkCount]` on `app-link-list` unless it has a nesting to reveal — that is what keeps `/insiden`, the situasi tab and the incident cards flat.
  - **`editable` is forwarded to every level on purpose;** the cosmetic over-permission and the per-link-predicate trade-off are described under Internal State.
  - **Don't "improve" the root's presentation** (byte-identical DOM to a plain row apart from the rail chip).
  - **`MAX_THREAD_DEPTH` (server write-side cap) is not mirrored here:** the read side is bounded by what the query fetched, so a host asking for deeper nesting just gets `[]`; a client that mirrors the cap silently loses a level the day the cap moves. A host wanting conversations open by default (or one specific one open) adds an input rather than re-deriving the toggle.
- **Single seams for the link feature** (contracts described under Pure helper modules above): `link-occurred-at.util.ts` for datetime-local ↔ API (offset-free, never `toISOString()` on naive wall time, shape-mismatch passed through **unchanged** because `null` on update is a destructive reset); `linkDisplayInstant(link)` for which instant a link displays (a new surface that groups, sorts or labels links must key on it, not `created`, or a back-dated report scatters one day under two headers and orders differently from the feed above it; the home feed's `groupFeedLinksByDay` applies the same fallback inline, the situasi section sorts on it); `link-thread-selection.util.ts` for any future grouping surface (so admin and submitter experiences can't drift).
- **Details/photos use an in-place expand/collapse idiom** (matching `vehicle-list.component.ts`) rather than a modal/drawer; build new expandable sections the same way.
- **The photo-attach path is additive:** `PhotoPickerComponent`, `ImageUploadService` and `MediaViewerComponent` are shared, feature-agnostic primitives (already reused by `features/spotting` and `features/gallery`), so any "attach evidence" flow can plug into the same picker/queue/viewer.
- **`InfiniteScrollDirective`** is a reusable sentinel (IntersectionObserver + coalescing) for any cursor-paginated list.

## 💡 Potential Feature Opportunities

- **Extend thread UI to the flat surfaces — still open.** `app-link-thread` ships on the **home feed** (today + Last Week); the two management surfaces roll their own (the console triage table is an accordion over the ordered tree with rails + child tint; My Submitted Links shows hierarchy as an indent). `/insiden`'s Submitted Links tab, the situasi tab and the per-incident cards stay flat and complete: a reader browsing "everything submitted" would lose rows, and a per-line filter wants a complete list of reports about that line. The component is host-agnostic and recursive, but adopting it is **not** a one-line swap; the remaining work is **selections**:
  1. `PUBLIC_SOCIAL_MEDIA_LINKS_QUERY` (Submitted Links, situasi, My Links, incident-card continuations) selects `parentId` / `isThreadRoot` / `sublinkCount` / `position` but **deliberately not `sublinks`**, which the wrapper expands from.
  2. The per-incident `links(first: 10)` sub-select selects **no** tree field (only `id url title occurredAt created status completed`), and the incident card builds ONE list from that sub-select **plus** continuation pages from the document above — page 1 would arrive with no tree fields while the rest had them (the same two-document hazard as `occurredAt`/`created`; pinned by `incident-card.component.spec.ts` on both documents).

  Real work: add nested `sublinks` to both documents (to the depth shown), keep the two selection sets in agreement, set `collapseThreads: true` on the first page **and every continuation**, and decide deliberately about `mine`, which the backend never collapses (a submitter must never lose their own sublinks behind a root). Each flat host's spec currently **fails** if the tree leaks in, so closing this is a deliberate, spec-visible product change, not a refactor.

- **Client-side filtering by line/vehicle/station/severity:** ready — `allIncidents`, `dayIncidents` and `pinned` are `computed()` over `incidentsResource`, so a filter-criteria signal folded into them is a small additive change. It filters the **loaded window** (selected month ±14 days plus ongoing), not all history, and needs no backend work.
- **Calendar export (iCal/.ics):** ready — `CalendarIncident` carries start/end datetime, title and brief, enough for a `.ics` feed or "Add to calendar" action from `incidentsResource` data with no schema change. `core/export/csv.util.ts` exists for CSV only; no `.ics` generator yet.
- **Ongoing-incident subscriptions/notifications:** good idea, not ready — `pinned` and `IncidentCardComponent.isOngoing()` already isolate active incidents, but there is no push-notification service or per-user subscription record anywhere in the app or backend. It needs a delivery mechanism (e.g. an FCM topic or backend webhook) and a backend "subscribe to incident" mutation/model first.
- **Shareable/deep-linkable incident state:** partially ready — day selection already round-trips through the URL, but per-incident UI state (`detailsExpanded`, `photosExpanded`) is local signals. Syncing an incident-id fragment/query param to them is a moderate change confined to `InsidenPage`/`IncidentCardComponent`; `core/url-state/query-param.util.ts` provides the read/write helpers.

## 💡 Potential AI Feature Opportunities

- **Automated incident summarization/triage:** `brief`, `details` and ordered `chronologies[]` are structured, timestamped text — a fit for an LLM plain-language "what happened and current status" summary, or auto-classifying `severity`/`impactFactor` at creation. The form already ships Gemini extract/summarize flows (`IncidentAiService` → Firebase function endpoints), so the plumbing exists.
- **Anomaly/pattern detection over incidents:** lines, vehicles, stations, severity and duration of the loaded window are resident client-side — a substrate for recurring-disruption or "this line has had N incidents this month" insights beside the calendar (a cross-month view would need wider fetches, since the page loads only the selected month ±14 days plus ongoing).
- **Smart photo/evidence assistance:** the photo pipeline (`PhotoPickerComponent` → `ImageUploadService` → `MediaViewerComponent`) is a ready hook for AI captioning, duplicate/blur detection or auto-tagging before upload, reusing the queue/compression flow.
