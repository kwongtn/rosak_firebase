# 2026-09-25

## spotting/line-details: pinned mobile type label styling parity (this change)

- **What**: on mobile (<768px) the type label renders twice — the in-flow full-width TYPE row and
  the pinned overlay copy (`data-testid="grid-mobile-pinned-label"`). Their class lists had drifted,
  so when a type anchored (pinned) under the header, its font size, colour and borders visibly
  jumped from the in-flow styles. Both copies now share one `mobileTypeLabelClass()` string: the
  pinned overlay's per-date totals cells use `border-b` to match the in-flow totals row's `border-b`
  (they previously used `border-t`), and the in-flow label's inner `<span>` wrapper was removed —
  the label is itself the flex row now. Desktop markup is untouched.
- **Why**: two markup copies of the same visual element each carried their own hand-maintained class
  list, so a styling pass on one copy was never mirrored to the pinned snapshot — pinning a type is
  exactly when the two copies are on screen at once, making the drift a visible jump.
- **Fix**: one class-producing method (`mobileTypeLabelClass()`) is the single source of the label's
  look classes for both copies, the pinned totals cells' border side was aligned to the in-flow
  totals row, and a new unit test pins that the pinned label carries the same look classes as the
  in-flow label so the parity can't regress silently.
- **Verified**: new unit test
  `"renders the pinned type label with the same look classes as the in-flow type label"` was RED 1
  failed / 10 passed → GREEN 11 passed / 11. Full suite `npm test -- --no-watch`: **87 test files /
  766 tests passed**. `npx prettier --check .` clean; `npm run build` exit 0.
  `npx playwright test e2e/spotting-details.spec.ts`: 2 passed (mobile 390×844 + desktop 1280×900);
  fresh screenshot `.omo/evidence/spotting-details-mobile-pinned.png` confirms the pinned label now
  matches the in-flow label.
- **Docs**: this entry + the monthly Highlights row; `MISTAKES.md` entry on duplicated
  pinned-overlay styling drift.

## core/graphql: retain equal response data references

- **What**: added a JSON-shaped `deepEqual` utility and wired `graphqlResource()` to pass it through
  Angular `httpResource`'s `equal` option. The resource now retains the previous response/data object
  on a structurally equal refresh by default; callers can opt out with
  `graphqlResource(requestFn, { retainDataIfEqual: false })` when every response must replace the
  reference.
- **Why**: route revalidation and polling should not churn computed signals, effects, or DOM
  bindings when the server returns the same GraphQL payload.
- **Fix**: the utility uses `Object.is` for scalar/identity semantics, compares arrays and plain
  objects structurally, and uses an explicit work stack for deeply nested JSON. The GraphQL wrapper
  keeps its existing retry/loading/error/reload/SSR behavior; the equality policy is the only new
  option.
- **Verified**: `npx prettier --check .`; `npx tsc -p tsconfig.app.json --noEmit`; targeted
  `graphql-client` (3) and `deep-equal` (6) suites; full `npm test -- --no-watch` (93 files /
  800 tests). `npm run build` was intentionally not run for this scoped work.
- **Docs**: this entry + the monthly summary; the route-persistence notepads record the filter and
  parallel-workstream findings.

## spotting/route-persistence: keep-alive pages, scroll memory, and silent revalidation

- **What**: shipped opt-in route persistence for the three spotting page routes. `ReusableRouteStrategy`
  extends `BaseRouteReuseStrategy`, detaches only routes marked `data: { reuse: true }`, keys handles by
  route-config identity plus declared path-param values, and keeps a bounded 10-handle LRU (evicted
  handles are destroyed with `destroyDetachedRouteHandle`); the optional details-tab matcher parameter is
  intentionally excluded so `/details` and `/details/:tab` share one mounted page.
  `RouteScrollMemoryService` remembers `ViewportScroller` positions by normalized URL path and
  reapplies them in a microtask after the router's `Scroll` event. `revalidateOnReturn` plus the
  `isSpottingLineRoute`, `isSpottingDetailsRoute`, and `isSpottingVehicleRoute` predicates in
  `spotting-route-patterns.ts` provide silent return-time reloads for the page and data-section owners,
  while `spotting-history.component.ts` stays excluded so its append pagination is not reset. The
  equal-response retention side is already documented in the `core/graphql: retain equal response data
references` section above; this work reuses that seam rather than duplicating it.
- **Why**: the default route reuse strategy destroyed the page component, its DOM, and its
  component-owned resources on every cross-page spotting navigation, so returning re-ran a pristine
  fetch and flashed skeletons. Scroll restoration could not reliably land on a remembered offset
  while the page was still skeleton-high, and imperative in-app back links did not get browser
  `popstate` restoration.
- **Fix**: registered `{ provide: RouteReuseStrategy, useClass: ReusableRouteStrategy }` in
  `app.config.ts`, marked the three page routes for reuse, and instantiated the browser-only,
  50-entry-LRU scroll-memory service through an app initializer. The service skips fragment anchors
  and same-path query-only changes. Shared route predicates now drive `revalidateOnReturn` for
  `LineOverviewPage`, `LineDetailsPage` (including `vehicle-spotting-grid`, `vehicle-status-trend`,
  `station-assets-section`, `situasi-section`, and `insiden-section`), `VehicleDetailPage`, and
  `incident-timeline`; it ignores first activation and same-pattern param/query navigations, then
  reloads when the route is re-entered from outside.
- **Verified**: **93 test files / 800 tests passed** with `npm test -- --no-watch`;
  `npx prettier --check .`, `npx tsc -p tsconfig.app.json --noEmit`, and `npm run build` (production
  SSR) all passed. Live verification restored list scroll 600 through details and an in-app back while
  the refresh was held for 2.5s, with 0 skeletons, the same DOM node, and a `VehicleTypesByLine`
  request count of 3→4; browser back/forward restored details 400/list 600, and details → vehicle →
  back restored 400 with the same grid DOM. Evidence: `.omo/evidence/keepalive-live-back-while-refreshing.png`
  and `.omo/evidence/keepalive-live-back-from-vehicle.png`.
- **Docs**: this entry + the monthly `SUMMARY.md` row + the `docs/components/spotting.md`
  route-persistence seam + `MISTAKES.md`; the earlier retention entry remains the source of truth
  for `retainDataIfEqual` / `deepEqual`.
