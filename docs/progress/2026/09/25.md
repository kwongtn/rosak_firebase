# 2026-09-25

## spotting/line-details: pinned mobile type label styling parity (this change)

- **What**: on mobile (<768px) the type label renders twice — the in-flow full-width TYPE row and
  the pinned overlay copy (`data-testid="grid-mobile-pinned-label"`). Their class lists had drifted,
  so when a type anchored (pinned) under the header, its font size, colour and borders visibly
  jumped from the in-flow styles. Both copies now share one `mobileTypeLabelClass()` string: the
  pinned overlay's per-date totals cells use `border-b` to match the in-flow totals row's `border-b`
  (they previously used `border-t`), and the in-flow label's inner `<span>` wrapper was removed —
  the label is itself the flex row now. Desktop markup is untouched.
- **Why**: two markup copies of the same visual element each carried their own hand-maintained class
  list, so a styling pass on one copy was never mirrored to the pinned snapshot — pinning a type is
  exactly when the two copies are on screen at once, making the drift a visible jump.
- **Fix**: one class-producing method (`mobileTypeLabelClass()`) is the single source of the label's
  look classes for both copies, the pinned totals cells' border side was aligned to the in-flow
  totals row, and a new unit test pins that the pinned label carries the same look classes as the
  in-flow label so the parity can't regress silently.
- **Verified**: new unit test
  `"renders the pinned type label with the same look classes as the in-flow type label"` was RED 1
  failed / 10 passed → GREEN 11 passed / 11. Full suite `npm test -- --no-watch`: **87 test files /
  766 tests passed**. `npx prettier --check .` clean; `npm run build` exit 0.
  `npx playwright test e2e/spotting-details.spec.ts`: 2 passed (mobile 390×844 + desktop 1280×900);
  fresh screenshot `.omo/evidence/spotting-details-mobile-pinned.png` confirms the pinned label now
  matches the in-flow label.
