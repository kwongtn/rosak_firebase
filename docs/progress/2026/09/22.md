## Home: spotting entry sheet hosted on the front page (wave 1 of the UI revision)

- **What**: the community front page can now host the existing spotting "Add a Spotting Entry" flow,
  opened from a line card and pre-scoped to that line — no new form.
  - `ReportSheetService` (`features/spotting/data/report-sheet.service.ts`) gained
    `lineId = signal<string | null>(null)` and `openFor(lineId)` (mirrors
    `LineStatusSheetService.openFor`); `open()`/`setOpen()`/`isOpen` unchanged.
  - `ReportFormComponent` seeds the model's `lineId` on the closed→open edge when a seed is present,
    then consumes it (`lineId.set(null)`) so a later seedless `open()` (the /spotting shell's own

    so the two edges can never race.

    `SpottingShellPage`); `(submitted)` closes the sheet and calls `store.reloadAll()`. The `""` route
    in `app.routes.ts` now also provides the spotting `SpottingLinesStore`. Testids:
    `spotting-entry-sheet` / `submit-spotting-entry`.
- **Tests**: new `report-sheet.service.spec.ts` + `report-form.component.spec.ts`, extended
  `home.page.spec.ts`. Full suite 71 files / 518 tests green; production build OK.

## Home: front-page UX round (commits 9c1acf8, dcf9885, a0f1b95, 858d059, 3e46c04)

- **Line-status submit errors + Cancel** (`9c1acf8`): `line-status-sheet.component.ts` now sets an
  inline `submitError` (`[data-testid="line-status-submit-error"]`, `role="alert"`) on all three
  previously-invisible failure paths — a GraphQL payload with `ok: false` (previously ignored, so a
  **false success toast** was shown and the sheet closed), a thrown `GraphQLRequestError` (server
  message mirrored), and a transport error (generic retry copy, rethrown to Sentry). A
  `[data-testid="cancel-line-status-report"]` button closes the sheet, and `clear()` resets the error.
- **Feed submit errors + schemeless URLs** (`dcf9885`): `link-submit-box.component.ts` shows an inline
  `[data-testid="feed-submit-error"]` for both a rejected and an unreachable submit; the URL input
  switched from `type="url"` to `type="text"` + `inputmode="url"` because native URL validation was
  silently blocking schemeless input (`example.com/x`) before `submit()` ever ran. New pure
  `feed-url.util.ts::normalizeFeedUrl()` scheme-qualifies the value at submit time (`https://` prefix,
  protocol-relative `//host` handled, an existing `http(s)://` left untouched, other schemes left
  alone).
- **Chart labels + reserved height** (`a0f1b95`): `line-status-chart.component.ts` labels all 24
  service-day hours (no every-third sampling) on a `min-w-[24rem]` strip inside an `overflow-x-auto`
  lane, so narrow screens scroll instead of collapsing the labels. The loading skeleton, "No reports"
  message and the loaded chart all share the exported `CHART_STATE_MIN_HEIGHT_CLASS` (`min-h-40`), so
  the card below never jumps between states.
- **Feed row + list pagination** (`858d059`): the feed timestamp is bottom-aligned into the tag row
  (or the title row when the card has no tags) via a stretched meta rail instead of its own footer
  row; `feed-link.util.ts::feedUrlPartsOf()` splits the URL so the domain keeps the card's foreground
  colour and the path renders muted. The page renders the feed in a `feed-scroll` container (max 60vh)
  and reveals one fetched page at a time, with a `[data-testid="feed-load-more"]` button while another
  page exists.
- **Per-category report pills** (`3e46c04`): the single `[data-testid="passenger-status-count"]` badge
  on the passenger chip was **removed** at the user's correction; the hover popover now renders one
  `[data-testid="status-count-pill"]` per reported status (e.g. `Normal (3)`), fed by the backend's
  `passengerStatusCounts` through `status-info.util.ts::passengerStatusRows()`.
- **Tests / gates**: 632 unit tests, production build, and 9/9 e2e green.
