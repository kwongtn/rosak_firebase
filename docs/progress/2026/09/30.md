## insiden: links are timestamped by when the event happened (`occurredAt`)

Backend half landed first (`SocialMediaLink.occurred_at` NOT NULL + indexed, backfilled from
`COALESCE(posted_at, created)`; `thread` self-FK). This is the frontend half: every link surface
now reads the event instant and keeps the submission time beside it as provenance.

- **What**:
  1. **New pure util `data/link-occurred-at.util.ts`** — `isoToOccurredAtInput(iso)` (API string →
     a `datetime-local` value, `""` for null/unparseable, seconds dropped) and
     `occurredAtInputToIso(value)` (`""`/null → `null`; otherwise normalised to
     `YYYY-MM-DDTHH:mm:ss` with **no offset**, and a value that doesn't match the control's shape is
     passed through unchanged rather than mapped to `null`). Both parse/format **by hand**: the
     backend runs `USE_TZ = False` with `TIME_ZONE = Asia/Kuala_Lumpur`, so a stored datetime is
     naive local wall time serialised without an offset and a `new Date(iso).toISOString()` round
     trip would shift it by 8 hours. Mirrors the incident form's
     `extract-data.util.ts::isoToDateTimeLocal` but lives in its own module, Angular-free, so it is
     unit-testable in isolation.
  2. **`LinkCardItem` gains `occurredAt?`** and `app-link-card` **displays `occurredAt ?? created`**
     (`occurredAt`/`occurredLabel` computeds). The testid stays `link-created` — it is the stable DOM
     hook host specs assert on — but the _value_ is now the event time. The tooltip's absolute stamp
     follows the same instant, and a second line (`data-testid="link-submitted"`,
     "Submitted MMM d, y HH:mm") appears **only when the two parsed instants differ** (both absent or
     both equal → no second line). Compared by `Date.getTime()`, not by string, because the backend
     serialises microseconds and `created` may arrive without a fractional part.
  3. **The link form** (`LinkFormComponent`) gains an optional `datetime-local` "When did this
     happen?" control, last in the "Link" section (after Title, before the tags block) with the hint
     "Leave blank to use the report time. You can correct this later." It is deliberately **not**
     validated (blank is the common, correct answer) and deliberately has **no** "now" default — a
     server/client clock or timezone skew would otherwise emit two different `value=` attributes for
     one request. Edit mode hydrates it with `isoToOccurredAtInput(target.occurredAt)` — from
     `occurredAt`, never from `created`; hydrating the wrong column would silently rewrite the event
     time on the next save.
  4. **The console edit sheet** gets the same control (`data-testid="edit-occurred-at"`, hint "Clear
     it to fall back to the report time. This is the column the public feed sorts on.") and the
     detail card an "Occurred on …" line (`data-testid="detail-occurred-at"`).
  5. **`linkStatusInput` re-sends `occurredAt: link.occurredAt`** verbatim. `SocialMediaLinkInput` is
     replace-not-patch _and_ `occurredAt` is tri-state with a destructive third state (explicit
     `null` resets the row to its submission time), so one `?? null` would have made every console
     Approve/Hide click rewrite the event time of every row — and re-sort the public feed with it.
  6. **Every day grouping and sort keys on the display instant.** `link-day-group.util.ts` exports
     the rule as `linkDisplayInstant(link)` (`occurredAt ?? created`) and `groupLinksByDay` buckets
     on it — the UTC frame is unchanged, only the field is. `groupFeedLinksByDay` (home, LOCAL frame)
     applies the same fallback inline. `situasi-section` sorts on `linkDisplayInstant` via
     `localeCompare` (plain string comparison is correct — both fields are naive wall time from one
     serializer) and `incidentLinkLine`'s `[yyyy-mm-dd hh:mm]` label reads `occurredAt ?? created`.
     The nested per-incident `links(first: 10)` sub-select in `insiden.queries.ts` also selects
     `occurredAt`, so an incident card's first page and its appended continuation pages label rows
     from the same column — worth stating because they briefly did not: the nested page fell back to
     `created` while the continuation pages (from `PUBLIC_SOCIAL_MEDIA_LINKS_QUERY`) showed the event
     time, splitting one list across two clocks.
- **Why**: a link's displayed and ordering timestamp was its submission time, so an operator post
  captured after publication sat at the top of the feed as if it had just happened, and there was no
  way to state that a link was about an event three days old. `occurredAt` answers "when did this
  happen" and is now the leading key of every ordering, window and keyset cursor; `created` is
  retained as the moderation-provenance axis and stays visible wherever that matters.
- **Verified**: `npx prettier --check .` clean; `npm test -- --no-watch`: **99 test files / 979 tests
  passed**; `npm run build` exit 0. New/changed specs: `link-occurred-at.util.spec.ts` (the two
  conversions, the midnight/hour boundaries, the pass-through-not-null case),
  `link-card.component.spec.ts` (display falls back, the second tooltip line appears only when the
  instants differ), `link-form.component.spec.ts` (submit sends the value, blank omits the key,
  edit round-trips it), `link-day-group.util.spec.ts`/`feed-day-groups.util.spec.ts` (buckets key on
  the event time), `incident-link-line.util.spec.ts`, `situasi-section.component.spec.ts`,
  `incident-card.component.spec.ts`, `link-status-input.util.spec.ts`, `date-range.util.spec.ts`.
- **Docs**: this entry + the monthly/yearly `SUMMARY.md` rows; `docs/components/insiden.md` (the
  field, the util, the card's two time axes, the form's tri-state) and `docs/components/home.md`

## insiden: shared pure utilities the `occurredAt` + thread wave introduced

Two Angular-free modules under `features/insiden/data/`, each with its own spec, each imported by
two features so their behaviour cannot drift:

- `link-occurred-at.util.ts` — `isoToOccurredAtInput` / `occurredAtInputToIso` (above). Contract:
  offset-free in and out, round-trips, and never silently turns a malformed value into `null` (which
  would be a timestamp reset).
- `link-thread-selection.util.ts` — `toggleSelection`, `areAllSelected`, `canGroup`,
  `selectedWithin`, `threadLabel`. Contract: every function is a **total, immutable** function of
  its arguments (no Angular, no signal, no RxJS) and returns a NEW array, because the results are
  written straight back into a signal — mutating in place yields the same reference, change detection
  never fires, and the checkbox silently stops updating. `areAllSelected` is false for an empty page
  (`[].every()` is vacuously true), `canGroup` is false below two **distinct** ids (a one-link thread
  is a no-op that still renders as a thread, and a duplicate id is a hard server rejection), and
  `threadLabel` returns `""` for an absent or `<= 1` size — the single place a link thread's
  pluralisation is decided **anywhere in the app**, so the console chip, the profile badge and the
  `app-link-thread` indicator cannot disagree. Consumers: the console triage table, "My Submitted
  Links", and the feed's thread wrapper. What differs between those callers is the **gate**, not the
  string: the table row and the profile badge sit on rows that may be plain unthreaded links and drop
  the chip on `""`, while the wrapper only renders its affordance when `threadLinks.length > 0`, so
  its minimum is 2 and the `""` branch is unreachable there. One helper serves both, and that is
  what keeps each site honest: the risk a future agent should watch is not one site adopting the
  other's helper, but a site "simplifying" its own copy of the string because the `""` branch
  happens to be unreachable there.
