## home/hero: the top edge is the status line, and the countdown moved onto the headline row

The Phase-0 **brand-orange accent rail is gone**. In its place the hero's top edge is a full-width
track whose fill is the fraction of the poll beat left, wearing the network's own tone; the `h1`
beside it wears the same tone as text. "Refreshing in Ns" moved out of the desktop-only bottom-right
`hidden justify-end lg:flex` corner into `hero-refresh-slot`, the **rightmost cell of the headline
row at every width** — "Refreshing in 12s" modifies the sentence above it, and the old gate hid the
control entirely at the mid widths.

1. **The tone is one pure rule, and the colour and the words cannot disagree.** New `NetworkTone` +
   `networkTone(total, needsAttentionCount)` in `data/network-summary.util.ts`, beside
   `summarizeNetwork` and derived from the SAME two counts the headline sentence is built from:
   `unknown` (no lines read) neutral, `normal` (0 needing attention) green, `degraded` (needs
   attention ≤ **half**) orange, `critical` (> half) red. Half is the CEILING of `degraded`, not the
   floor of `critical` — at exactly half most riders are still on working trains, and painting that
   the same alarm red as a broadly-down network trains readers to ignore red. Seven cases in
   `network-summary.util.spec.ts`, including `(16, 8)`, `(16, 9)` and `(4, 3)`. The shade choices stay
   in the component (`_headlineClass` / `_lineClass`, dark-mode aware) because which orange is a design
   decision, not a fact about the network — but the Tailwind strings are full literals so the compiler
   sees them.
2. **`hero-countdown-line` is drawn from `secondsRemaining()/intervalMs()`, never
   `percentRemaining`.** `refreshNow()` resets `secondsRemaining` immediately while `percentRemaining`
   only moves on the next 1s tick, so the latter lags a manual refresh by a second and would refuse to
   refill while claiming to be full. Both ends are clamped (paused → 100%, overshot → 0%); on the
   server `secondsRemaining` is `0`, so the SSR paint is a 0%-wide neutral line the client fills on
   first binding — the same swap the removed ring did, and the reason there is no hydration guard.
   `duration-1000 ease-linear` matches the tick and carries `motion-reduce:transition-none`.
3. **The hero card no longer clips.** `overflow-hidden` is gone from its `<section>` because the
   headline popover, the tile popovers and the menu panel are all positioned inside it and must escape.
   The two decorative edges round themselves instead: the countdown track `rounded-t-2xl`, the colour
   ribbon `rounded-b-2xl`, each keeping its own `overflow-hidden` to clip only its own fill/segments.
4. **`HomeStore` is injected for the beat alone.** The hero authors no request and starts no timer; it
   reads the same route-scoped store, in the same injector tree, that `HomeRefreshControlComponent`
   reads. Both specs that render the hero already mock `polling`.
5. **Default theme, not brand orange.** "Report a delay" (lost `bg-brand text-brand-foreground
hover:bg-brand/85`) and "Live map" (lost `text-brand`) now take the `hlmBtn` defaults.

## Round 2b · gradual refinement: the fill tweens again, and snaps only on reset

A second pass on entry 2 above, from the user watching the line move. **Why:** with the transition
removed, the fill stepped once per second and then jumped to full on a refresh — the user wants the
countdown to read **gradual (no stepping)** while still not "flowing" back up after a beat reset.

**What** (`hero/home-hero.component.ts` only):

- The width transition is back on the fill — `transition-[width] ease-linear` +
  `motion-reduce:transition-none` — so each once-per-second width write is interpolated across the
  next second: continuous movement while the beat counts down.
- A jump UP is still instant: `[style.transition-duration]="_snapToFull() ? '0s' : '1s'"` on the same
  span. `_snapToFull` is a signal seeded `true` (so the 0%-wide SSR paint fills without sweeping up
  over hydration), and a constructor `effect` re-derives it on every read of `secondsRemaining` by
  comparing against the previously observed value — `seconds > previous` (or a first read) means a
  (re)start (the beat's own reset, `refreshNow()`, a store resume) and renders at `0s`, i.e. snaps to
  full; a count-DOWN (`seconds <= previous`) gets the normal 1s tween.

🔴 **Supersedes entry 2 of Round 2b above** ("the countdown fill SNAPS — the width transition is
gone"): true when written, now **gradual with instant reset**. The concern that entry named (an
un-qualified tween makes every refresh read as a sweep back to full) is exactly what the
`_snapToFull` edge carries, so neither half of the reasoning is lost.

Evidence (live): width samples move ~5.5px per 150ms continuously while counting down; immediately
after a refresh click the fill reads 100% at `transition-duration: 0s`, and `1s` again on the next
tick.

## Round 2e (enhancements): the circle stays put, all three glyphs are 22×22, "Updated" acknowledges every clean settle, the tooltip says how stale, and the tone bar announces itself

**Why:** five things the user saw in the browser after round 2d. The pinned-right donut **moved**
once a second because the glyph sat BEFORE the label, whose own width changes ("30s" → "9s"); the
Updating spinner and the Updated check were still 14px `size-3.5` glyphs beside a 22px ring, so one
button wore three different widths; the "Updated" flash was **click-only and lasted 2000ms**, which
on a 30s beat means it was on screen one time in fifteen — long enough to read as a lingering status,
short enough that a reader who looked away missed it, and never there at all for the refresh a passive
reader actually watches; the tooltip could say when the NEXT refresh was but never how stale the
numbers already on screen were; and the hero's tone bar changed colour with no transition at all, so
a network recovering was as quiet as a network sitting still.

**What changed** (`src/` — `refresh-control/home-refresh-control.component.ts` and
`hero/home-hero.component.ts` + specs; no backend change, no other feature touched):

1. **Glyph AFTER the label.** The label `@if` chain is now the button's FIRST child, the one fixed
   `inline-flex size-7` slot second, the tooltip third. The button is `justify-end` inside the hero's
   `shrink-0` slot, so the circle is now pinned to the row's fixed right edge and the countdown text
   changes width under it.
2. **All three glyphs 22×22.** The ring was already the tracker's `CountdownRingComponent` geometry;
   the spinner was **rebuilt on that same 22-unit geometry** (`width`/`height="22"`,
   `viewBox="0 0 22 22"`, track circle cx/cy 11 r 9 `stroke-width 2.5 stroke-opacity 0.25`, arc
   `M20 11a9 9 0 0 0-9-9` round-capped, still `[animation:spin_1s_linear_infinite_reverse]` +
   `motion-reduce:[animation:none]`, still no inline `style`), and the check kept its 24-unit viewBox
   with an explicit 22×22 box (an svg preserves its aspect ratio, so only the box changes). Both lost
   `size-3.5` **on purpose**: a CSS size outranks the `width`/`height` ATTRIBUTES, which is exactly how
   the 14px glyph survived the round-2d slot. Row width is now constant across all three states.
3. **"Updated" after ANY clean settle, for 500ms.** `REFRESHED_VISIBLE_MS` 2000 → 500, and the
   click-arm is gone: `_refreshPending` + `_refreshStarted` collapsed into ONE `_sawRefresh` latch, set
   when a NON-pristine refresh is observed in flight and consumed on the settle edge (which keeps the
   deliberately conservative page-wide `hasError` suppression). So the 30s beat confirms itself —
   a reader who watched the row change is owed the same "Updated" a reader who clicked gets — and the
   short flash is what keeps a 30s cadence from being noise. The **pristine first load is still
   excluded from both states** (data that was never on screen cannot be stale), derived from the same
   `isLoading() || isLoadingLastWeek()`. Two behaviours fell out: a refresh going in flight CLEARS a
   visible "Updated" plus its timer (`_hideRefreshed`, so a confirmation cannot outlive the state it
   describes), and `ARM_EXPIRY_MS` is now purely the click-raised "Updating" guard — its own presence
   tells the effect not to tear that label down on an unrelated re-run, and it returns early when
   `_sawRefresh` is true so a slow request is never mistaken for a dropped click. `onRefreshClick()`
   is three lines: raise the label, arm the expiry, `refreshNow()`.
4. **Tooltip line two — `Last updated {age}`.** `_lastUpdatedAt` (epoch ms) stamped on every clean
   settle, rendered by a plain **method** (`_lastUpdatedLabel()`, not a `computed`, which would freeze
   the age at "just now" for as long as the tooltip was open): `—` until a fetch has ever completed,
   then `just now` (<5s) / `{n}s ago` (<60s) / `{n}m ago` (<60m) / `{n}h ago`, backwards clock clamped
   into "just now". 🔴 **Live-QA fix:** the pristine fetch often settles BEFORE the control's effect
   first runs (warm cache, local API, late hydration), so the tooltip read `—` until the first 30s beat
   on data that was seconds old; a `firstRun` closure flag now stamps at mount when the store is
   already idle (`!isRefreshing && !pristineInitialLoad && !hasError()`). `—` therefore only appears
   while a first load is genuinely in flight, and a FAILED first paint never stamps itself.
5. **Hero tone bar: 300ms fade + 5s glow.** The fill gained `transition-colors duration-300
motion-reduce:transition-none` (a class, not an inline style — the existing spec still pins
   `style.transitionDuration === ""`) and `motion-safe:animate-icon-glow` for **5s** after each tone
   change: two of the keyframe's 2.5s box-shadow pulses, ended by a `setTimeout` because the animation
   is `infinite` (`ngOnDestroy` clears it). Each tone class now carries BOTH `bg-*` and the matching
   `text-*`, since `icon-glow` paints its shadow in `currentColor`; `animate-breathe` is deliberately
   not used (its scale would breathe the full-width bar). An effect over `_tone()` remembers the
   previous tone: the first run glows only for a real tone (an `unknown` first read is an empty read,
   not a network event), every later run on any change.

**Evidence:** full suite **131 files / 1791 tests passed, 0 failed**, `npm run build` exit 0.
Live in the browser: on data arrival the fill's computed style read `animation-name: icon-glow` with
`transition-duration: 0.3s`, and the glow class was gone ~5s later with `bg-green-500` intact; the

1. **The draw-in.** Both strokes animate their **own** `stroke-dashoffset` from **their own** length to
   `0` over **500ms** — the track circle (`stroke-dasharray="56.55"`, the r=9 full turn, mirroring the
   component's `RING_CIRCUMFERENCE`) and the arc path (`"14.14"`, the quarter turn, which is exactly
   that path's length) — carrying `animate-spinner-draw-ring` / `animate-spinner-draw-arc`.
2. **The rotation waits.** The spin shorthand gained a **500ms delay**:
   `[animation:spin_1s_linear_500ms_infinite_reverse]` (duration still 1s, `reverse` still INSIDE the
   shorthand — the shorthand resets every animation sub-property, so a separate
   `[animation-direction:reverse]` would still be dead markup). The rotation therefore starts on a
   complete ring.
3. **Reduced motion keeps all THREE elements off** — the svg's `motion-reduce:[animation:none]` plus
   `motion-reduce:animate-none` on each stroke (the generated form of the same `animation: none`).
   Nothing sets a base `stroke-dashoffset`, so with the animations off the strokes fall back to the
   default `0`: the glyph renders **fully drawn, static, and honest**. All three stay classes, never
   inline styles — an inline animation outranks every class in the cascade, including the opt-out.

🔴 **Live-QA root cause + fix (the part worth remembering).** The first version put both `@keyframes` in
the refresh control's own `styles` array and referenced them with a Tailwind arbitrary-property
utility. It **silently did nothing**: Angular's emulated view encapsulation RENAMES `@keyframes`
declared on a component — `home-refresh-spinner-draw-ring` came out as
`_ngcontent-ng-cXXXX_home-refresh-spinner-draw-ring` — while the utility emits `animation-name` from
the **global** sheet, so the name matched no keyframes and the strokes sat at their default offset: a
finished circle, no entrance. The spec was green and the build was clean, because **jsdom computes no
styles** — the class strings were all correct while the animation was not. **Fix:** the keyframes and
their `--animate-spinner-draw-ring` / `--animate-spinner-draw-arc` tokens now live in the **global
`@theme`** in `src/styles.css`, applied as the generated `animate-*` utilities — the same pattern as
`--animate-icon-glow`, `--animate-breathe` and `--animate-tick-up` — and the component's `styles` array
is back to `[":host { display: inline-block; }"]`. Recorded in `MISTAKES.md`.

→ 31.37** and the arc's **14.14 → 7.84** over the first ~180ms, with a computed
`animation-delay: 0.5s` on the spin — the entrance fires, and the rotation begins on the complete ring.
