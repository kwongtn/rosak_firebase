Five fixes to the rider home board, all about saying less:

1. **"My lines" renders only when the reader has pinned lines.** The group's
   `@if (_mine().length > 0)` wraps the whole `<section>`, heading included, and the old empty-state
   paragraph (`line-board-mine-empty`, "Pin a line to keep it here.") is **deleted**. An empty pin list
   is a gap, not an invitation: a heading whose only content is "nothing is here" is noise on a board
   whose whole job is showing lines.
2. **Section dividers are per-section and conditional.** Each lower group still carries
   `border-t pt-4` on its own section, but only when a section actually precedes it:
   `_attentionRendered()` / `_mineRendered()` / `_allRendered()` mirror each group's own `@if` length
   predicate, and the bindings are `[class.border-t]` / `[class.pt-4]` rather than static tokens. The
   **first visible group** under the controls row draws neither — the controls row's own `border-b` is
   the only line there, and a second divider would have doubled it. With My lines hidden, All lines is
   still the second visible group and keeps its divider when it follows attention. The attention group
   never carries the pair: it is always the first section rendered.
3. **Both pins explain themselves.** The card's `line-card-pin` and the row's `line-row-pin` become the
   trigger of an `app-info-popover` (`showIcon=false` / `showMethodologyLink=false`, panel testids
   `line-card-pin-popover` / `line-row-pin-popover`). Final mechanism: the button is passed as the
   popover's `[triggerTpl]` (declared in a sibling `<ng-template #cardPinTpl>` / `#rowPinTpl>`), so the
   popover renders no button of its own and the interactive control is never nested inside another
   button (the intermediate `ng-content`-in-`ng-template` attempt rendered empty in the real app — see
   `MISTAKES.md`). The tooltip title travels with the
   state — "Click to pin" / "Click to unpin" — and the body says what pinning does and how to undo it
   ("Pin this line to keep it in My lines at the top of the board." / "Unpin this line to return it to
   its regular group on the board."). The fill-when-pinned glyph, `aria-pressed` and action-naming
   `aria-label` are unchanged.
4. **The confidence and passenger chips are Active-only.** On the card (`line-card-confidence` +
   `passenger-status`) and the row (`line-row-confidence` + `line-row-passenger`) both chips now render
   inside `@if (line().status === "ACTIVE")`. A non-Active status badge already carries the line's
   story, so "Unconfirmed (0 reports)" / "No data" beside "Partial Disruption" is noise rather than a
   qualification. The pure `statusConfidence` rule is untouched — a `PARTIAL_DISRUPTION` line with no
   reports still resolves to `unconfirmed`, the chip simply is not drawn where the badge says the same
   thing. This is a rendering rule, not a change to `status-confidence.*`; the methodology registry was
   deliberately **not** touched (same precedent as round 3's heat-grid note).
5. **The row's fleet count reuses the card's chip.** `line-row-vehicles` is wrapped in the same
   `app-status-info-chip` the card's `line-vehicle-count` uses, with an `aria-label` of "N of M vehicles
   in service". The card's two private computeds were lifted into `data/status-info.util.ts` as
   `vehicleCountInfo()` (the registry definition, read at call time so chip and `/methodology` cannot
   drift) and `vehicleBreakdownRows()` (the non-zero per-status rows in enum order, closed by a derived
   `Total`), and the card now calls them too — so "12/16 in service" is explained one way on every board
   surface. The row's meta strip therefore carries two popovers, which is why the report walkthrough's
   specs now scope to the reports element rather than to `line-row-meta`.

**Specs** updated/extended: `status-info.util.spec.ts` (the lifted helpers and their empty-counts case),
`network-board.component.spec.ts` (My lines absent when nothing is pinned; the four appear/disappear
cases for the conditional divider on the first vs a later visible group),
`line-pulse-card.component.spec.ts` (card pin tooltip opens/flips with state; confidence + passenger

## Home tooltip concision + `InfoPopover` viewport clamp

Findings in `.omo/notepads/homepage-tooltip-concision/learnings.md` and the round's open
issues in `.omo/notepads/homepage-tooltip-concision/issues.md`. Frontend-only: no GraphQL
document, no backend change, no new dependency.

1. **The registry grew a tooltip tier.** `MetricDoc` gained an optional `summary` — a
   tooltip-sized precis of `definition`, carrying the same `{{TOKENS}}`. New
   `metricTooltip(id)` returns `summary ?? definition` and still goes through `metricDoc()`,
   so an unknown id throws before any copy is produced. The eight long `network.*` metrics
   (`lines-normal`, `needs-attention`, `reports-now`, `activity-sparkline`,
   `line-reports-summary`, `heat-strip`, `report-ranking`, `has-data`) got summaries; their
   `definition` strings are **untouched, byte-for-byte**, and `/methodology` still renders the
   full text. Because both tiers live on one registry entry, the page and the popover can
   never disagree about the rule. Six home consumers switched from
   `renderMethodologyCopy(metricDoc(...).definition)` to `metricTooltip(...)`.
   `lastReviewed` for the eight metrics and the owning `line-status` section is bumped through
   the new `REVIEWED_AT_TOOLTIP_CONCISION = "2026-10-07"` constant — a **separate** date
   because this review asked a different question (is the published rule short enough to read
   in a tooltip?), and folding it into an earlier constant would let either bump silently
   claim the other. The two registry specs pin it: every `summary` renders with no unresolved
   `{{` and is strictly shorter than its `definition`.
2. **The panel is now clamped to the viewport.** An `InfoPopover` panel is
   `position: absolute` with a static `left-0` / `right-0` / `left-1/2` anchor, so a panel on
   a right-edge trigger — the board rows' pins and chips, the Pro header chips — ran past the
   viewport edge and was silently cut by `html, body { overflow-x: clip }`; the panel's
   `max-w-[calc(100vw-2rem)]` capped its size, never its position, and no collision handling
   existed. The panel is measured **once per open** (a `viewChild` + a browser-only `effect`,
   no scroll/resize listeners) and nudged back inside by an 8px margin: the correction is
   written as a `margin` on the side `align` owns (`margin-right` for `align="end"`, else
   `margin-left`) so it composes with `align`'s `-translate-x-1/2` instead of fighting it, and
   both edges are clamped together so a right-edge pull cannot push the left edge back out.
   When the panel would overhang the bottom **and** a full flipped copy fits above the
   trigger, it renders `bottom-full mb-1.5` instead of `top-full mt-1.5`. The effect measures
   the unshifted rect and never reads its own correction back, so it cannot ping-pong. This is
   distinct from the 2026-10-05 ancestor-`overflow-hidden` clip recorded in `MISTAKES.md`:
   that was an ancestor mid-card, this is the viewport edge.
3. **Two silent Angular binding-grammar no-ops, found while implementing the clamp.** (a)
   `[class.mt-1.5]` binds the class `mt-1` — the class-binding name grammar stops at the first
   dot, so the fractional gap was silently dropped (the DOM showed `mt-1`). (b) A style-map key
   `"margin-left.px"` is applied nowhere — map-hop `[style]` keys are property names verbatim,
   so the `.px` names no property and the `style` attribute stayed `null` (units belong in the
   **value**, or use the single-property `[style.margin-left.px]` binding). Both are worked
   around: the panel's full class list and its correction are single computed strings
   (`_panelClasses()` / `_shiftStyles()`), and `info-popover.spec.ts` grew specs that read the
   **rendered** `classList` / `style` attribute.
4. **The clamp — and the summary tier — are pinned in a real browser.** Two tests added to
   `e2e/home.spec.ts`: `VISITOR: clamps a right-edge popover into the viewport` (1000×800;
   asserts the clamp-relevance predicate first — the rightmost trigger's unclamped `left-0`
   panel would exceed `innerWidth - 8` — then that the opened panel's box stays inside;
   measured live: trigger x=784.03, panel right lands exactly at 992.03 = 1000 − 8) and
   `VISITOR: the hero tooltip carries the short summary, not the full definition`. jsdom
   computes no layout, so this class of bug is invisible to the unit suite. Screenshot
   evidence: `.omo/evidence/visual-qa/2026-10-07-home-tooltip-viewport-clamp.png`.

🔴 **Five older home e2e tests remain red for pre-existing reasons, deliberately unaddressed
this round** (the working tree was frozen for close-out; CI does not run Playwright): the
feed mock is variable-agnostic, so the same stub is served to the Today and Last Week panels
and unscoped `app-link-card` locators hit strict-mode violations; and commit `2883604` made
KJL a compact `app-line-pulse-row` while those tests still query `app-line-pulse-card`. Both
proven pre-existing by stashing the whole tree and running the fresh HEAD bundle
(`e2e/home.spec.ts:209`, the pre-change line). Tracked with a fix sketch in
`.omo/notepads/homepage-tooltip-concision/issues.md`.

## Shared Vitest setup for jsdom polyfills (agent-friction Task 2)

Inventory + compatibility audit first. jsdom ships **no** `matchMedia`, `ResizeObserver`,
