# 2026-10-03

## home: the network board, Phase 0 — foundations and quick wins

The plan is a five-phase rebuild of `/` as a live network board. Phase 0 lays the groundwork every
later phase reads — reader preferences, a URL-state seam, a pure summary rule, a hero, a real action
hierarchy on the card, and a board ordered worst-first — **without adding a single network read**.

1. **`PreferencesService` (`core/preferences/preferences.service.ts`).** Reader-owned display state
   (`pinnedLineIds`, `viewMode`, `density`, `lastReportedLineId`, `recentLineIds`) under the
   **versioned** key `rosak:preferences:v1`. API: `isPinned` / `togglePin` / `setViewMode` /
   `setDensity` / `setLastReportedLine` / `pushRecentLine` (deduped, capped at 5) / `reset()` /
   `snapshot()` / `hydrated()`. 🔴 **The constructor never reads storage.** It builds on the defaults
   and hydrates in `afterNextRender`, which does not run on the server — a constructor read would make
   the client's first paint disagree with the server's HTML and throw an `NG0500` hydration mismatch
   for any rider who had pinned anything. The persist `effect` is gated on `hydrated()` for the
   mirror-image reason: an ungated effect fires on its first run, BEFORE the read, and would overwrite
   real preferences with the defaults they are about to inherit. Every stored field validates
   **independently**, because a half-recognisable payload (an older deploy wrote fewer keys) is the
   common case, not an edge case — dropping the whole object would silently unpin a rider's lines
   because one unrelated key changed shape.
2. **`query-param.util.ts` (`core/url-state/`).** The read/write seam for URL-owned view state
   (`?view=`, `?sort=`, `?line=`, `?q=`), split exactly like `line-overview.page.ts`'s existing pattern:
   pure parsing over a `ParamMap`-shaped record (`parseEnumQueryParam`, `parseTextQueryParam`,
   `readEnumQueryParam`, `readTextQueryParam`), plus one browser-gated `navigate()`
   (`writeQueryParams`). Two rules callers now inherit instead of re-deriving: **a default value never
   appears in the URL** (`queryParamForWrite` → `null`) and **writes merge and replace, never push**.
   `isBrowser` is a parameter because reading `PLATFORM_ID` needs an injection context a plain
   function should not have — and because a _reactive_ `navigate()` during SSR hangs the render.
3. **`network-summary.util.ts`.** The board's whole rule, pure and total: `LINE_STATUS_SEVERITY_RANK`,
   `NEEDS_ATTENTION_PASSENGER_RANK`, `lineNeedsAttention`, `compareLineSeverity`,
   `sortLinesBySeverity`, `summarizeNetwork`, `networkHeadline`, `lineCallout`. Two decisions worth
   recording. First, the operational order is a **total order, not the backend enum's**:
   `TOTAL_DISRUPTION` 6 > `PARTIAL_DISRUPTION` 5 > `PARTIAL_ACTIVE` 4 > `DEFUNCT` 3 > `TESTING` 2 >
   `ACTIVE` 0 — DEFUNCT and TESTING are settled, un-actionable facts and must not outrank a line that
   is only partly running. Second, the passenger threshold is `DELAYED` (5), **not** `CROWDED`:
   crowding describes one carriage rather than the service, and counting it would leave the headline
   reading "0 of 16 lines running normally" on any busy evening. `PASSENGER_SEVERITY_RANK` (added to
   `passenger-status.util.ts`) mirrors the backend `PassengerStatus` enum order — the schema exposes
   the enum in declaration order, so a higher rank IS a more severe status, and the numbers are the
   server's order made numeric rather than an editorial layer on top of it.
4. **`app-home-hero`.** A full-width strip ABOVE the `home-panels` grid (the headline and tiles
   describe both columns, so a one-column hero would make half the summary lie): plain-language
   headline + an `app-info-popover` reading `metricDoc("network.lines-normal")`, the worst-line
   callout, four stat tiles, and an intent-based CTA row — Report a delay · Spot a train · Share a
   link · Live map. It **reads nothing**: `lines` / `linksToday` are bound from `store.lines()` and
   `store.feedTotalCount()`, both already in flight. "Report a delay" emits `reportDelay`, which the
   page answers by scrolling to the board; the chooser belongs to the board, not to a summary strip.
5. **Card CTA hierarchy + menu.** Two buttons, one primary and one secondary: **Report status**
   (`submit-line-status`) and **Log spotting** (`add-spotting-entry`) — same testids, de-jargoned
   copy. Pin and the two Line HQ links moved into a kebab (`line-card-menu` →
   `line-card-menu-panel`, items `line-card-pin` / `line-card-hq` / `line-card-hq-details`), closing
   on Escape / outside click / item choice. `src/app/ui/` has no dropdown primitive to reuse, so the
   menu is inline against the contract `app-info-popover` already established. The card also draws the
   line's `displayColor` as a leading accent rail and records the line into
   `PreferencesService.recentLineIds` on the expanded panel's open edge.
6. **The board is now ONE worst-first list.** The ACTIVE-first partition with a collapsed
   "Other lines" `<details>` is **gone** (testids `other-lines` / `other-lines-summary` retired). It
   had the right instinct — a degraded line must not read as routine — and the wrong mechanism: the
   page's own hero would say "3 lines need attention" above a column of lines that are fine, and the
   fold also inverted the priority it was meant to protect (a rider scanning for a problem read the
   healthy majority first). Rows are `sortLinesBySeverity(lines())` under a
   `line-board-attention-heading` caption counting with the hero's OWN predicate, so the caption, the
   hero tile and the row order cannot disagree.
7. **Smaller things.** The `""` route gained `title: "MLPTF | Live Network Board"` (the one route
   without a title) and `HomePage` sets the `<meta name="description">` through `Meta.updateTag`, so
   it lands in the SSR HTML. The `feed-empty` block became an invitation — "No links yet today — be
   the first" plus a `feed-empty-cta` that opens the same shared sheet the hero's "Share a link" does,
   because the old copy stated a fact and left the reader to work out what to do about it, which is
   how a page whose job is community reports ends up reporting nothing.
8. **Methodology registry.** Three `MetricDoc`s (`network.lines-normal`, `network.needs-attention`,
   `network.severity-order`) plus the `NEEDS_ATTENTION_PASSENGER_RANK` constant, with the `line-status`
   section's `lastReviewed` bumped to 2026-10-03. The hero surfaces the headline metric through the
   popover, so the number in the tile and the sentence on `/methodology` cannot drift.
9. **`--brand`.** Brand orange (`#ee7104`) as an **accent only** — never an action control's fill
   (`--primary` stays the blue). Added to `:root` and `:root.dark` and mapped through
   `@theme inline { --color-brand: var(--brand) }`, so `bg-brand` compiles to `var(--brand)` and the
   dark override is picked up with no `dark:` utility to drift. The hero's rail and its primary CTA are
   the only surfaces using it today.
10. **`@ng-icons/lucide` works on Angular 22** (installed v34, peer `@angular/core >=21`). This is
    the library's first usage in `src/` — `NgIcon` + `provideIcons({ lucideEllipsisVertical,
lucidePin, lucideExternalLink })` builds, tests and SSR-bundles clean, so **no inline-SVG
    fallback was needed**. The existing chevron SVGs are untouched.

- **Verified**: `npx prettier --check .` clean; `npm test -- --no-watch` — **112 files / 1362 tests
  passed, 0 failed** (baseline before this change on this branch: 108 / 1280; the +82 being
  `preferences.service.spec.ts` (14), `network-summary.util.spec.ts` (28), `query-param.util.spec.ts`
  (17), `home-hero.component.spec.ts` (9) and the rewritten/extended home specs); `npm run build`
  exit 0, initial total 349.19 kB (the `spotting-grid` CSS-syntax warning and the ESM-import
  warnings are pre-existing). New specs: `preferences.service.spec.ts` (corrupt JSON → defaults, a
  non-object payload → defaults, per-field validation with the recognised fields surviving, dedupe of
  blank/duplicate ids, persist-then-reload, the recents cap, and — the load-bearing one — a
  `PLATFORM_ID: "server"` run that spies on `Storage.prototype` and asserts **neither** `getItem` nor
  `setItem` is ever called, plus the reverse guard that hydration never lets the defaults overwrite a
  stored payload); `query-param.util.spec.ts`; `network-summary.util.spec.ts` (including that the
  registry's published threshold renders to the same number the code compares with, and that a
  missing `statusReportCount` sums to 0 rather than `NaN`); `home-hero.component.spec.ts` (including
  that the popover's panel text IS `renderMethodologyCopy(metricDoc(...).definition)`).
- **Known limits (deliberate, Phase 0)**: the board still renders every line (no filter, no grouping);
  the report chooser does not exist — "Report a delay" only scrolls; `viewMode` / `density` /
  `lastReportedLineId` / `recentLineIds` are persisted but not yet read by any surface (Phase 1+);
  and `query-param.util.ts` has no caller yet — it ships as the seam the URL-state phases bind to.

## Network board — Phase 1 (groups, compact rows, rider/pro toggle)

Phase 0 gave the front page the numbers and the vocabulary. Phase 1 turns the one worst-first list
into the board the plan describes, and answers the three questions the hero alone could not: _which
lines are mine, how much should I trust this, and where is it happening._

### What shipped

1. **The board's derived views moved onto `HomeStore`** (`data/home.store.ts`) — `networkSummary`
   (`summarizeNetwork` over the single lines read), `attentionLines`, `myLines`, `allLines`, and a
   `boardSort` signal (`"severity" | "name"`) with `setBoardSort()`. **Zero new reads**: every view is
   a `computed()` over `lines()` plus `PreferencesService.pinnedLineIds()` (injected, root-provided, so
   it deliberately outlives the route-scoped store). The rule lives here, not in a template, because a
   rule that only exists in markup cannot be tested without a DOM or reasoned about by a reader.
2. 🔴 **The three groups are a PARTITION — every line in exactly one.** One decision, applied in one
   order: **attention membership always wins**, so a _pinned-but-broken_ line sits in "Needs
   attention" and NOT also under "My lines". Pinning says "I care about this line", not "hide a broken
   one further down", and printing a dead line twice would be worse than the group it gives up. Each
   group subtracts the ids the previous one claimed rather than re-deriving its own predicate — three
   independently-written filters is exactly how a line ends up in two groups or in none.
   `attentionLines`/`myLines` are always severity-sorted; only `allLines` follows `boardSort`
   (severity, or `code` via `localeCompare`, so `K10` does not sort before `K2`).
3. **`app-network-board` REPLACES `app-line-pulse-list`** (component and spec **deleted** — it was one
   worst-first list, which is the shape the board replaces). Structure: `line-skeleton` rows while the
   FIRST read is in flight and there is nothing to show, the dashed `line-board-empty`, then
   `board-controls` and three groups — `Needs attention · N` (full `app-line-pulse-card`s, **hidden
   when empty**, `line-board-attention-heading` testid kept from the old list), `My lines` (compact
   rows, or the invitation `line-board-mine-empty` "Pin a line to keep it here."), `All lines`. Every
   row keeps the `line-board-row` wrapper. It takes **no inputs**: it injects `HomeStore`, the way
   `app-home-refresh-control` injects the store's beat.
4. **`app-line-pulse-row`** — the compact row: backend-hex colour rail, `code · name`,
   `line-row-status` (non-ACTIVE lines only — "Active" is the unremarkable default),
   `line-row-confidence`, `line-row-passenger`, `line-row-vehicles`, `line-row-reports`, a
   `line-row-pin` toggle (`aria-pressed`) and `line-row-report` (which calls
   `LineStatusSheetService.openFor(line.id)` — the full "which line?" chooser is Phase 2, so this is
   exactly as honest as the card's). `line-row-toggle` (`aria-expanded`) opens `line-row-expanded`,
   which reuses the SAME lazy chart + reports the card shows. **Pro view adds `line-row-pro`**:
   "N reports · 15 min window" (a bare count is what a pro reader over-reads; the window makes it
   interpretable) plus both Line HQ links. Density changes padding and NOTHING else.
5. **Controls row** — three labelled `role="group"` segmented controls with `aria-pressed`:
   `board-sort-*`, `board-view-*`, and a **pro-only** `board-density-*`.
6. 🔴 **URL state** through `core/url-state/query-param.util`. Read half: `toSignal(route.queryParamMap,
{ initialValue: route.snapshot.queryParamMap })`, so the server render reads the server's URL.
   `readTextQueryParam` distinguishes absent from unrecognised and `readEnumQueryParam` narrows it, so
   `?view=wizard` degrades to the shared DEFAULT (a URL is user input). Effective value = **URL when
   present, else the stored state**, which is what makes `?view=pro` shareable while a returning Pro
   reader still gets Pro without one. Write half: ONE browser-gated `effect` through
   `writeQueryParams`, **guarded on the URL already saying the same thing** — without that guard a
   browser back/forward immediately re-navigates onto the parameters it just left. Defaults are
   written `null`, so "no query params" and "the default view" are one state. **Density is
   preference-only.** Two further effects push a deep link down into the durable state, because
   `signal.set` with an equal value does not notify and so they never fight a toggle.
7. **Confidence semantics** (`data/status-confidence.util.ts`, pure + spec-covered) — four levels,
   **first match wins**, and the ORDER is the design: `official` (any `isAutomated` pulse link,
   checked FIRST so a 40-rider tally cannot outrank the operator) → `none` ("No recent reports") →
   `confirmed` (`statusReportCount >= CONFIRMED_MIN_REPORTS` = 3) → `unconfirmed`
   ("Unconfirmed (N reports)"). Evidence = a report in the line's own window OR a rider status above
   `NORMAL` OR a non-`ACTIVE` operational status — so an operator-declared disruption with no rider
   reports is honestly "Unconfirmed (0 reports)", while `passengerStatus: "NORMAL"` is NOT evidence
   (it is the derived "nothing notable" reading; treating it as one would put a green chip on a line
   nobody reported). `hasOfficialPulseLink` tests `=== true`, never truthiness. The chip renders on
   BOTH row elements, next to the status it qualifies, and its popover reads the resolved level's OWN
   registry entry (`status-confidence.official|confirmed|unconfirmed|none`) — never a literal.
8. **Backend, additively**: `isAutomated` added to `FRONT_PAGE_LINES_QUERY`'s `pulseLinks` selection
   and to `LinePulseLink`. The field already existed on `SocialMediaLinkScalar`, so this is a
   selection change, not a schema change; `home.queries.spec.ts` now pins it (a fixture can invent any
   field it likes — only the document knows what the server was asked for). **No other read changed**
   and the six-read `HOME_FEED_COLLAPSE_VARS` invariant is untouched.
9. **Per-station strip** (`station-strip` + `station-strip-count`) inside the expanded report list:
   the rows the reader has ALREADY loaded, tallied by `station.displayName`, busiest first, hidden when
   there is no station data. No request, no new fields — it answers WHERE, which the list cannot at a
   glance. 🔴 v1 counts only the loaded pages (first page of ten), so it is "where, among the reports
   you can see", never a total; completing it needs an additive backend aggregate over the
   status-report table, deliberately NOT taken because this phase ships zero new reads and a
   client-side total over a truncated page would be a lie the reader cannot detect.
10. **Hero finishing** — the network's own colours as a decorative `aria-hidden` bottom ribbon
    (`hero-ribbon`, a blank colour is DROPPED so a line without one leaves no hole); the
    **official-update callout** (`hero-official-callout` / `-badge` / `-link`) rendered **above** the
    disruption callout when — and only when — the same worst line `summarizeNetwork` names has an
    `isAutomated` post, linking the ORIGINAL with `target="_blank" rel="noopener noreferrer"` and the
    words "Open original"; and the **desktop `app-home-refresh-control` instance moved into the hero**
    (still `hidden lg:flex`, mobile copy unchanged), so the live indicator sits above the fold on every
    layout. 🔴 Only the WRAPPER moved — a second copy of the countdown/Updating/Updated state machine
    there would double every confirmation and desync the two from the one beat they share.
11. **`home.page.ts`** — `app-line-pulse-list` → `app-network-board`, the line-section refresh instance
    dropped (it is in the hero now), everything else intact. **No feed tabs** (later phase).
12. **Methodology registry** — four new `MetricDoc`s (`status-confidence.official` /
    `.confirmed` / `.unconfirmed` / `.none`, `sectionId: "line-status"`, `lastReviewed: 2026-10-03`) plus
    `METHODOLOGY_CONSTANTS.CONFIRMED_MIN_REPORTS` (`{ value: 3, source: "LINE_STATUS_DERIVE.md" }`).
    The owning `line-status` section's `lastReviewed` is bumped to `2026-10-03`. ⚠️
    `methodology-render.util.spec.ts` pinned `Object.keys(METHODOLOGY_CONSTANTS)` to exactly two
    entries — it now pins three, with a reason for each.

### Acceptance specs

- **(a) A disrupted/passenger-degraded line renders ABOVE an active one regardless of backend order** —
  `network-board.component.spec.ts`, over a fixture whose backend order is deliberately hostile
  (healthy first, broken last).
- **(b) A pin persists across reload and causes NO SSR hydration mismatch** — two halves.
  Persistence: `home.store.spec.ts` seeds the service's own storage key so `myLines` reads the pin
  _through the same `afterNextRender` hydration the page does_, and
  `network-board.component.spec.ts` re-derives the group from it. Hydration:
  `line-pulse-row.component.spec.ts` pins the ORDER — the service reports defaults and
  `hydrated() === false` before the render pass (which is what the server sees, because
  `afterNextRender` never runs there), and the stored pin only afterwards.
- **(c) Each line appears in exactly one group** — asserted twice: `home.store.spec.ts` (as the
  partition identity over an `it.each` of empty / all-healthy / all-broken / mixed inputs) and
  `network-board.component.spec.ts` + `home.page.spec.ts` (on screen, counted from the row wrappers
  across all three groups, with a pinned-but-broken line and a pin for a line this read does not
  contain).

## Network board — Phase 2 (report chooser, draft-first sheet, success feedback)

Phases 0 and 1 made the network legible. Phase 2 makes it **reportable from a phone** — one chooser for
every intent, a form that does not punish a logged-out reader, and visible confirmation that the report
landed on the line it was about.

### What shipped

1. **`app-report-chooser` + `ReportChooserService`** (`features/home/report/`) — the front page's ONE
   submission surface. Five intent tiles (amendment §12 #4: **Delay / crowding · Stopped · Spot a
   train · Share a link · Report an incident**) and, for the three line-based intents, a line picker.
   Root-provided service (`isOpen` + `intent`), mirroring `LinkSheetService`; `intent` is cleared by
   `open()` and by every close, so a stale trigger can never resurrect a half-finished "which line?".
2. 🔴 **Every tile dispatches to a sheet that already exists; nothing is invented.** Delay →
   `LineStatusSheetService.openFor(id)` with **no** preset ("Delay / crowding" is two conditions and
   only the reader knows which); Stopped → the same sheet with
   `openFor(id, { presetStatus: "DISRUPTED" })`, i.e. the rider's word mapped onto the **existing**
   PassengerStatus rather than a ninth value; Spot → `ReportSheetService.openFor(id)`; Share a link →
   `LinkSheetService.open()`; Incident → `IncidentSheetService.open()` **then**
   `router.navigate(["/insiden"])` — that sheet is hosted by `/insiden`, so opening it first (its
   service is root-provided) is what makes it already open on arrival. Every line-based choice also
   calls `PreferencesService.pushRecentLine(id)` and the chooser closes after dispatching in all five
   cases.
3. **The picker's order IS the prefill**: `report-chooser-order.util.ts` (pure, spec-covered) sorts
   **pinned → recent → severity**, with the board's own comparator as the tiebreak inside every band.
   Pinned outranks recent deliberately — "I care about this line" is a standing statement the reader
   can correct by unpinning, while recency is an artefact of scrolling. It reads
   `HomeStore.lines()`, so the chooser adds **zero requests**. A filter box (`chooser-line-filter`)
   narrows on code/name fragments and never reorders what survives; with no lines loaded the three
   line intents are disabled with `chooser-no-lines`/`chooser-empty-lines` and the other two still work.
4. 🔴 **Draft-first `line-status-sheet`.** The form AND its footer render logged out; the only addition
   is a banner above the form ("You'll need to log in before submitting, but feel free to fill in the
   details first." + `login-button`) — wording deliberately identical to the spotting report form's.
   The account is asked for at exactly ONE place, `submit()`, which writes the message inline
   (`line-status-submit-error`, `role="alert"`, above the footer so it survives a missed toast) and
   toasts. The draft is discarded on exactly ONE edge (open→closed), so the login popup cannot cost
   the reader their typing — asserted end-to-end (fill logged out → submit → login → submit, and the
   second request carries the same notes/status). One `effect` handles both sheet edges (consume a
   `presetStatus` on open, `clear()` on close) so the seed and the reset cannot race the same
   `_wasOpen` latch. On success it records `setLastReportedLine(id)` + `pushRecentLine(id)`.
5. **Success feedback — back to the line.** `HomeStore.highlightLine(lineId)` sets
   `highlightedLineId` and arms a 2000 ms timer (the same window as the refresh control's "Updated");
   `ngOnDestroy` cancels it. 🔴 The signal lives in the STORE because the board takes **no inputs** —
   giving it one would mean re-deriving on the page what it already owns. Every board row wrapper (all
   three groups) now carries a stable `id="line-<id>"` plus `scroll-mt-24`, and the board draws the
   ring (`ring-2 ring-brand ring-offset-2 ring-offset-background` + a `data-highlighted` marker) and
   scrolls that anchor into view from a browser-gated `effect` (`block: "center"`). Reduced motion
   drops the TRANSITION (`motion-reduce:transition-none`), never the ring — the information has to
   survive, only the flourish goes. The page reads the line id from
   `LineStatusSheetService.lineId` (which survives the close, so `submitted` stays payload-free); for
   spotting it comes from a new payload: `ReportFormComponent.submitted: output<string | null>()`,
   read before the form's own `clear()` — the form consumes its one-shot seed, so the service has
   nothing left to hand the host.
6. 🔴 **Mobile action bar, one refresh control.** The sticky `home-mobile-bar` (`lg:hidden`,
   `pb-[env(safe-area-inset-bottom)]`) hosts **Report** (the chooser), **Refresh**
   (`store.polling.refreshNow()` — the SAME call the countdown's click makes, so there is one beat and
   two affordances) and **Live map** (a `/tracker` link, so the hero row's fourth CTA is not the one
   thing mobile loses). `main` grew `pb-24 lg:pb-6` so the bar never covers the last feed row. The
   mobile feed-column `app-home-refresh-control` copy was **removed**: two controls on one phone was
   one too many, and the bar is the only place a reader scrolled to the bottom can reach Report at
   all. `line-refresh-countdown` is therefore no longer a duplicated testid.
7. **Hero wiring.** `reportDelay` (the output) and `HomePage.scrollToLineBoard()` (the scroll wiring)
   are **gone**, with no dead code left behind: "Report a delay" now calls `ReportChooserService.open()`
   like the bar's Report does. The CTA named an intent and the reader is on a platform without the
   board's line list in front of them — scrolling them somewhere to hunt for a row answered a question
   they did not ask.
8. 🔴 **Sheet mount ORDER is load-bearing.** `HlmSheet` locks page scroll from an effect on its own
   `open()`, and Angular flushes effects in creation order — so the chooser (which OPENS other sheets)
   must be created BEFORE them, or its close (unlock) runs after the target's open (lock) and leaves a

## Network board — Phase 3 (service-day history widgets + the feed line filter)

The backend half shipped first (`rosak_backend` `cb60769`: `networkStatusHistory` and
`linesStatusHistory`, both public, both bucketed through the existing `bucket_hourly`). This phase
gives the front page three ways to draw those 24 service-day hours, plumbs the feed's line filter
through every feed variable, and pins the two rules that make it safe to add charts to a page that
already works.

### What shipped

1. **Two documents in `home.queries.ts`** — `NETWORK_STATUS_HISTORY_QUERY`
   (`networkStatusHistory(dayStartHour)`) and `LINES_STATUS_HISTORY_QUERY`
   (`linesStatusHistory(lineIds)`), with `NetworkStatusHistoryQueryVars/Data`,
   `LinesStatusHistoryQueryVars/Data` and the `LineStatusHistory` interface. Both select the same
   `LineStatusHourBucket` fields the existing `LINE_STATUS_HISTORY_QUERY` already did.
   🔴 **`dayStartHour` is declared and passed but deliberately NEVER sent**, so the backend's own
   default of 3 (the 03:00→02:00 community service day) applies — the same rule the last-week window
   follows, for the same reason: a client clock or a computed date in query variables makes the server
   render and the client hydration disagree, and `retainDataIfEqual` / TransferState then refetch
   instead of reusing the payload. A declared-but-unused GraphQL variable is a validation error, so
   the variable has to exist to be left unset.
2. **`status-history-display.util.ts`** (pure, 28 tests) — the ONE vocabulary the three widgets share:
   MYT hour labels, the pluralised report phrase, the per-series bar scale with a visible floor, the
   breakdown/title builders, `historySummaryLabel` (the single sentence each widget hands its
   `role="img"`), and the heat grid's two dimensions. 🔴 `HEAT_INTENSITY_CLASSES` is a list of
   **literal** Tailwind utilities, not `opacity-${n}`: Tailwind v4 compiles only what it finds as
   literal text in the source, so an interpolated class is never emitted. Verified in the built CSS.
3. **`PASSENGER_BAR_CLASS` / `passengerBarClass()`** promoted into `passenger-status.util.ts` and the
   expanded card's chart pointed at it. Three widgets now share one palette instead of three near-copies
   — a "Delayed hour" cannot be amber in one widget and yellow in another. Deliberately NOT merged
   with the badge-variant table: a badge is a tinted chip with a label beside it, a bar is a fill with
   nothing beside it.
4. **Three widgets.**
   - `hero/network-sparkline.component.ts` — 24 bars in the hero, tall by how many reports the WHOLE
     network received in that hour, coloured by the dominant status. Reads
     `HomeStore.networkHistory()`; adds no request of its own.
   - `line-pulse/line-history-strip.component.ts` — the compact row's own 24-cell strip, drawn **above**
     the disclosure and served by the store's single `linesStatusHistory` read, so sixteen rows cost one
     request rather than sixteen. Scaled to **its own line's** busiest hour, so a quiet line next to a
     busy one looks quiet.
   - `pro/network-heat-strip.component.ts` — the Pro grid: lines × hours, colour = the dominant status,
     opacity = the report volume relative to the busiest cell on screen. Mounted by
     `NetworkBoardComponent` **only** when the effective view is `pro`. Hand-rolled divs; no charting
     dependency.
5. 🔴 **Widget-level failure isolation (the phase's acceptance rule).** Both history resources stay out
   of `hasError`, `isLoading`, `isLoadingLastWeek` and `isRefreshing`, because those four drive the
   page-level retry banner, the board skeleton and the refresh control's "Updating" label — folding a
   decorative chart into them would replace a working page of statuses with one banner. Each widget
   reads its OWN `networkHistoryFailed` / `linesHistoryFailed` and hides entirely; an **empty** answer
   hides it too, because `[]` is the backend's "nothing reported this service day", not an error.
   `home.store.spec.ts` fails both history reads and asserts all four flags stay `false`.
6. 🔴 **The reads are lazy AND widget-opted-in.** `HomeStore.requestHistoryReads()` opens the gate and
   each widget calls it in its own constructor. This is not tidiness: `graphqlResource` installs an
   effect that reads the underlying `httpResource`, so a gate only the projections satisfied would not
   defer the request at all. One explicit call from the surface that renders the answer is the only
   honest gate — and it is what keeps a Rider board (no heat grid) and every feed-focused store spec
   from issuing two extra requests. `linesStatusHistory`'s id list is capped at
   `HISTORY_LINE_ID_CAP = 64`, the backend's own limit, at the variable.
7. 🔴 **The feed line filter, as plumbing.** `$lineId: ID` added to `FEED_QUERY` and passed to
   `publicSocialMediaLinks`; `FeedQueryVars.lineId?: string` is `string | undefined` and **cannot** be
   written `null`, so "unfiltered" is the ABSENCE of the key rather than one of two spellings.
   `HomeStore.lineFilter` + `setLineFilter()` derive it for both resources and both `loadMore*`
   continuations from ONE signal, and **drop every appended page for both feeds on the change** — a
   cursor is only meaningful inside the query that minted it, and keeping the appended rows would leave
   the previous filter's links on screen beside the new one's. The 30 s beat, which does not change the
   filter, still preserves Load More progress. The controls land in a later phase; nothing sets the
   filter yet.
8. 🔴 **The vote-overlay invariant, restated.** `lineId` is now the ONE key the overlay reads may omit,
   and it is the key they MUST: the overlay reads stay unfiltered because a wider read is harmless under
   the invariant while a narrowed one loses votes (and would freeze the filter's answer at mount). The
   structural compare in `home.store.spec.ts` was rewritten to assert exactly that asymmetry — the
   overlay's variables equal the mirrored resource's variables with the single `lineId` key removed,
   the key SETS are compared too so a future variable is not quietly exempted, and the filter is applied
   BEFORE the resources are captured or the omission would be trivially true.
9. **Methodology registry** — three `MetricDoc`s (`network.activity-sparkline`,
   `network.line-history-strip`, `network.heat-strip`, all `sectionId: "line-status"`) plus
   `SERVICE_DAY_START_HOUR`, `SERVICE_DAY_HOURS` and `HEAT_INTENSITY_STEPS`. The three constants MIRROR
   backend shapes rather than inventing thresholds, and `status-history-display.util.spec.ts` pins each
   of them against the code that uses it, so a backend change that is not mirrored fails a test instead
   of quietly mislabelling a chart. A separate `REVIEWED_AT_HISTORY_WIDGETS` constant records that this
   is a different review of the same section than the board's headline metrics.
10. **`line-status-chart.component.ts`** now imports the shared palette; its local `BAR_CLASS` copy is
    gone. Its own public testids and copy are untouched.
