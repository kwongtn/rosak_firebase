# 2026-10-04

## spotting/report-form: the vehicle picker is alphabetical, with Married/Decommissioned sunk to the bottom

The picker's list was whatever order the `LinesAndVehicles` response happened to flatten to:
`VehicleType.vehicles` comes back type-by-type (each type alphabetical from its DataLoader), so the
combined roster was grouped by vehicle type rather than alphabetical overall, and a decommissioned or
married vehicle could sit at the very top of the dropdown. Frontend-only by design — the shared
`LinesAndVehicles` resolver also feeds the fleet tables, whose vehicle-type grouping must not change,
and the whole roster is already fetched in one shot, so there is nothing pagination-wise to gain
server-side.

1. **The order is a display rule in the feature's pure util.** New `sortVehiclesForPicker` in
   `data/vehicle-search.util.ts` sorts by `identificationNo` with
   `localeCompare(..., { numeric: true })` (so "Set 2" precedes "Set 10" instead of sorting after it)
   and demotes vehicles whose current status is `MARRIED` or `DECOMMISSIONED` to the bottom,
   alphabetical among themselves. It returns a copy — the computed's source array is never mutated.
2. **Applied at the one place the form builds combobox items.** `vehicleItems` maps the sorted rows,
   so both the unfiltered list and `vehicleFilterFn`'s query-filtered list preserve the same order
   (the combobox only filters an already-ordered array).
