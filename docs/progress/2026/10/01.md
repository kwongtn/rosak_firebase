## console/spotting: rows are selectable by default, and Shift-click range-selects

Frontend-only interaction work on the admin spotting queue — no GraphQL contract change, no backend
touch (`MARK_AS_READ_MUTATION` and `data/console.queries.ts` are byte-identical).

1. **The "Select rows to mark as read" switch is gone.** Checkboxes, the row highlight and the
   bulk-action button need no enabling toggle any more, so the label + its `hlm-checkbox` were
   removed and every `@if (selectMode())` gate (header cell, per-row cell, the button) with them.
   `useBulkActions` lost `selectMode`/`toggleSelectMode` entirely — `ConsolePage` was its only
   consumer repo-wide (grep-verified before the API change), so nothing else had to be touched.
2. **Clicking anywhere on a row toggles it.** `(click)="onRowClick(event.id, $event)"` on the `<tr>`,
   with `cursor-pointer hover:bg-muted` for affordance. The three inner interactive elements — the
   event-id and reporter deep links into the Django admin, and the vehicle `routerLink` — call
   `stopPropagation()` so activating them doesn't also select the row.
3. **Shift-click applies the clicked row's new state to the anchor→row span.** The anchor is the
   last row clicked _without_ shift; a shift-click does not move it, which is what lets a second
   shift-click retarget or undo the same range. Order comes from a new
   `computed(() => events().map(e => e.id))`, not from the `Set` (which has no order). Shift-clicking
   a _checked_ row un-checks the range.

- **The checkbox is driven by `(click)`, not `(checkedChange)`** — only a click carries `shiftKey`,
  so Shift+click on the box has to run the same handler as Shift+click on the row, and it must read
  the row's state rather than the box's or the two paths can disagree. It calls
  `event.stopPropagation()`; because the checkbox's own signal write is synchronous, the bubbled row
  click would otherwise see the post-toggle state and undo it. Verified empirically that a click on
  `hlm-checkbox`'s inner `<button role="checkbox" tabindex="0">` **does** reach a host-level
  listener (Spartan does not stop propagation), which is also what makes the box keyboard-operable:
  the synthesized Space/Enter click carries the same modifiers into the same handler, so
  Shift+Space range-selects too.
- **Anchor lifetime** (the easy thing to get wrong): cleared by `clearSelection()` (which `search()`
  and a successful `markAsRead()` already call), by any selection that empties, and by **every**
  `load()` — including an appended "Load more" page, since the ids the anchor indexed into have
  shifted. A stale anchor would silently sweep an arbitrary span. Degenerate cases (no anchor, or an
  anchor/target no longer in the list) degrade to a single-row toggle rather than throwing.
- **Range core is pure and exported**: `toggleCheckedRange(checked, orderedIds, anchorId, targetId,
targetState)` next to the composable, with the applying method `toggleCheckedInRange(orderedIds,
targetId, targetState)`. It returns a new `Set` and never mutates the one it is given, matching the
  composable's existing immutable-update contract.

  38 tests), then the full gate — `npx prettier --check .` clean; `npm test -- --no-watch`: **102 test

## insiden/home: the link conversation becomes a nested, ordered, editable tree

Frontend half of the shared plan `.omo/plans/link-thread-tree.md`; the backend half (the
`django-tree-queries` model, migration, mutations, loader) is a parallel agent's work in
`rosak_backend` and is not repeated here. Three user requests: **the number of links and its
display belong inside the parent (first) link, not individually outside it**; **the data structure
should have a sequence** (`django-tree-queries`, which stores nothing and answers a recursive CTE per
query, over `django-treenode`'s in-memory tree); **sublinks should be editable in the front page UI**.
Plus a confirmed decision that the hierarchy is a nested tree and existing groups migrate.

1. **The count moved inside the first card.** `app-link-card` gained `sublinkCount = input(0)`,
   `sublinksExpanded = input(false)` and `sublinkToggle = output<void>()`, and renders the
   conversation affordance — chevron plus a readable "N links" — **inside the card's right rail**.
   The chip row beside Pending/Official was the ideal slot and it is inside the card's `<a>`, where a
   `<button>` is invalid HTML whose click also navigates, so the card's own "interactive controls are
   siblings, never children" constraint outranked the nicer placement. The card's outer markup is
   otherwise unchanged and the spec pins `outerHTML` parity between a threaded and an unthreaded root.
2. **The hierarchy is now an ordered nested tree.** `app-link-thread` became **recursive** — it
   includes _itself_ in `imports`, so no separate branch component was needed (verified under the
   vitest builder and AOT) — rendering the root, then each child as a nested thread with its own
   `expanded` signal and an indent per level. Fields renamed across the type layer:
   `threadId`→`parentId`, `threadSize`→`sublinkCount`, `threadLinks`→`sublinks` (recursive; the
   element type is `LinkCardItem` itself), plus `position` added. The old three are **gone
   server-side with no alias**, so a stale spelling is a hard "Unknown field" on the whole query.
   `FEED_QUERY` nests `sublinks` four blocks deep; its type chain stops at level 3 because
   `MAX_THREAD_DEPTH = 3` counts a root as depth 0, so a level-4 node is never materialised.
3. **Sublinks are editable.** `editable` is forwarded at every depth and `edit` re-emits the clicked
   descendant's own `LinkCardItem`. The previous wave's rationale ("a collapsed group is a summary;
   the host's edit flow is root-driven") is **superseded by the user's decision** and was rewritten in
   place, not deleted. Known and accepted: `editable` is one boolean for the whole conversation, so a
   root-derived `canEditLink(root)` also paints a pencil on somebody else's sublink — a cosmetic
   over-permission the backend rejects on write.
4. **The sequence round-trip was finished.** The console and My Links both gained move up/down,
   nest-under-a-row, and the sibling run. 🔴 The last piece was a real bug: `reorderSocialMediaLinks`
   is a **permutation** of one sibling set, so the payload must be the **stored** order
   (`position` ASC, `id` as the required tie-break) with one row moved — never the feed's
   `occurredAt DESC, id DESC` arrival order, and never a conversation the backend assembled
   oldest-first (which therefore arrives reversed). Both components now sort the run once, in
   `siblingsOf` / `_shape`, and derive the payload, the move index and the "already first / already
   last" reason from that single array. 🔴 Both also **refuse** to reorder when any sibling's
   `position` is missing (a synthesised order would become the stored truth, since the server writes
   the permutation verbatim) and when the loaded set is not provably complete — a filtered console
   queue (`queueIsComplete`) or an un-paged My Links list (`!_hasMore`), because the server _tolerates_
   a partial permutation rather than rejecting it, silently pushing an unseen row to the end.
5. **The vote overlay's walk is now recursive.** `HomeStore.loadVoteOverlay()` recurses through
   `sublinks` at every depth. The reads already collapsed and already matched the service-day window;
   the loop walked one level, so a deep member's vote read as the anonymous `0` — invisible, because
   a missing overlay entry falls back to `link.userVote`, which for `graphqlResource` data is always
   `0`. The invariant is now written down in full: **same query, same variables, AND walk every
   level**; the overlay's read set must equal the _rendered_ id set. No `MAX_THREAD_DEPTH` mirror on
   the client — that is the server's business, and mirroring it silently loses a level when the cap
   moves.
6. **Flat hosts stay flat.** `/insiden` "Submitted Links", the situasi tab and the per-incident card
   do **not** select `sublinks`, and `app-link-list` never binds `[sublinkCount]`, so the card's gate
   is false and no chip appears. Each surface now pins that on **both** of the documents its list is
   assembled from — the previous wave had to fix a bug where a list's page 1 and its continuation
   pages disagreed about which timestamp they labelled, and this is the same hazard one field over.

## docs: `reorderSocialMediaLinks.parentId` is nullable-and-defaultless, so "required" was never true of it

A documentation pass recorded this argument as "**required, nullable** — omitting it is a client bug
**rejected by validation**". The types built on that reasoning are fine; the _explanation_ was wrong,
and it was wrong in the most trust-damaging way — a specific, confident, incorrect claim sitting in the
documents the next agent reads instead of re-deriving.

- **The error**: in GraphQL **"required" IS "non-null"**, so "required, nullable, no default" is not
  a state the SDL can express. `is_required_argument` in graphql-core's
  `validation/rules/provided_required_arguments.py` is
  `is_non_null_type(arg.type) and arg.default_value is Undefined`; `parentId: ID` is nullable, so it
  is `False`, `ProvidedRequiredArgumentsRule` never fires, and the omission **reaches the resolver**,
  where `strawberry.Maybe` supplies `UNSET` and the guard at
  `rosak_backend/incident/schema/mutations/interactions.py:287` raises the `GraphQLError`.
- **Verified** against the emitted SDL (`rosak_backend/rosak/tests/snapshots/schema.graphql:678`,
  graphql-core 3.2.6): `is_required_argument` is `False` for `reorderSocialMediaLinks.parentId` and
  `True` for its `linkIds`, and **all three** spellings a client can send — key omitted from the
  selection, key omitted from a declared nullable variable, explicit `null` — `validate()` clean and
  enter the resolver. The only spelling stopped earlier declares `$parentId: ID!` and omits it, which
  is a client-chosen type (variable coercion), not a property of the field. `collapseThreads:
Boolean! = false` is the contrast: `Expected value of type 'Boolean!', found null.` The backend
  test that pins the guard (`rosak_backend/tests/incident/test_social_link_threads.py:1250`) sends
  the argument absent from the selection and asserts the tree is unchanged — it passes **because** the
  guard is in the resolver.
- **The true framing, which is the interesting part**: the omission is refused on purpose, not by the
  type system. `ID!` would make the meaningful `null` ("reorder the roots") a hard error, so the
  schema cannot express the omitted/`null` distinction and the guard does it. The backend docstring
  (`interactions.py:271-286`) already said this and is **unchanged** — a parallel task verified it by
  sabotage (deleting the guard made the mutation silently succeed and the existing test caught it), so
  the docs were the only wrong side.
- **Corrected**: `MISTAKES.md` (the `collapseThreads` entry's null-semantics coda, which had carried
  the three-way comparison with the false claim, is now a corrected three-row table plus the rule, the
  verification cites, and the "delete the guard to find out which layer is really testing" warning);
  `docs/components/console.md` (the `link.parentId ?? null` payload note); `docs/components/profile.md`

- **No type, query document or behaviour was changed.** The Vars types are deliberately left alone:

### 2. Long URLs and titles wrap instead of clipping (L2)

- The URL anchor gets `break-all` (it is **one unbroken token**, so nothing else stops a long address
  running past `max-w-72` into the table's scroll clip — the precedent is the detail sheet's URL
  anchor); the title cell gets `break-words` (prose, so it breaks only where it has no other
  opportunity). Neither cell may gain `truncate` / `whitespace-nowrap` / `overflow-hidden`.
- The two **date** columns keep `whitespace-nowrap` on purpose: a wrapped `Aug 1, 2026 08:30` reads
  as two values, and the whole point of the two clocks side by side is that each is legible at a
  glance. Pinned by a spec so a later "make the table tidy" pass cannot leak the wrap into them.

### 3. Approve also marks the link completed (L3)

Approve is now a **two-write sequence**: `updateSocialMediaLink(status: "LIVE")` then
`markSocialMediaLinkCompleted(linkId:)`, then **exactly one** reload. Both fields stay — they are
orthogonal axes and the backend keeps both (no migration, deliberately, to avoid colliding with the
in-flight tree refactor): `status` is feed visibility, `completed`/`completedAt`/`completedBy` is the
global triage flag. Before this, approving published a row and left it in the Pending queue forever,
so the admin had to press a second button for the thing they had just done.

- ⚠️ **Order is the contract.** The publish goes first because it is the half that can fail alone;
  completing a row still `PENDING_APPROVAL` would retire a link nobody can see.
- 🔴 **A partial failure is never silent and never rolls back.** Publish fails → the existing error
  toast, **no** completion call, **no** reload. Publish succeeds but completion fails → the error
  toast's **title** says _"Link approved, but not marked completed"_ (never a bare "couldn't
  complete", which an admin would read as "nothing happened") and the reload **still** runs so the
  row comes back as server truth. The return value is the **publish** outcome, which is what the
  sheet's close-on-success reads.
- 🔴 **Hide deliberately does not complete.** `completed` is the triage flag; hiding is a feed
  decision. Auto-completing would retire a row from the queue because an admin removed it from the
  feed. Asserted in the spec (`Hide only changes visibility — it never marks the link completed`).
- The **detail panel** gained its own Approve (`data-testid="panel-approve"`, rendered only while
  `status !== "LIVE"`), reached through the _same_ `approveLink` — not a panel-only variant — so the
  two surfaces cannot drift. `approveFromPanel` closes the sheet when the publish succeeded, like
  `markCompletedFromPanel` does.
- The standalone "Mark completed" row/panel action is **unchanged** and still needed: a row that is
  already `LIVE` can need retiring on its own, and a partially-completed approve points at it.
- Implementation shape that keeps one reload honest: `sendLinkStatus` / `sendMarkCompleted` are
  request-only helpers that **reject** and never catch; `setLinkStatus` / `markCompleted` are the
  toast-and-reload wrappers over them and stay the path for every single-request verb, so the
  replace-not-patch payload still has exactly one builder (`linkStatusInput`).

## console/links: the triage queue is an ACCORDION over the link tree (L4)

The last piece of the links half (L4): grouped links no longer render as a flat, indented table. The
queue walks the ordered TREE the backend already sends (`parentId` / `position` / `sublinkCount`) and
draws one row per link with the conversation structure — **collapsed by default**, exactly like the
public feed's `app-link-thread`. Frontend-only: no GraphQL document change (`sublinks` stays
unselected; the hierarchy is derived client-side from `parentId` over the flat array the queue already
loads), no backend change, no new dependency.

### What replaced the flat table — and why the old rationale was half right

The tree wave's class docstring said grouping was "a moderation/organisation tool here, NOT a display
mode — the list stays flat … nesting a conversation inside a table cell is the single thing that makes
a moderation queue unreadable". That was right about the ROW SET (an admin compares rows, and every
link should keep its own row, checkbox and action cell — nothing is nested inside a cell) and wrong
about the VISIBLE SET: a four-link conversation printed as four unrelated lines interleaved with
whatever the triage order happened to put between them. The accordion fixes the visibility without
touching the row set, so the reasoning is kept in the docstring and marked superseded rather than
deleted.

### The rules, and the two places they could go wrong

- **Collapsed by default.** `expandedIds = signal<ReadonlySet<string>>(new Set())`, keyed by id and
  **surviving a refetch** — ids are stable, so a conversation stays open through the reload a
  grouping or a reorder triggers. Immutable updates are load-bearing: a signal compares by reference,
  so an in-place `add`/`delete` would produce the SAME `Set`, change detection would never fire, and
  the chevron would silently stop responding.
- **`renderedLinks` is a walk, not a per-row predicate.** The top-level pass skips a row iff its
  DIRECT parent is loaded (it is emitted by the recursion from its parent's own position, which is
  what makes "directly beneath it" structural), and recursion emits each open row's children in
  STORED order (`position` ASC, `id` tie-break — the existing `compareStoredSequence`). "Visible iff
  every loaded ancestor is expanded" falls out of that rather than being written twice. **Root order is
  unchanged** — the queue's `occurredAt DESC, id DESC`.
- 🔴 **The chevron's gate is `childCountOf` (LOADED children), never `sublinkCount`.** On a filtered
  page `sublinkCount > 0` describes descendants that are not in the result and the chevron would
  expand to nothing; conversely `sublinkCount: 0` with a loaded child is hand-edited data, and
  refusing the chevron would strand a row the payload does contain. `sublinkCount` still owns the
  CHIP, which is a statement about the whole conversation including rows this page cannot show.
- 🔴 **The safety net had to learn the difference between "hidden" and "unreachable".** Cyclic
  hand-edited data (`a → b → a`) has no root for the recursion to start from, so anything the walk
  did not emit is appended at its flat position — a queue that silently swallowed links is worse than
  one that shows them untidily. The FIRST version of the net asked "is a loaded ancestor closed?",
  which is true for every descendant of a closed conversation, so closing a conversation fed its own
  children back into the net and the accordion drew a closed conversation in full (caught by the
  collapsed-by-default spec, not by inspection). The check is now **"is a RENDERED ancestor closed?"**
  — a closed ancestor always exists somewhere up the chain, even when the intermediate nodes were
  themselves never reached, and a cycle has none.
- 🔴 **Select-all reads the RENDERED rows; the grouping mutations scope to the LOADED ones.** Two id
  lists on purpose: `renderedLinkIds` drives `toggleSelectAll` / `allVisibleSelected`, because a
  checkbox must not tick rows the admin cannot see (it would read "all selected" while whole
  conversations sit closed, and a second press would clear those ticks); `visibleLinkIds` stays the
  scope of `scopedSelection`, because collapsing is a VIEW gesture, not an intent to forget — tick a
  root, open it, tick two children, close it, and Group must still move all three. Documented in the
  class docstring, `scopedSelection`, `toggleSelectAll` and `docs/components/console.md`.
- `_runsByParentId` is now the ONE map a sibling run is built, with three readers: the accordion's
  child runs, `childCountOf`, and `siblingsOf` (a row's siblings ARE its parent's children, so the
  reorder payload, the move index and the move-blocked reasons read the same array the accordion
  expands). It is memoised and shared, so a caller that reorders a run must copy first —
  `reorderSiblings` does.
- The depth indent, the `N links` chip and its coupling tooltip, and every per-row verb (Ungroup /
  Move up / Move down / Nest under… / Approve / Hide / Mark completed / Delete) are unchanged and
  reachable on every rendered row. The chevron carries `data-testid="thread-toggle"`, `aria-expanded`
  and a rotating icon, and does `$event.stopPropagation()` — the `<tr>` opens the detail panel on
  click. A childless row draws an **equal-width `size-4` placeholder** where the chevron would be,
  because the chevron sits inside the padded wrapper: without it every open/close shifts the URL and
  every column after it.
- ⚠️ **Acknowledged divergence from `MISTAKES.md`** (the 2026-09-30 `collapseThreads` entry rules
  that "client-side grouping of a flat page is unsound in the first place … so collapsing has to be
  the backend's decision"). The accordion groups a flat payload client-side and is safe here only
  because the console resolver has **no pagination and no row cap**, so an unfiltered queue's loaded
  set **is** the whole table — the `queueIsComplete` precondition — and every structural action is
  refused when the loaded set cannot prove completeness. A parent missing from a filtered result
  renders its child as a root, never a fabricated grouping, and the accordion only decides which
  rows of a complete set are **drawn**.
