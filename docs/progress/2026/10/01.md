## home: the refresh beat covers the links section too, and its confirmation actually fires

Three user-approved changes, one feature:

1. **The 30s beat and the manual click refresh the whole page** — line statuses, the Today feed's
   first page and the Last Week first page — while **never** dropping already-loaded `Load More`
   pages. `HomeStore.reloadFirstPages()` is the new beat callback: it reloads all three resources and
   bumps `linesRefreshTick`, and touches no appended-page signal. `reloadAll()` (full reset) keeps its
   existing callers — submit box, link sheet, status sheet, retry banner — and its semantics.
   `reloadLines()` is gone (nothing else used it).
2. **The refresh control moves on top of the links section on mobile**, staying at the top of the
   line-status panel on desktop. The countdown was moved into a new standalone
   `refresh-control/home-refresh-control.component.ts`, rendered twice with **CSS-only** visibility
   (`lg:hidden` in the feed section, `hidden lg:block` in the line section) so SSR and hydration emit
   identical markup — no `matchMedia` placement signal.
3. **A green success check.** The transient "Updated" is now `text-green-600 dark:text-green-400` on
   both the tick and the label, and — this is the actual bug fix — it fires **at all**: the old page
   effect keyed on `store.isLoading()`, which is pristine-first-fetch-only, so after the first load
   it never became true again and a pending-flag-plus-`isLoading` effect could not re-run (it could
   equally flash success on a FAILED refresh, since it never read `hasError`).

- **Why the graph layer changed**: `graphqlResource()` gains an **additive** `isFetching`
  (`computed(() => raw.isLoading())`, the raw in-flight flag — true for the first fetch, a
  `reload()` and a retry). `HomeStore.isRefreshing` ORs that across the three page resources, and the
  control arms on a **click**, latches `_refreshStarted` when `isRefreshing` goes true, and confirms
  only when it settles false with `!store.hasError()`. `isLoading` itself is untouched: it stays the
  skeleton gate.
- **Why a dedup guard**: keeping the appended pages while refetching page one means the two sets can
  legitimately overlap — an admin edit/deletion between the reads shifts a row out of page one and
  into a position an appended page already covers. `edges`/`lastWeekEdges` now de-duplicate by
  `edge.node.id` (first occurrence wins, backend order preserved), because a duplicate id would
  throw on the page's `@for (… track link.id)`.
- **Last Week excludes today, from the backend default.** `FEED_QUERY` / `FeedQueryVars` are
  **unchanged** — the frontend deliberately does not send `displayTodayInLastWeek`, so a frontend
  deployed before the backend change still gets the right window instead of requesting a variable an
  older schema rejects. The effective window is the 7-day `lastWeekOnly` range closed at 00:00 today,
  so the newest day group in the section is always "Yesterday" (the Today feed already covers today
  on its own).
