# TranSPOT / Spotting

## Path(s) & Routing

- **URL paths:** `/spotting` and `/spotting/:id` — both public, no route guard.
- **Route definitions:** `src/app/app-routing.module.ts:102-131`.
- **Page `<title>`:** `"MLPTF | TranSPOT"` for both routes (`app-routing.module.ts:104,119`).
- **Component:** standalone `SpottingMainComponent`, lazy-loaded via `loadComponent()` from `src/app/spotting/spotting-main.component.ts` (`app-routing.module.ts:111-113,126-128`). Both the bare `/spotting` route and the `/spotting/:id` route resolve to the exact same component — there is no separate "detail" component.
- **`:id` is a Line ID, not an event/report ID.** This is the single most important correction to make vs. a naive reading of the route table: `:id` is matched against `data.lines[...].id` from the `lines` GraphQL query (`spotting-main.component.ts:9-12,236-251`) and is used purely to deep-link to which **line tab** (e.g. MRT Kajang Line, LRT Ampang Line) is initially selected. There is no per-spotting-report detail page or permalink anywhere in this feature — an individual spotting entry (an `Event` row) has no route/URL of its own. `/spotting/:id` should be thought of as "TranSPOT, with line `:id`'s tab pre-selected," not as a spotting-report permalink.
- **Route guards:** none. Neither route has `canActivate`/`AuthPipe` (contrast with `/console` → `adminOnly`, `/situasi` → `betaTesterOnly`, `/profile` → `redirectUnauthorizedToSpotting`). Fully public — viewing all spotting data requires no login. Only the _submit new entry_ action inside the page is gated (client-side check + backend permission, see Permissions section).
- **Maintenance-mode switch:** `app-routing.module.ts:19-54` — `maintenance.spotting.curentlyInMaintenance` (currently hardcoded `false`) is checked independently at both route definitions (`app-routing.module.ts:106,121`); if `true`, `ConstructionComponent` (`src/app/construction/construction.component.ts`) is loaded instead of `SpottingMainComponent`. Purely a source-code boolean, no env var or admin toggle.
- **Redirect rules that make this the app's landing page:**
  - `{ path: "", redirectTo: "/spotting", pathMatch: "full" }` (`app-routing.module.ts:217-221`)
  - `{ path: "transpot", redirectTo: "/spotting", pathMatch: "full" }` (`app-routing.module.ts:222-226`)
  - Neither redirect preserves a trailing `:id` — visiting `/` or `/transpot` always lands on bare `/spotting`, which (per the client-side logic below) then immediately self-navigates to `/spotting/<first-line-id>`.
- **Client-side auto-redirect to the first line:** on load, once the `lines` query resolves, if the route has no `:id` param, `SpottingMainComponent.ngOnInit` picks `tabActiveIndex = 0` and calls `this.router.navigate(["spotting", this.tabActiveId])` (`spotting-main.component.ts:242-245`) — i.e. bare `/spotting` always ends up at `/spotting/<id-of-whatever-line-the-backend-returns-first>` (no explicit ordering requested on the `lines` query, so "first" is whatever order Django/Postgres returns by default — see Open Questions).
- **Not the wildcard fallback**: unmatched paths go to `FallbackComponent` (`app-routing.module.ts:227-234`), unrelated to spotting.

## Purpose

TranSPOT is the app's public, crowd-sourced train/vehicle-spotting log: anyone (member of the public, no account required) can browse, per rail line, every rolling-stock vehicle's current status, spotting history, and incident timeline; logged-in users can additionally submit a new "I saw this vehicle, here's its status/location/photos" report. It is explicitly the flagship/default feature — `/`, `/transpot`, and `/spotting` all converge here, and the page title advertises the product's colloquial name ("TranSPOT"). It underpins most of the rest of the product's operational data (vehicle status counts, incident correlation, media) since every other vehicle-status-driven view in the app (e.g. `console`, `profile`) ultimately reads from the same `spotting.Event` rows this page's submission form writes.

## Component Tree

- **`SpottingMainComponent`** (`src/app/spotting/spotting-main.component.ts`, selector `app-spotting-main`) — page shell. Owns: the `lines` query and resulting tab list, the upload-progress indicator in the top bar, and opening/closing the "Add spotting entry" drawer (`NzDrawerService`). Reads/writes the `:id` route param via `ActivatedRoute`/`Router`.
  - For each line, renders **`VehicleTypeContainerComponent`** (`src/app/spotting/vehicle-type-container/vehicle-type-container.component.ts`, selector `app-vehicle-type-container`) inside an `nz-tab`'s `<ng-template nz-tab>` (ng-zorro's standard lazy-tab-content pattern — content for a tab is not instantiated until that tab is first activated). Inputs: `[lineId]`, `[title]`, `[lineStatus]`.
    - Renders shared **`line-status-tag`** (`LineStatusTagComponent`, `src/app/@ui/line-status-tag/`) next to the line title, driven by `[lineStatus]` (one of `TESTING`/`DEFUNCT`/`ACTIVE`/`PARTIAL_ACTIVE`/`PARTIAL_DISRUPTION`/`TOTAL_DISRUPTION`).
    - Renders one **`SpottingTableComponent`** (`src/app/spotting/vehicle-type-container/spotting-table/spotting-table.component.ts`, selector `app-spotting-table`) per vehicle type on that line (e.g. per train class), `[dataSource]` = one `TableDataType` bucket.
      - Each row uses shared **`vehicle-status-tag`** (`VehicleStatusTagComponent`) for the vehicle's current status and shared **`wheel-status-tag`** (`WheelStatusTagComponent`) for its wheel condition.
      - Rows whose vehicle has ≥1 spotting or ≥1 incident are expandable (click the row); expanding mounts, conditionally:
        - **`InlineTimelineComponent`** (`spotting-table/inline-timeline/inline-timeline.component.ts`, selector `spotting-table-inline-timeline`) if `incidentCount > 0` — an independent GraphQL query per vehicle.
        - **`InlineHistoryComponent`** (`spotting-table/inline-history/inline-history.component.ts`, selector `spotting-table-inline-history`) if `timesSpotted > 0` — an independent, paginated GraphQL query per vehicle.
          - Each history row uses shared **`vehicle-status-tag`** again (for that historical entry's reported status) and shared **`spotting-type-cell-display`** (`src/app/@ui/spotting-type-cell-display/`, not itself gated by the task's shared-component list but pulled in transitively) to render the spotting `type`/location metadata.
          - If a history row has media or was reported by the current user, renders **`ui-spotting-image-preview-button`** (`ImagePreviewButtonComponent`, `src/app/@ui/spotting/image-preview-button/`), `[count]`/`[eventId]`/`[isMine]` — opens a drawer showing that event's photos (`SpottingImageListComponent`, outside this doc's scope) and, if `isMine`, lets the owner queue additional photo uploads for that already-submitted report via the shared `ImageUploadService`.
  - The "Add spotting entry" button opens an `NzDrawerService` drawer hosting **`SpottingFormComponent`** (`src/app/spotting/spotting-form/spotting-form.component.ts`, selector `app-spotting-form`) — the submission form. Communication is entirely through the drawer's content-component handle (`drawerRef.getContentComponent()`), not `@Input`/`@Output` bindings — `SpottingMainComponent.submit()` calls `contentComponent.onSubmit()` directly (`spotting-main.component.ts:175-212`).
    - Uses shared **`vehicle-status-tag`** next to each vehicle option in the vehicle `<nz-select>` dropdown.
    - Embeds **`FormUploadComponent`** (`src/app/@ui/spotting/form-upload/form-upload.component.ts`, selector `spotting-form-upload`) for attaching photos to the new entry; emits `(newImageEvent)` with the current `{[filename]: ImageFile}` map.
    - Embeds **`ui-action-list`** (`src/app/@ui/action-list/`, out of this feature's documented scope) filtered to `['spotting']`, showing entries the user has added _this browser session_ (via `SessionHistoryService`, in-memory only).
- **Non-component helpers used throughout:** `src/app/spotting/utils.ts` (pure mapping functions: GraphQL response → tab list / dropdown options / status-tag config) and `src/app/spotting/spotting-form/spotting-form.utils.ts` (form cross-field validators + the vehicle run-number search heuristic).

## Functionality & Behavior

### Line tabs (`SpottingMainComponent`)

1. On init, fires `GetLinesAndVehicles` (a page-local, unnamed-in-service `gql` query — see Data & API Contracts) once (`spotting-main.component.ts:230-252`). While it is in flight, `showLoading` is `true` and a full-width `<nz-spin>` is shown (`spotting-main.component.html:42-44`); there is no separate empty-state message if `lines` comes back `[]` — the tab bar would just render with zero tabs and `tabActiveId` would stay `undefined` (`data.lines[0]` would throw if the array is empty — see Known Quirks).
2. Tabs are built via `lineQueryResultToTabEntries` (`spotting/utils.ts:21-37`): tab title = `line.code`, tooltip/detail text = `line.displayName`, `lineStatus` passed straight through.
3. **Deep-link resolution** (`spotting-main.component.ts:238-251`): reads the current `:id` route param via `firstValueFrom(this.route.params)`.
   - No `:id` → select index 0 and **push** a navigation to `/spotting/<that line's id>` (see Routing section — this is how bare `/spotting` always ends up with a concrete id in the URL).
   - `:id` present → `tabActiveIndex = tabItems.findIndex(item => parseInt(item.id) === parseInt(currentDataId))`. If the id doesn't match any known line (bad/stale id, e.g. after a line is deleted, or a typo), `findIndex` returns `-1`; `tabActiveId` is still the truthy (invalid) string so the tab **container** still renders (`@if (tabActiveId)`, `spotting-main.component.html:46`), but `nz-tabset`'s `[nzSelectedIndex]="-1"` means **no tab appears selected** — a silent "nothing shown" state rather than an error message or fallback to line 0.
4. **Switching tabs** (`activeTabChange`, `spotting-main.component.ts:260-265`): updates `tabActiveId`/`tabActiveIndex` and calls `router.navigate(["spotting", tabActiveId])` — a normal (non-`replaceUrl`) navigation, so every tab switch pushes a new browser-history entry; using the browser Back button cycles backward through previously-viewed line tabs one at a time rather than leaving the page.
5. **Per-tab lazy data loading**: each tab's `app-vehicle-type-container` content lives inside `<ng-template nz-tab>` — ng-zorro's default is to defer instantiating that content until the tab is first activated, and (absent `nzForceRender`, which isn't used here) to keep it mounted afterward rather than destroy it when you switch away. Practically this means: the GraphQL `vehicleTypes` query for a given line fires once, the first time you open that line's tab, not for every line up front and not again on every re-visit to an already-opened tab in the same page view (see Open Questions — exact ng-zorro remount semantics not exercised at runtime here).
6. **Responsive drawer width**: `width` is recomputed on every window resize (`@HostListener("window:resize")`, `spotting-main.component.ts:88-93`) — `100vw` under 700px viewport width, else a fixed `700px`; passed as `nzWidth` to the "Add spotting entry" drawer.
7. **Top-bar upload progress indicator** (`spotting-main.component.html:1-41`): once at least one upload has ever been queued (`hadUpload`, set permanently `true` the first time `$pendingUploadCount` emits `>0`, `spotting-main.component.ts:220-228`), a persistent tooltip+progress-bar (`nz-progress`, `nzSteps` = total queued count) plus a spinner (shown while `$uploadPercentage !== 100`) appears next to the "Add spotting entry" button, backed by the shared `ImageUploadService` observables (`$totalUploadCount`, `$pendingUploadCount`, `$percentUploaded`). This is page-global — it reflects **all** pending uploads app-wide (spotting photos or incident-calendar photos, see `PendingUploadType`), not just this page's.
8. **Staging-environment CSS hook**: the top button bar gets an extra `.staging` class combined from `env.sentry.environment` (`spotting-main.component.html:1`, `.scss:6-10`) which adds `padding-top: 40px` under 1360px width — presumably compensating for an app-wide "staging" banner pushing content down; purely cosmetic/environment-driven, unrelated to spotting logic itself.

### Vehicle-type container + table (`VehicleTypeContainerComponent`, `SpottingTableComponent`)

9. **Query re-fires on every `@Input` change** (`ngOnChanges`, `vehicle-type-container.component.ts:171-193`), not just on `lineId` — a change to `title` or `lineStatus` alone (neither of which is actually part of the GraphQL filter) would still discard the previous subscription and re-run `GET_VEHICLES`. In this feature's actual usage all three inputs are set once per tab and never change afterward, so this is inert today, but it is a latent inefficiency if the parent ever started passing dynamic `title`/`lineStatus` values.
10. **`GET_VEHICLES` variables** include a `DISTINCT: true` field inside `vehicleTypeFilter` (`vehicle-type-container.component.ts:181-186`). **Correction (verified live against the production GraphQL endpoint during the rewrite): this field is real and load-bearing.** Without it, `vehicleTypes(filters: {lineId})` returns one duplicate `VehicleType` row per vehicle↔line join match (up to one per vehicle on the line); with `DISTINCT: true` it correctly collapses to one row per type. An earlier pass of this doc (see the now-corrected Data & API Contracts / Known Quirks sections below) had wrongly concluded this field doesn't exist on the backend's `VehicleTypeFilter` input type from static source reading alone — that analysis was incorrect; always verify against the live schema before trusting a static read on a dynamically-injected filter field.
11. **Per-vehicle-type breakdown** (`filterTabItems`, `vehicle-type-container.component.ts:93-165`): for each `VehicleType` returned, builds one `TableDataType` bucket (`displayName`, the 7 status counts + total, and a sorted-by-`identificationNo` row list) and accumulates page-wide totals across all vehicle types into `tagListDisplayConfig`'s counts, shown as the "Total: N | In Service: N | Not Spotted: N | ..." chip row above the per-vehicle-type tables (`vehicle-type-container.component.html:22-46`). Each chip's tooltip shows that status's percentage of the page total (`toPrecision(3)`, e.g. `"42.9%"`).
12. **Row `$expandConfig`** (`vehicle-type-container.component.ts:138-143`): a row is `expandable` iff `spottingCount > 0 || incidentCount > 0`; otherwise clicking the row (which still has a `cursor-pointer` class only when expandable) does nothing.
13. **Per-table status filter chips** (`SpottingTableComponent.changeChecked`, `spotting-table.component.ts:158-193`): the table's own header/collapse-panel chip row (distinct from the page-total chip row above) lets the user toggle individual status chips on/off to filter that table's rows client-side (no re-query — this is a pure in-memory filter over already-fetched rows via `allowedStatuses`, checked in the template with `allowedStatuses.has(rowItem.status)`, `spotting-table.component.html:71`). Clicking "Total" resets to showing everything (`markTotalCheckedTrue`, `spotting-table.component.ts:147-156`); if every individual chip ends up unchecked, "Total" is automatically re-checked (`totalChecked` recomputed at the end of `changeChecked`).
14. **Table is collapsible** (`nz-collapse`/`nz-collapse-panel`, `isCollapsed` starts `!false` i.e. `true` — collapsed by default, `spotting-table.component.ts:64`). The header shows a condensed chip summary only while collapsed (`@if (!isCollapsed)` block, `spotting-table.component.html:168-202` — note the inverted condition: the summary chips in the _header_ show only when the panel is **expanded**, i.e. `!isCollapsed` means "not collapsed" = expanded; a second, separate chip row is shown inside the panel body regardless).
15. **Columns**: Vehicle ID (+ nickname on a second line if present), Status, Last Spotted, In Service Since, Times Spotted, Wheel Status, Notes (`spotting-table.component.ts:71-121`). A "Last Spotted By" column is present in the code but commented out (`spotting-table.component.ts:96-101,129`) — dead/disabled, not shown.
16. **Horizontal scroll**: the table has a fixed layout with `nzScroll.x = '1330px'` (`spotting-table.component.html:53`) — on narrow viewports the table scrolls horizontally rather than reflowing; column pixel widths are hardcoded per-field (`tableWidthConfig`, `spotting-table.component.ts:123-133`).

### Inline history (`InlineHistoryComponent`)

17. Queries `GetSpottingHistoryService` (`eventFilters: { vehicle: { id: vehicleId } }`, `eventOrder: { spottingDate: "DESC" }`, `eventPagination: { limit: 30, offset: 0 }`, `fetchPolicy: "network-only"`) — always a fresh network fetch, no cache reuse, on every expand (`inline-history.component.ts:134-162`).
18. **Infinite scroll pagination**: a native `scroll` listener is attached directly to the rendered `nz-table`'s internal `.ant-table-body` DOM element (`ngAfterViewInit`, `inline-history.component.ts:164-170`) — when scrolled within `50px` of the bottom (`LOAD_MORE_THRESHOLD_PX`, `inline-history.component.ts:40,66-73`) and not already loading, calls `loadMore()`, which `fetchMore`s the next page (`offset` = current row count, same `limit = 30`) and **concatenates** results onto `dataSource` (`inline-history.component.ts:176-200`). There is no "end of results" detection — if the vehicle has exactly a multiple of 30 spottings, one extra empty-page fetch will occur near the bottom before the user stops scrolling (harmless, just an extra network round trip returning `[]`).
19. **Row extras beyond the typed `LastSpottingsTableElement` interface**: `runNumber` and `wheelStatus` (shown as 🏃‍♂️/🛞-prefixed inline annotations under the Status cell, only if present, `inline-history.component.html:38-63`) and `mediaCount`/`isMine` (drive whether the image-preview button renders, `inline-history.component.html:75-87`) are read off the row objects even though the strict TS interface doesn't declare them — the component's own `tableRows` getter is deliberately typed `any[]` with a comment explaining this (`inline-history.component.ts:56-58,86-92`).
20. **Location remap**: if a row has a `location`, `mapGqlResultsToDisplayData` (`inline-history.component.ts:202-218`) reshapes the raw GeoJSON-style `[longitude, latitude]` tuple the backend returns (`location.location`) into explicit `latitude`/`longitude` fields on the row object for display — but nothing in this component's own template actually renders `latitude`/`longitude`; this remap exists but currently has no visible effect in `InlineHistoryComponent`'s own markup (see Known Quirks).

### Inline timeline (`InlineTimelineComponent`)

21. Fires once per expand, no pagination, no re-fetch (`inline-timeline.component.ts:69-111`). Sorts `vehicleIncidents` by `order` ascending, then maps to alternating top/bottom card positions (`index % 2`) along a horizontal line, colored by `severity` (`TRIVIA`→info blue, `STATUS`→success green, `CRITICAL`→danger red — `severityToDotColor`, lines 59-67). The connecting segment after each item is `"none"` if that item is flagged `isLast` (backend-computed "this incident is still ongoing/most-recent" flag) else `"dashed"` for the last item in the list or `"solid"` otherwise.
22. **Empty state**: if `vehicleIncidents` is `[]`, nothing renders at all — no "Notable Incidents" heading, no placeholder text (`inline-timeline.component.html:5`, guarded by `timelineList.length > 0`). Since this component is only mounted when `incidentCount > 0` (`spotting-table.component.html:138`), an empty result here would only happen if the two counts disagree (e.g. a race with data changing between the parent's `incidentCount` and this query), which is an edge case rather than a normal empty state.

### Submission form (`SpottingFormComponent`)

23. **Not-logged-in banner**: if `authService.userData` has not resolved to a user, an info alert with a "Login" button (`authService.login()`) is shown above the whole form (`spotting-form.component.html:12-33`) — the rest of the form is still fully visible/fillable while logged out; the login gate is enforced only at submit time (see below), not by disabling the form.
24. **Form fields and validators** (`FormGroup` built in the constructor, `spotting-form.component.ts:264-294`):
    - `line` (required) — `<nz-select>` of all lines (`lineQueryResultToOptions`, alphabetically sorted by `"code - displayName"`).
    - `vehicle` (required) — a grouped `<nz-select>` (one `nz-option-group` per vehicle type on the selected line), disabled until a line is chosen (`onLineChanges`, `spotting-form.component.ts:455-486`); each option shows the vehicle's current status via shared `vehicle-status-tag`. Custom search matcher `vehicleSearchFn` (`spotting-form.component.ts:182-201`) matches on raw substring **or** on a line-specific "run-number → probable set/unit numbers" heuristic (`numberSeenToSetNumbers`, `spotting-form.utils.ts:68-209`) — e.g. typing a 3-4 digit number seen painted on an LRT/MRT/monorail train, or a KTM coach-class code, resolves to the likely fleet/unit identifier so users can search by what's physically visible on the train rather than its internal ID. This is a fairly elaborate, line-specific piece of domain knowledge (separate constants for LRT Kelana Jaya/Ampang/Sri Petaling, Monorail, MRT Kajang/Putrajaya, and KTM EMU/ETS/DMU classes 61/81/83/91/92/93) baked directly into the frontend.
    - `spottingDate` (required, defaults to "now") — date picker, not clearable.
    - `status` (required, default `IN_SERVICE`) — one of `IN_SERVICE` / `NOT_IN_SERVICE` / `DECOMMISSIONED` / `TESTING` (a deliberately narrower set than the vehicle's own current-status enum, which also includes `NOT_SPOTTED`/`MARRIED`/`UNKNOWN` — those are system/derived states, not user-reportable).
    - `type` (required, default from `SpottingStorageService`, else whatever was last stored) — `DEPOT` / `LOCATION` / `BETWEEN_STATIONS` / `JUST_SPOTTING` / `AT_STATION`.
    - `atStation` / `originStation` / `destinationStation` — only relevant (and only validated as required) when `type` is `AT_STATION` or `BETWEEN_STATIONS` respectively; populated from a per-line `stationLines` query fired on type change (`onInputTypeChanged`, `spotting-form.component.ts:358-406`).
    - `wheelStatus` (optional) — `FRESH` / `NEAR_PERFECT` / `FLAT` / `WORN_OUT` / `WORRYING`.
    - `notes` (optional, free text).
    - `runNumber` (optional) — only shown at all if `allowRunNumber(lineId)` is true, i.e. `lineId` is `"2"` (MRT Kajang) or `"3"` (MRT Putrajaya) (`spotting-form.utils.ts:64-66`) — hardcoded to those two line IDs.
    - `isAnonymous` (checkbox, default `false`) — see backend effect below.
    - `sanityTest` (checkbox, default `false`) — only shown/required when the selected vehicle's status is `DECOMMISSIONED`/`MARRIED`/`OUT_OF_SERVICE`/`UNKNOWN` (`onVehicleChanges`, `spotting-form.component.ts:343-356`; validator at `spotting-form.utils.ts:25-44`) — an explicit "Yes, I know what I'm doing" acknowledgment gate before letting the user submit a report against a vehicle in one of those unusual states, framed as a guard against likely misclicks.
    - `location` — only populated (and only required) when `type === "LOCATION"`: on selecting that type, calls `navigator.geolocation.getCurrentPosition` with `{ maximumAge: 0, timeout: Infinity, enableHighAccuracy: true }` (`spotting-form.component.ts:407-444`); success populates `location` with the raw `GeolocationCoordinates` fields and shows a one-time info toast ("Location accessed. Take note that we will not know your location until you submit the form."); failure shows an error toast with the browser's `PositionError.message` and **silently reverts `type` back to `JUST_SPOTTING`**.
    - `uploads` — populated by the embedded `FormUploadComponent`'s `(newImageEvent)`.
    - **Cross-field validators** on the group itself (`spotting-form.component.ts:288-292`): `betweenStationTypeOriginDestinationStationValidator`, `abnormalStatusSanityTestValidator`, `atStationTypeStationValidator` (all in `spotting-form.utils.ts`).
25. **"Between Stations"/"At Station" selected before a line" guard**: selecting either of those types with no line yet chosen silently resets `type` back to `JUST_SPOTTING` and flips `isShowBetweenStationsModeSelectedBeforeLineSelectionError = true`, which forces the `line` field into a visible error state with explanatory text ("Please select a line before selecting 'Between Stations' or 'At Station' mode. Then, select the type again.") even though the `line` control's own validity hasn't actually changed (`onInputTypeChanged`, `spotting-form.component.ts:358-369`; template `spotting-form.component.html:43-54`) — a deliberately misdirected error display used as a UX nudge.
26. **Changing the line resets downstream state**: `onLineChanges` (`spotting-form.component.ts:455-486`) recomputes vehicle options for the new line, clears `stationOptions`, forces `type` back to `JUST_SPOTTING`, recomputes whether the run-number field should show, and resets `vehicle`/`originStation`/`destinationStation`/`runNumber`/`atStation`/`sanityTest` — i.e. switching lines discards all downstream selections rather than trying to preserve anything compatible with the new line.
27. **"Open our guide" link** (question-mark icon next to the vehicle field, `spotting-form.component.html:134-145`): opens (new tab) a URL built from `GetLineGuideLinkService` — a GitHub wiki anchor (`.../wiki/MLPTF-all-about-Trains#<anchor>`) whose per-line anchor fragments are read live from a **Firestore** document `public/line-guide` (`onSnapshot`, `get-line-guide-link.service.ts:20-27`) — this is the one piece of this feature backed by Firestore rather than the GraphQL backend. If a line has no entry in that document, the link degrades to the wiki page's top (`#` with empty anchor).
28. **Vehicle-status warning banner**: if the selected vehicle's current status is `DECOMMISSIONED`/`MARRIED`/`OUT_OF_SERVICE`/`UNKNOWN`, a warning alert appears explaining the situation and hosting the `sanityTest` checkbox described above (`spotting-form.component.html:147-183`).
29. **Location-derived read-only fields** (only when `type === "LOCATION"` and the corresponding raw geolocation value is truthy): Altitude (`"{alt}m±{altitudeAccuracy}"`), Heading (raw degrees), Speed (`speed * 3.6` → km/h from the browser's m/s), Coordinates (via shared `coordinatesHumanizer` pipe, `±accuracy`) — all rendered as disabled `<input>`s (`spotting-form.component.html:286-374`).
30. **Submission gate & payload shaping** (`onSubmit`, `spotting-form.component.ts:493-617`):
    - Blocks with a toast if the form is invalid, or if `authService.isLoggedIn()` is false (client-side login check — this is a UX guard, not the real enforcement; see Permissions).
    - If `type === "LOCATION"` but `location` never got populated (geolocation still pending/denied without having reverted `type`), blocks with an error toast.
    - **Field distillation before sending**: clears `originStation`/`destinationStation` unless `type` is `BETWEEN_STATIONS`/`AT_STATION`; for `AT_STATION`, moves `atStation`'s value into `originStation` and clears `destinationStation`/`atStation`; clears `runNumber` unless `allowRunNumber(line)`; clears `location` unless `type === "LOCATION"`.
    - **Date normalization**: converts the picked `Date` to a timezone-corrected `YYYY-MM-DD` string by subtracting the local timezone offset before calling `.toISOString().slice(0,10)` (`spotting-form.component.ts:557-563`) — a common pattern to avoid the UTC-conversion date-shifting bug, applied here specifically because `spottingDate` is a pure calendar date on the backend (`date`, not `datetime`).
    - Persists `type` and `line` back into `SpottingStorageService` (in-memory only, page-session scoped — see State Management) so the next time the drawer opens, those two fields (plus, for `AT_STATION`, the previously-chosen station) are pre-filled.
    - Strips fields the GraphQL mutation doesn't take (`line`, `sanityTest`, `uploads`) and unwraps `vehicle` from its `{name, value, status}` option object down to just `value` (the vehicle ID).
    - Fetches a fresh Firebase ID token (`authService.getIdToken()`) and sends it as a `Firebase-Auth-Key` header on the mutation (there is a commented-out `g-recaptcha-response` header and a commented-out `ReCaptchaV3Service` injection throughout this file — reCAPTCHA is fully wired on both ends of the code but currently disabled; see Known Quirks).
    - Fires `addEvent` (see Data & API Contracts) and returns `{ uploads, spottingSubmission: <promise>, formData }` up to `SpottingMainComponent`.
31. **Post-submit flow** (`SpottingMainComponent.onFormCloseHandle`/`submit`, `spotting-main.component.ts:107-212`): on a successful mutation (`data.addEvent.id` present), every attached photo is handed to `ImageUploadService.addToQueue(eventId, file, "SPOTTING_EVENT")` (uploaded out-of-band, independent of the drawer closing — see Data & API Contracts, upload endpoint). A success toast reads "Spotting entry recorded! 🥳" (no photos) or "...Please wait for uploads to complete before closing this tab." (photos attached). The submitted entry (plus a client-generated `id`) is appended to `SessionHistoryService` under the `"spotting"` bucket, feeding the "As of Current Session, you added the following entries" list at the bottom of the form. On failure, an error toast shows `reason.message` directly (raw Apollo/GraphQL error text, unformatted).
32. **Image attachment UI** (`FormUploadComponent`, used identically by the top-level form): drag/click to add one or more images; client-side type allow-list is `image/jpeg`, `image/png`, `image/gif`, `image/tiff` (rejecting with a toast otherwise) — video types are listed in source as commented-out "future support" (`form-upload.component.ts:15-26`); every added file gets an async-generated 300×300 preview thumbnail (spinner shown until ready) and, if over 9MB (`MAX_MEGABYTE = 9e6`), is queued for client-side binary-search JPEG recompression before it's eligible to actually upload (see `ImageCompressionService` below); clicking a thumbnail asks for confirmation (`nz-popconfirm`) before removing it from the pending set. Uploads never actually POST through this component itself — `beforeUpload` always returns `false` (its own comment explains: files are processed client-side only and physically uploaded later, out-of-band, by `ImageUploadService`).

## Data & API Contracts

All GraphQL calls go through the app-wide Apollo client configured in `src/app/graphql.module.ts` (`environment.backendGraphqlUrl`), composed on the backend at `rosak/schema.py` from the `operation`, `incident`, and `spotting` Django apps (this feature touches all three).

### `lines` (query) — line tabs

- **Used by:** `SpottingMainComponent` (`GET_LINES`, `spotting-main.component.ts:38-47`) — requests `id, code, displayName, status`. **Not** the same query object as `GetLinesAndVehiclesGqlService` (below) despite the similar name — this one is line-only, no vehicle nesting.
- **Backend:** `operation/schema/schema.py:28`, `OperationScalars.lines: List[Line] = strawberry_django.field(filters=LineFilter)`. No `filters` argument sent, no permission classes — fully public. `Line.status` is the model's `TextChoicesField` (`operation/enums.py:24-35`: `TESTING`/`DEFUNCT`/`ACTIVE`/`PARTIAL_ACTIVE`/`PARTIAL_DISRUPTION`/`TOTAL_DISRUPTION`). No explicit `order` is passed by the frontend, so tab order is whatever the DB/ORM's default ordering returns (not confirmed to be stable/meaningful — see Open Questions).

### `vehicleTypes` (query) — per-line vehicle table data

- **Used by:** `VehicleTypeContainerComponent` (`GET_VEHICLES`, `vehicle-type-container.component.ts:29-57`), variables `{ vehicleTypeFilter: { lineId: <line id>, DISTINCT: true } }`.
- **Backend:** `operation/schema/schema.py:35`, filtered by `VehicleTypeFilter` (`operation/schema/filters.py:27-31`). **`DISTINCT: true` is real and required** — verified live: omitting it returns one duplicate `VehicleType` row per vehicle↔line join match; including it correctly collapses to one row per type. (A prior pass of this doc claimed the opposite — that it wasn't a declared field and would be rejected — based on a static read of `filters.py` that missed how this field is actually wired; that claim was wrong and has been corrected here and in Known Quirks below. Trust live verification over static source reading for anything filter/schema-injection-related.)
- **Fields requested & their resolvers** (`operation/schema/scalars.py:164-224`, all no explicit permission classes — public): `id`, `internalName`, `displayName`, the seven `vehicleStatus*Count` fields plus `vehicleTotalCount` (each individually resolved through a batched per-`(vehicleTypeId, status)` DataLoader, `operation/schema/loaders.py`), and `vehicles[]` with `id, identificationNo, status, nickname, lastSpottingDate, inServiceSince, spottingCount, notes, incidentCount, wheelStatus`. `spottingCount` accepts optional `after`/`before` date args the frontend never supplies (defaults to all-time count). `incidentCount`/`spottingCount` are also what backs the "is this row expandable" decision on the frontend (mirrors, but does not directly reuse, the backend's own `can_expand` field, which this query never actually requests).

### `GetLinesAndVehicles` (query) — form dropdowns

- **Used by:** `GetLinesAndVehiclesGqlService` (`services/get-lines-vehicles-gql.service.ts:10-28`), injected into `SpottingFormComponent`. Requests `lines { id code displayName vehicleTypes { id internalName displayName vehicles { id identificationNo status } } }` — a lighter-weight sibling of the main-page query (no status counts, no per-vehicle spotting/incident metadata), used only to populate the Line/Vehicle dropdowns.
- **Backend:** same `lines`/`Line.vehicle_types`/`VehicleType.vehicles` fields as above, no filter passed (all lines + all their vehicles are fetched up front for the form, unfiltered by line — filtering to the selected line happens client-side in `lineQueryResultToVehicleCascaderOptions`, `spotting/utils.ts:89-120`).

### `GetStationLines` (query) — station dropdowns

- **Used by:** `GetStationLinesGqlService` (`services/get-station-lines-gql.service.ts:17-25`), fired from `SpottingFormComponent.onInputTypeChanged` whenever `type` becomes `AT_STATION`/`BETWEEN_STATIONS`, variables `{ stationLineFilter: { line: { id: <lineId> } } }`.
- **Backend:** `operation/schema/schema.py:31`, `stationLines: List[StationLine]`, filtered by `StationLineFilter` (`operation/schema/filters.py:65-72`, supports `id`, `displayName`, `internalRepresentation`, `station`, `line`). Returns `id, displayName, internalRepresentation` — `StationLine` (not `Station` directly) is the line-specific "stop" concept (a `Station` can belong to multiple `Line`s via multiple `StationLine` rows, e.g. an interchange), which is why the form filters on `StationLine`s scoped to the chosen line rather than raw `Station`s.

### `AddSpottingEntry` → `addEvent` (mutation) — submitting a report

- **Frontend:** `ADD_ENTRY` (`spotting-form.component.ts:75-81`), `mutation AddSpottingEntry($data: EventInput!) { addEvent(input: $data) { id } }`, sent with a `firebase-auth-key` header (the commented-out `g-recaptcha-response` header noted above).
- **Backend:** `spotting/schema/schema.py:61-177`, `SpottingMutations.add_event`. **Permission classes: `[IsLoggedIn]` only** (`IsRecaptchaChallengePassed` is commented out here too, `spotting/schema/schema.py:62-66` — consistent with the frontend's disabled reCAPTCHA) — `IsLoggedIn` (`rosak/permissions.py:36-40`) just checks `bool(info.context.user)`, i.e. a valid Firebase ID token was resolved to a `common.User` by request middleware.
- **`EventInput`** (`spotting/schema/inputs.py:11-24`, a `strawberry_django.partial` of the `Event` model): `spotting_date` (date), `vehicle` (ID), `notes`, `run_number`, `status`, `type`, `wheel_status`, `origin_station`/`destination_station` (IDs — note: these are `StationLine` IDs from the frontend's perspective, but the resolver treats them specially, see below), `location` (`WebLocationInput`: `accuracy, altitudeAccuracy, heading, speed, latitude, longitude, altitude`, all optional), `is_anonymous`.
- **Resolver-side business logic worth knowing** (`spotting/schema/schema.py:67-177`):
  - `wheel_status` is only kept if `input.notes != UNSET` (line 75) — this reads as a copy-paste bug (checking `notes`'s unset-ness to decide whether to keep `wheel_status`) rather than checking `input.wheel_status` itself; in practice `notes` is sent by the form on every submission (even as `""`) so this doesn't currently manifest, but it means `wheel_status` would be silently dropped if a client ever sent `wheel_status` without also sending `notes`.
  - `origin_station`/`destination_station` inputs are **`StationLine` IDs**, but the resolver resolves them through `StationLine.objects` to the underlying **`Station`** id before saving (`spotting/schema/schema.py:80-104`) — i.e. the `Event.origin_station`/`destination_station` FKs point at `operation.Station`, not `operation.StationLine`; the frontend's line-scoped `StationLine` selection is translated down to the underlying physical station server-side. For `BETWEEN_STATIONS`, both origin and destination are resolved this way; for `AT_STATION`, only `origin_station` (the frontend's `atStation` field, remapped to `originStation` before sending — see Functionality item 30) is resolved, and `destination_station` stays `None`.
  - `data_source` is force-set to the `EventSource` row named `SITE` (`SpottingDataSource.SITE`, `spotting/enums.py:31-33`) — distinguishing web-submitted spottings from e.g. Telegram-bot-submitted ones (`SpottingDataSource.TELEGRAM`) at the data-model level, invisible to this frontend.
  - A DB-level `CheckConstraint` (`spotting/models.py:101-129`) enforces the `origin`/`destination` station combination is consistent with `type` (both required + distinct for `BETWEEN_STATIONS`; only origin for `AT_STATION`; neither for `DEPOT`/`JUST_SPOTTING`/`LOCATION`) — a second, DB-enforced line of defense behind the frontend's own cross-field validators.
  - Response only echoes back a hand-built `EventScalar` with the fields the resolver explicitly set (not a fresh DB re-fetch) — the frontend only actually reads `.id` from it anyway.
- **`isAnonymous`'s real effect**: stored on the `Event` row; the separately-resolved `reporter` GraphQL field on `EventScalar` (`spotting/schema/scalars.py:42-46`) is loaded via `batch_load_reporter_from_event`, which explicitly filters `is_anonymous=False` (`spotting/schema/loaders.py:9-19`) — so for an anonymous event, `reporter` resolves to `None` for **any** caller, not just non-owners. This feature's own queries never request `reporter` at all, so this has no visible effect within TranSPOT itself; it matters for other features (e.g. `console`/`profile`) that do query it.

### `events` (query, aliased via `GetSpottingHistoryService`) — per-vehicle spotting history

- **Frontend:** `services/get-spotting-history.service.ts:12-50`. Variables: `eventFilters: { vehicle: { id } }`, `eventPagination: { limit, offset }`, `eventOrder: { spottingDate: "DESC" }`, `fetchPolicy: "network-only"`.
- **Backend:** `spotting/schema/schema.py:25-27` (`SpottingScalars.events`), filtered by `EventFilter` (`spotting/schema/filters.py:19-77` — supports far more than this feature uses: `id`, `type`, `created`, a misleadingly-named `spotted` date filter that doesn't correspond to any request here, `notes`, `status`, `is_anonymous`, `vehicle`, plus custom filter fields `has_notes`, `different_status_than_vehicle`, `is_read`, `only_mine`, `free_search` — none of which this feature's query uses), ordered by `EventOrder` (`id`/`spotting_date`/`created`), paginated via strawberry-django's built-in offset pagination. **No permission classes on the field itself** — public, but two of `EventScalar`'s own resolved sub-fields are more restrictive: `is_read` requires `IsLoggedIn` (`spotting/schema/scalars.py:48-52`, not requested by this feature) and `is_mine` (requested by this feature) returns `False` outright if there's no logged-in user, otherwise compares the request user's id against the **true underlying `Event.reporter_id`** — independent of `is_anonymous` (unlike the separate `reporter` field described above, `is_mine` is computed via direct model-attribute access, not the anonymity-filtering loader, so an anonymous entry's true owner still correctly sees the "manage my photos" affordance).
- **Fields requested:** `id, spottingDate, status, type, notes, runNumber, mediaCount, isMine, wheelStatus, location { accuracy altitudeAccuracy heading speed location altitude }, originStation { id displayName }, destinationStation { id displayName }`. `mediaCount`/`location` are both resolved via batched DataLoaders (`spotting/schema/loaders.py`). `location.location` is a GeoDjango `Point` serialized as an `(x, y)` = `(longitude, latitude)` tuple (`generic/schema/scalars.py:6-11`) — the frontend explicitly remaps `location.location[1]`/`[0]` to `latitude`/`longitude` (see Functionality item 20).

### `vehicleIncidents` (query) — per-vehicle incident timeline

- **Frontend:** `GET_TIMELINE_DATA` (`inline-timeline.component.ts:27-38`), variables `{ vehicleIncidentFilter: { vehicle: { id: vehicleId } } }`.
- **Backend:** `incident/schema/schema.py:23-25`, filtered by `VehicleIncidentFilter` (`incident/schema/filters.py:20-22`: `id`, `date`, `severity`, `isLast`, `vehicle`), no permission classes (public). Fields requested: `order, date, severity, title, brief, isLast` — all plain fields on `VehicleIncident`/`IncidentAbstractScalar` (`incident/schema/scalars.py:13-27`), no loaders involved. `severity` is the model's `IncidentSeverity` choices (`incident/enums.py:4-7`): `CRITICAL`/`TRIVIA`/`STATUS`, matching the frontend's `IncidentSeverityType` exactly (note this is a distinct enum from `CalendarIncidentSeverity`'s `MAJOR`/`MINOR`, used elsewhere in the `incident` app, not by this feature).

### Photo upload (REST, not GraphQL) — `POST {backendUrl}upload/`

- **Frontend:** `ImageUploadService.triggerUpload` (`src/app/services/image-upload.service.ts:45-103`) — a `multipart/form-data` POST with `related_id` (the `Event` id), `upload_type` (`"SPOTTING_EVENT"` for this feature), `image` (the file), header `Firebase-Auth-Key`. Queued via `addToQueue`, drained by a 1-second `setInterval` poller (`image-upload.service.ts:162-169`) with bounded concurrency (`PromisePool.withConcurrency(environment.upload.concurrency)`, currently `10`). Files still marked `toCompress && !isCompressed` (compression still in flight — see `ImageCompressionService` below) are pushed back onto the queue rather than uploaded prematurely (`image-upload.service.ts:60-66`). On any HTTP error, the file is also pushed back onto the queue for an unbounded retry on the next interval tick (`image-upload.service.ts:81-90`) — there is no retry limit or backoff.
- **Backend:** `common/views.py:30-78`, `GenericUpload.post`. Validates `upload_type` is a known `TemporaryMediaType` (`SPOTTING_EVENT`/`INCIDENT_CALENDAR_INCIDENT`); resolves the current user from the `Firebase-Auth-Key` header (`FirebaseUser(request).get_current_user()`), 401 if absent. **For `SPOTTING_EVENT` uploads specifically: 403 Forbidden unless the authenticated uploader is the same user as the target `Event.reporter`** (`common/views.py:56-60`) — i.e. only the original reporter of an event can attach photos to it, whether at initial submission or later via the "manage photos" drawer; this is the real server-side enforcement behind the frontend's `isMine`-gated UI. The file is not attached to the `Event` directly — it's written to a `common.TemporaryMedia` row with `status=PENDING` (`common/enums.py` defines `PENDING`/`CLEARED`/`TRUSTED_CLEARED`/`OVERRIDE_CLEARED`, among others) — implying an out-of-band moderation/clearance step (not in this doc's scope) before an uploaded photo actually becomes visible as one of an `Event`'s `medias`/counts toward `mediaCount`.

### Firebase SDK usage

- **Firestore** (read-only): `GetLineGuideLinkService` (`spotting/services/get-line-guide-link.service.ts`) subscribes live (`onSnapshot`) to document `public/line-guide`, used only to build the "open our guide" link's per-line anchor.
- **Auth**: `SpottingFormComponent` reads `AuthService.userData`/`isLoggedIn()`/`login()`/`getIdToken()` throughout (see `src/app/services/auth.service.ts`, documented separately) — both to gate the submit button and to attach the `firebase-auth-key`/`Firebase-Auth-Key` header on the mutation and on photo uploads.
- No Firestore **writes**, no Firebase Storage, no Firebase Analytics calls anywhere in this feature's own files.

### Browser storage

- **None.** No `localStorage`/`sessionStorage`/`IndexedDB` usage anywhere under `src/app/spotting/**` or in `SpottingStorageService`/`SessionHistoryService` (both are in-memory-only despite the "Storage"/"History" naming — see State Management).

## State Management

- **`SpottingStorageService`** (`src/app/services/spotting-storage.service.ts`) — `providedIn: "root"`, plain in-memory fields (`lineId`, `typeObj` default `"JUST_SPOTTING"`, `atStationStationObj`), no persistence layer despite the name. Written only from `SpottingFormComponent.onSubmit` (persists the just-submitted `line`/`type`, and — only for `AT_STATION` — the chosen station) and read only from the form's constructor to pre-fill the next time the drawer opens. Cleared implicitly on full page reload (nothing survives a refresh); persists across opening/closing the drawer multiple times within one SPA session.
- **`SessionHistoryService`** (`src/app/services/session-history.service.ts`) — `providedIn: "root"`, a `BehaviorSubject<IHistoryStore>` map keyed by submission timestamp, plus a derived `historyStoreLength` count. Written by `SpottingMainComponent.submit()` on every successful submission (bucketed under `historyType: "spotting"`, shared with an unrelated `"mediaUpload"` bucket type used elsewhere). Read by `SpottingFormComponent`'s embedded `ui-action-list` (filtered to `['spotting']`) to render the "As of Current Session, you added the following entries" list — only shown at all if the user is logged in **and** `historyStoreLength > 0` (`spotting-form.component.html:528-542`). In-memory only; gone on refresh; never explicitly cleared within this feature (a `clearSessionHistory()` method exists on the service but nothing in this feature's files calls it).
- **`ImageUploadService`** (`src/app/services/image-upload.service.ts`) — `providedIn: "root"`, app-wide (shared with the unrelated `incident`/calendar photo-upload flow via `PendingUploadType`). Its three `BehaviorSubject`s (`$totalUploadCount`, `$pendingUploadCount`, `$percentUploaded`) are read by both `SpottingMainComponent` (top-bar progress indicator) and `ImagePreviewButtonComponent` (queuing additional photos onto an existing event). State persists for the lifetime of the SPA session (not per-page) — navigating away from `/spotting` mid-upload does not cancel or lose queued uploads, since the service and its `setInterval` poller are singletons outside any component's lifecycle.
- **`GetLineGuideLinkService`** (`spotting/services/get-line-guide-link.service.ts`) — `providedIn: "root"`, holds a live Firestore `onSnapshot` subscription and the last-received `guideLinks` map for the lifetime of the app; has an explicit `dispose()` method but nothing in this feature calls it (the service is never torn down as written — see Known Quirks).
- **Per-query-service DI scope**: `GetLinesAndVehiclesGqlService` and `GetStationLinesGqlService` are `providedIn: "any"` (a fresh instance per injecting module/standalone component tree) whereas `GetSpottingHistoryService` is `providedIn: "root"` — inconsistent DI scoping across near-identical `apollo-angular` `Query` subclasses within the same feature, though since none of them hold any state beyond the static `gql` document, the practical difference is negligible.
- **Component-local state**: all tab-selection state (`tabActiveId`/`tabActiveIndex`), all form-field state (Angular `FormGroup`), and all fetched-rows state (`VehicleTypeContainerComponent.tableData`, `InlineHistoryComponent.dataSource`, `InlineTimelineComponent.timelineList`) is plain component-instance state, re-fetched from scratch whenever the owning component is (re)created — none of it is cached/shared across sibling tabs or across a full page navigation away and back.

## Permissions, Roles & Flags

- **Viewing** (`lines`, `vehicleTypes`, `events`, `vehicleIncidents`, `stationLines` queries): fully public on both sides — no route guard, no backend `permission_classes` on any of these fields. Anyone, logged in or not, sees the entire vehicle roster, status counts, spotting history, and incident timelines for every line.
- **Submitting a new entry** (`addEvent` mutation): enforced **only** by `IsLoggedIn` on the backend (`spotting/schema/schema.py:61-66`, `rosak/permissions.py:36-40`) — any authenticated Firebase user may submit, no role/custom-claim required. The frontend additionally checks `authService.isLoggedIn()` before even attempting the mutation (`spotting-form.component.ts:510-519`) and shows a login prompt if not — this is a UX nicety, not the actual security boundary (a logged-out but scripted/DevTools-driven client hitting the mutation directly would still be rejected server-side by `IsLoggedIn`).
- **reCAPTCHA is currently disabled on both ends** — `IsRecaptchaChallengePassed` is commented out of `add_event`'s `permission_classes` on the backend, and the corresponding `ReCaptchaV3Service` injection/execution and `g-recaptcha-response` header are commented out on the frontend (`spotting-form.component.ts:5,248-249,584-585,599`). The `environment.captcha.key` config value still exists and is otherwise unused by this feature. Net effect: submitting spotting reports currently has no bot/abuse mitigation beyond requiring a Firebase account.
- **Uploading a photo to an existing entry**: enforced server-side only — `GenericUpload.post` 403s unless the requester is the event's original `reporter` (`common/views.py:56-60`). The frontend's `isMine` flag (from `EventScalar.is_mine`) only controls whether the "manage photos" _button_ is shown (`inline-history.component.html:75-87`) — it is not itself a security boundary, just UI affordance matching the real backend check.
- **`auth-permissions.ts`** (`src/app/services/auth-permissions.ts`, the app's role→path permission map): contains no entry for `spotting` (grepped, zero matches) — consistent with this being the one area of the app requiring no role at all.
- **Maintenance flag**: `maintenance.spotting.curentlyInMaintenance` in `app-routing.module.ts` (currently `false`) swaps in `ConstructionComponent` for both `/spotting` and `/spotting/:id` if flipped — a manual source-level toggle, no admin UI or env var.
- **No admin/moderator-only capability exists inside this feature's own files** — no delete/edit-entry UI here (that lives in `src/app/profile/spottings/**`, a different feature, using its own `DeleteEventService` against the same `deleteEvent` mutation) and no "mark as read"/moderation UI here either (that lives in `src/app/console/**`, gated `adminOnly` at the route level, using the same backend `spotting` app's `markAsRead` mutation, which additionally requires `IsAdmin` server-side). Both of those mutations exist on the same backend `SpottingMutations` type documented above but are **not invoked anywhere under `src/app/spotting/**`\*\* — worth knowing so a rewrite doesn't assume they belong to this page.

## Known Quirks / Tech Debt

- ~~`vehicleTypeFilter.DISTINCT` appears to be a dead/stale field~~ **— corrected, this was wrong.** Live verification against the production GraphQL endpoint during the rewrite pass confirmed `DISTINCT: true` is real and necessary: without it, `vehicleTypes(filters: {lineId})` returns one duplicate row per vehicle↔line join match (observed up to 58 duplicate rows for a single vehicle type on one line); with it, results are correctly deduplicated. The earlier claim that it wasn't a declared input field, reached from reading `operation/schema/filters.py` and the installed `strawberry-graphql-django` source without executing a live query, was incorrect — the field's presence isn't visible from that static path (likely wired through a mechanism this pass didn't check, e.g. a resolver-level or Meta-level hook rather than the plain filter dataclass). Lesson for future doc passes: for anything filter/schema-injection-related, a live query against the real backend is authoritative; a static source read that says a field "doesn't exist" is not strong enough evidence to override it.
- **`ngOnChanges` re-queries on any input change, not just `lineId`** (`vehicle-type-container.component.ts:171-193`) — harmless today only because `title`/`lineStatus` never change after initial binding in this feature's actual usage.
- **`wheel_status` save condition checks the wrong field**: `wheel_status = input.wheel_status if input.notes != strawberry.UNSET else None` (`spotting/schema/schema.py:75`) — checks `input.notes`'s unset-ness, not `input.wheel_status`'s; currently harmless because the frontend always sends `notes` (even as `""`), but is a latent bug for any other client of this mutation.
- **reCAPTCHA fully wired but disabled everywhere** (frontend `spotting-form.component.ts:5,248-249,584-585,599`; backend `spotting/schema/schema.py:62-66`) — see Permissions. The unused `environment.captcha.key` config is dead weight in this feature's context.
- **"Last Spotted By" column** fully coded but commented out (`spotting-table.component.ts:96-101,129`) — dead code, not shown to users.
- **`InlineHistoryComponent`'s location lat/lng remap has no consumer**: `mapGqlResultsToDisplayData` (`inline-history.component.ts:202-218`) computes `latitude`/`longitude` onto each row but the component's own template never reads them — either vestigial from a removed feature (e.g. a map popover) or scaffolding for one never finished.
- **`GetLineGuideLinkService.dispose()` is never called** (`spotting/services/get-line-guide-link.service.ts:35-39`) — the Firestore listener it sets up in its constructor lives for the app's entire lifetime since the service is a `providedIn: "root"` singleton with no `ngOnDestroy`/`OnDestroy` implementation and nothing else ever calls `dispose()`. Not a leak in practice (one singleton listener for the whole app), but the `dispose()` method itself is dead code.
- **Extensive `console.log`/`console.debug` left in place** throughout `spotting-main.component.ts`, `vehicle-type-container.component.ts`, `spotting-form.component.ts`, `spotting-table.component.ts` (e.g. logging the entire form value, entire query responses, every row on expand-toggle) — noisy but not functionally harmful; worth stripping in a rewrite.
- **Invalid `:id` in the URL silently deselects every tab** rather than falling back to the first line or showing a "line not found" message (`spotting-main.component.ts:246-251` — see Functionality item 3).
- **Tab switches push browser-history entries** rather than replacing the current URL (`spotting-main.component.ts:264`, no `replaceUrl: true`) — clicking Back cycles through previously-viewed lines one at a time instead of leaving the page in one step; may or may not be the intended UX.
- **Raw error messages surfaced to users**: both the submission failure path (`spotting-main.component.ts:152`, `reason.message`) and elsewhere show backend/Apollo error text verbatim in a toast, rather than a friendlier mapped message.
- **DI scoping inconsistency** across the feature's `apollo-angular` `Query` subclasses (`providedIn: "any"` vs `"root"`) — cosmetic today, listed under State Management.
- **`allowRunNumber`/line-specific vehicle-search heuristics are hardcoded magic line IDs** (`"2"`, `"3"` for run numbers; a much larger hardcoded table in `numberSeenToSetNumbers` for `"1"` through `"20"`, `spotting-form.utils.ts:64-66,80-209`) — fragile if line IDs are ever renumbered in the backend; there is no symbolic/name-based lookup, purely numeric-string line-ID literals.
