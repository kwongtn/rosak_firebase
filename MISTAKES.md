## [2026-10-22] core/http: a read that continues an anonymous list was signed once the interceptor signed everything (F191)

**Problem**: After the auth interceptor landed, a signed-in viewer's imperative reads that continue an anonymous `graphqlResource` list were signed, so one list mixed vote states. Page 1 of the links tab came from the anonymous resource (`userVote` 0) and the appended pages came back signed. The home feed's Load More (today and last week), the gallery's `loadMore` and photo deep link, and the incident card's `loadMoreLinks` had the same split.
**Root Cause**: Before the interceptor an imperative `GraphQLClient.request` was anonymous unless the caller attached the header by hand, and these continuation reads did not. The interceptor signs every backend request of a signed-in viewer unless it carries `ANONYMOUS`, and only `graphqlResource` (by default) and two REST reads set that, so an imperative read had no way to stay anonymous.
**Fix**: `0478a8e`: `GraphQLRequestOptions.anonymous` sets `ANONYMOUS` on the request, with an interceptor spec. `a68e144`: the home paged feeds, the gallery's `loadMore` and `openMediaById`, the links section's `loadMore` and the incident card's `loadMoreLinks` pass it, and their specs pin it. The profile's public user read was already signed on staging and is not marked.
**Prevention**: A read that continues an anonymous list is anonymous too: pass `anonymous: true`. A new public, cacheable `HttpClient` or `httpResource` read to `backendUrl` sets `context: new HttpContext().set(ANONYMOUS, true)`, or a signed-in viewer's request loses the SSR transfer cache. Never hand-attach `firebase-auth-key`. Keep the interceptor in `core/http`: `app.routes.spec.ts` forbids `core/auth` from `main`, and importing `AuthService` there would pull Firebase Auth (about 91 kB) into the initial bundle, which is why `AuthService` registers itself in the root `AUTH_SESSION` token. `graphqlResource(fn, { authenticated: true })` waits once for `auth.whenReady`, does not refetch on a sign-in or sign-out, and has no production consumer yet.

## [2026-10-22] ui/icon-button: a component that applies a class-merging directive through `hostDirectives` must expose `class` (F581)

**Problem**: `<button app-report-bug-button class="size-7">` would render both its own `size-7` and the directive's default `size-8`. Which one wins is then decided by stylesheet order, not by the consumer.
**Root Cause**: `HlmIconButton` merges a consumer class through `hlm()` (twMerge) from its `class` input. A host directive's inputs are not exposed on the component unless `hostDirectives` lists them, so the consumer's `class` never reached that input and the merge never ran.
**Fix**: `1279875`: `ReportBugButtonComponent` uses `hostDirectives: [{ directive: HlmIconButton, inputs: ["class"] }]`, and `report-bug-button.component.spec.ts` asserts that `class="size-7"` keeps `size-7`, drops `size-8` and keeps `rounded-full`.
**Prevention**: When a component wraps `HlmIconButton`, or any directive that merges a consumer `class` through `hlm()`, list `inputs: ["class"]` in `hostDirectives`. Give the wrapper a spec with a conflicting consumer class (`size-7` against the default `size-8`) and assert that the default is absent.

## [2026-10-22] ui/icon-button: a dev-mode accessible-name check in `ngOnInit` does not see a wrapper component's host bindings (F581)

**Problem**: `HlmIconButton` warns in dev mode when the button has neither `aria-label` nor `aria-labelledby`. Its first comment said that host bindings are applied before `ngOnInit`, so a bound name counts. A wrapper component that sets `aria-label` through a host binding would trigger a false warning.
**Root Cause**: The check runs in `ngOnInit`. At that point the element has its static attributes and the `[attr.*]` bindings of the template that declares it, but Angular applies the host bindings of a wrapper component after the preorder hooks.
**Fix**: `606126b` rewords the comment to say what the check sees. The check stays in `ngOnInit`, because no adopter names its button through a wrapper host binding, and `icon-button.spec.ts` covers the static, bound and `aria-labelledby` cases.
**Prevention**: A dev-mode check that reads attributes in `ngOnInit` must not claim to cover host bindings. Name a wrapped button with a static `host` attribute, as `ReportBugButtonComponent` does with `"aria-label": "Report a bug"`; if a wrapper ever needs a host binding, move the check to `ngAfterViewInit`.

## [2026-10-22] forms/validateTree: an error with a `field:` key lands on the form root and never shows under its control (F271, F080)

**Problem**: In the spotting report form, the station and sanity-gate errors never appeared under their controls, and in the incident form the end-before-start error never appeared under End. Submit stayed blocked with no visible message at the field, because the errors sat on the form root.
**Root Cause**: A Signal Forms `validateTree` error targets a child field only through `fieldTree`. A `field:` key is silently ignored. In `@angular/forms` 22.2.3, `addDefaultField` runs `error.fieldTree ??= ...`, so the error falls back to the root. An untyped `const errors = []` evolving array hides the wrong key from `tsc`.
**Fix**: `ab86eaf`: the report form uses `fieldTree: fieldTreeOf(f.<field>)`, with `report-form.schema.spec.ts` asserting the messages per field. `f1b7876`: the incident form's end-before-start rule is `validate(f.endDatetime, ...)`, so the message shows under End. `11e100b` corrects the schema comment and `docs/components/insiden.md`, which first named the wrong cause.
**Prevention**: In a `validateTree`, type the array as `ValidationError.WithOptionalFieldTree[]` so a wrong key fails to compile, and take `fieldTreeOf` from the validator context (passing a `SchemaPath` straight to `fieldTree` is a TS2345 error). For a rule on one field, use `validate(path, ({ value, valueOf }) => ...)` and read siblings through `valueOf()`. A schema spec asserts the message on the field, not only that the tree is invalid.

## [2026-10-22] tracker/RtSource: `??` turned a deliberate null refresh interval into the 30 s default, and the countdown then divided by it (F279, F148)

**Problem**: Choosing 'Do not refresh' (`intervalMs: null`) still polled every 30 s. After that was fixed, any source on a null interval wrote `Infinity` into `secondsRemaining` and `NaN` into `percentRemaining`, and the info panel ring's `stroke-dashoffset` became `NaN`.
**Root Cause**: The constructor read `config.intervalMs ?? DEFAULT`, and `??` also replaces `null`, which is a real value here. Nothing exercised the null path until a spec drove `setRefreshInterval(null)`. `tick()` computed the seconds and percent remaining for a source with nothing scheduled.
**Fix**: `a8a04a2`: `=== undefined ? DEFAULT : value`. `e8ef8fe`: `tick()` reads 0 remaining when nothing is scheduled, with a spec case that fails without it ('expected Infinity to be +0'). `docs/components/tracker.md` says what a null interval means: one fetch, no timer, the countdown reads 0, and later sources inherit it.
**Prevention**: Use `=== undefined` for a default whenever `null` is a meaningful value. After a fix exposes the next layer of a path that never ran, spec the whole path (state, countdown, ring) and not only the first symptom. Still open: F148, `pause()` with an in-flight fetch re-arms the poll timer; an `it.fails` case in `gtfs-realtime.service.spec.ts` pins it and must flip to a plain `it` when it is fixed.

## [2026-10-22] core/graphql: `graphqlResource` waited 10 s before its first retry, not the documented 5 s (F203)

**Problem**: A failed read waited 10 s before its first retry, not the 5 s of the documented schedule (5, 10, 20, 40, 80, 160, 180 s).
**Root Cause**: `scheduleRetry` read the attempt counter after the effect had already incremented it, so the exponent was one too high.
**Fix**: `3cc94bb`: `2 ** (attempt() - 1)`. `graphql-resource-retry.spec.ts` pins the whole schedule, the countdown, the reset, the GraphQL-errors answer, destroy and the server platform (no timer, nothing re-sent, `hasError` false).
**Prevention**: Spec a backoff as a table of delays, not as 'it retries'. The first delay is the one that a counter that moves before it is read gets wrong.

## [2026-10-22] tsconfig: excluding `server.ts` from the app config stops `ng build` type-checking it, and jszip puts Node globals back in browser code (F324)

**Problem**: `@types/node` was `^20` while the runtime and CI use Node 24, and `tsconfig.app.json` listed `node` in its `types`, so browser code could use Node globals unchecked.
**Root Cause**: The app build type-checks the server entry only because `src/**/*.ts` includes it. Moving `server.ts` out of `tsconfig.app.json` removes it from the `ng build` type check. ## [2026-10-22] core/upload: image compression hung, rejected or mislabelled several inputs, and the queue saved photos that were still compressing (F196)

**Problem**: A truncated JPEG left compression pending forever and Submit stuck. A null `canvas.toBlob` became a `File` containing the text 'null'. A PNG over the limit was rejected. The re-attached Exif kept its Orientation, so a viewer could rotate the photo a second time. The size search could return a step over the limit. A re-encoded PNG kept its old extension, although the backend names the stored file by extension. `addToQueue` saved a photo that was still compressing, so a resumed record would send the uncompressed original.
**Root Cause**: `getUint16` threw inside a `FileReader` `load` listener, which does not reject the surrounding promise. `retrieveExif` rejected anything that was not a JPEG and read no bounds. Nothing checked the `toBlob` result, and the queue saved every entry unconditionally.
**Fix**: `63ba5a7`: every marker is bounds-checked and the file is read with `blob.arrayBuffer()`; a null `toBlob` throws; a non-JPEG is re-encoded; Orientation is reset to 1; the search returns the last size that fit. `462699c`: a re-encoded non-JPEG is renamed `.jpg`, and the size limit is documented as excluding the Exif segment. `7b5e081`: `addToQueue` saves only `!toCompress || isCompressed`.
**Prevention**: A callback that parses bytes must be wrapped so a throw rejects the promise. Spec the service with crafted buffers (Exif in both byte orders, PNG, truncations, an empty file, a null `toBlob`). A record that a later session resumes must be in its final sendable state when it is saved. Still open: the search re-decodes the file at every step (F197, F260), and the picker keeps the owner's choice to upload the original (`c955733`).

## [2026-10-22] ui/sheet: a closed `HlmSheet` stays mounted, so its focus trap and its dialog role must follow its open state (F294)

**Problem**: Once the alert bell's pre-prompt had opened once, each pinned row kept a closed but mounted `HlmSheet` right after its bell. One Tab from the bell landed on a focus-trap anchor, which sent focus to the hidden Allow button. Tab and Shift+Tab then cycled Not now and Allow inside an invisible panel. Escape could not leave, because the sheet acts on Escape only while it is open. Enter on the hidden Allow started `subscribe()` and the browser's permission prompt. The panel also kept `role="dialog"` and `aria-modal="true"` in the accessibility tree, so a screen reader could treat the rest of the page as inert. ## [2026-09-15] testing: Angular unit-test builder & Vitest traps

**Problem**: Several ways a test run lied: selection flags that ran nothing (a typo is a silently green zero-test run), `isolate: false` cross-file leaks, module-mock identity that never matched, strict-null spec errors, specs hitting the real GraphQL backend, bare `vitest`, and unmatched `routerLink`s.
**Root Cause**:

- `ng test`'s first positional arg is the project, not a file. `--filter` is a case-sensitive regex against the TEST NAME (the `describe`/`it` string), not a path, and the runner does not treat an empty match as an error: `--filter "network-board"` (2026-10-06; the `line-pulse-card` case hit the same one commit earlier) matched 0 tests, skipped every file and exited 0. `--filter` is a regex over describe and test names and never over file names or paths, so an alternation of describe names selects several specs: `--filter 'HlmIconButton|ReportBugButton'` selects the icon-button and report-bug specs by their describe names (2026-10-22).
- `@angular/build:unit-test` is pinned to `isolate: false` in `angular.json` (`65b00e1`): files in a worker share jsdom globals AND the module cache, so leaks made specs pass alone and fail in the suite. An earlier file can also bind the real module into a cached service, so a `vi.mock` module binding is reliable only when the spec resets the module cache around it (see the 2026-10-22 `testing/isolate` entry).
- Specs are type-checked under `strict` (TypeScript 6's default; `tsconfig.json` sets no `strict` key), so a typed `querySelector<T>(…)` deref fails (`TS18047`). A filtered `--include` run also builds only the included files with no node types, so a spec using the bare `process` global fails to compile there (`TS2591`; `link-occurred-at.util.spec.ts`), while the full suite is fine. It recurred on 2026-10-22: `--include src/app/features/insiden/data` failed with "Cannot find name 'process'" in `link-occurred-at.util.spec.ts`, while `--include src/app/features/console --include src/app/features/insiden/incident-form` compiled and ran. Use the full suite, or `npx tsc --noEmit -p tsconfig.spec.json`, to type-check specs.
- A component using `graphqlResource()` leaves the real `httpResource` POSTing to `localhost:8000` unless the spec provides `provideHttpClientTesting()` and flushes the request (CI `ECONNREFUSED`, hung `whenStable()`).
- Bare `npx vitest run <file>` does not init the TestBed (`Need to call TestBed.initTestEnvironment()`) and has no globals (`describe is not defined`); only `ng test` does.
- A spec that CLICKS a real `routerLink` with no matching route rejects the navigation, and Vitest reports an unhandled rejection that fails the whole run even though the assertions passed. A plain `<a href>` only logs "navigation not implemented" in jsdom.

**Fix**:

- Scope one spec with `--include <path>`; filter on the describe/test name (`--filter "NetworkBoardComponent"` ran 32 tests) and grep the spec's `describe(...)` for the string instead of guessing from the filename (`line-pulse-card.component.spec.ts` describes `LinePulseCardComponent`).
- Use `vi.stubGlobal` + `vi.unstubAllGlobals()` for globals and restore mutated module/registry state in `finally` (`vi.resetModules()`); verify with `--isolate` when chasing order-dependence. Prefer a TestBed DI seam to `vi.mock` where the unit has one (`UPLOAD_ERROR_REPORTER` and `LOAD_FEEDBACK` are the reference fixes). A spec that still `vi.mock`s a shared module resets the module cache around it, as `gtfs-static.service.spec.ts` now does (2026-10-22). Stub `AuthService` in nav specs, as `compact-nav.component.spec.ts` does.
- Keep the `nativeElement.querySelector(…) as HTMLElement` idiom, or null-guard.
- Provide `provideHttpClientTesting()` and flush the reference POST; never instantiate services that import `firebase/*` in specs, stub them.
- Bare `vitest run` is still the fast path for a spec with no TestBed (a pure function/util), but it skips the unit-test build's spec type-check, so run the real gate before trusting it.
- Give the router a matching route (`provideRouter([{ path: "spotting/:lineId/vehicle/:vehicleId", children: [] }])`); for a plain anchor, suppress the log with a `preventDefault()` listener on it (this does not affect the propagation a `stopPropagation` assertion depends on).

**Prevention**: Use `--include` for files and a correctly-cased anchored regex for `--filter`; treat a 0-test filtered run as a FAILURE (check the reported test count before reading anything else) and re-run unfiltered (`npm test -- --no-watch`) before trusting a green result; the full suite's file/test count is the only reliable regression signal. Treat "passes alone, fails in suite" as module-cache contamination, not a flake; write specs hermetic.

## Cross-Component Opportunities

> Four shared capabilities are repeatedly needed (non-AI 1–3; AI 4). Build each utility **once**,
> then apply it to every listed feature. Numbering follows `docs/COMPONENTS.md` (non-AI items 1–3;
> item 4 here is the AI-gateway item of its AI list; its non-AI bulk-actions item 4 is tracked there
> only). Dates are catalogue dates (2026-08-13 per-feature audits; 2026-08-24 fixes), compiled from
> `docs/COMPONENTS.md` and `docs/components/*.md`. The helpers for 1–3 now exist (status as of
> 2026-10-22); the per-feature bullets list only the features that have not adopted them.

### 1. Shared URL / query-param sync — `core/url-state/query-param.util.ts` — 6 features not yet adopted

The helper exists (`readEnumQueryParam`, `readTextQueryParam`, `queryParamForWrite`, `writeQueryParams`: pure read helpers, one browser-gated merge/replace write; a default is never written to the URL). It is adopted by `home` (`?view=`/`?sort=`/`?line=`/`?q=`: `home-view-mode.service.ts`, `pro-dashboard.component.ts`, `network-board.component.ts`) and `insiden` (`?lines=`/`?severity=`/`?mine=`: `incident-filter.util.ts`, `insiden.page.ts`). Spotting's `line-overview.page.ts` writes `sort`/`dir` through `writeQueryParams`/`queryParamForWrite` and keeps its own `isSortColumn` read guard (`line-details.page.ts` still reads query params directly). There is no signal-binding wrapper (`syncSignalWithQueryParam` does not exist). Elsewhere only path params are bound.

- **console** — shareable/saved moderation filter views (e.g. "unread depot spottings with notes"); `ConsolePage` does not inject `ActivatedRoute`; filter state lives only in local signals.
- **gdpr** — deep-link to an individual checklist item; `group.title`/`child.title` are used as `@for` track keys but not rendered as element `id`s.
- **about** — anchors for the three content sections (projects, personnel, tech stack); `AboutPage` takes no route params.
- **spotting** — `VehicleSpottingGridComponent`'s `statusFilter`/`months` (owned by `line-details.page.ts`) are plain local signals; `months` is a computed date range, not a flat enum, so it needs custom encoding (e.g. ISO month key).
- **insiden** — `detailsExpanded`/`photosExpanded` in `IncidentCardComponent` are local signals; day selection and the line, severity and "My lines" filters already round-trip (`/insiden/:dateKey`, `?lines=`, `?severity=`, `?mine=`).
- **tracker** — shareable map view: `LayerSelectionService`'s applied (layer) signals plus viewport (center, zoom) are not synced.

**Prevention**: handle encoding/decoding, default omission, browser-only writes, SSR safety; make query-param sync a required acceptance criterion for any new filterable view.

### 2. Shared client-side export utility — `core/export/csv.util.ts` — 2 features not yet adopted

`toCsv` (pure; always emits a header row, even for zero rows; it does not defuse spreadsheet formulas, so community text goes through `neutralizeSpreadsheetFormula`), `downloadCsv`, `downloadText` and `downloadIcs` (browser-gated), `json.util.ts` (`downloadJson`) and `ics.util.ts` (`buildIcs`) exist. Their consumers are home's Pro lines widget (`home/pro/pro-lines-widget.component.ts`, CSV), profile's spotting history (CSV and JSON, paged from the API), insiden ("Add to calendar" and "Export month") and the tracker info panel (CSV). The tracker info panel exports through `downloadCsv(…, toCsv(…))` (`tracker/info-panel/tracker-info-panel.component.ts`, F440); its third-party feed text is not yet passed through `neutralizeSpreadsheetFormula`. No zip helper exists. Data is already resident client-side in the remaining cases, so no backend or query change is needed.

- **console** — export the filtered moderation queue (`events: Signal<ConsoleEvent[]>`).
- **gallery** — bulk download of a year's photos as a zip; evaluate client-side fetch-and-zip vs. a backend batch-export endpoint by expected volume.

**Prevention**: reuse `core/export` instead of a private per-feature helper and point `downloadJson` at `downloadText`; add export as a standard capability for any data-table / media-grid; add "Add to calendar" for date-based lists.

### 3. Shared persistence — `core/preferences/preferences.service.ts` — 2 features not yet adopted

`PreferencesService` exists (localStorage key `rosak:preferences:v1`; typed fields: pinned lines, view mode, recent/last-reported lines, Pro table layout/sort; hydrated in `afterNextRender`, see the 2026-10-03 entry). Home is its only writer (insiden's "My lines" filter reads the pinned lines), and it is a typed home-shaped payload, not a generic `get`/`set`/`watch` API (`UserPreferenceService` does not exist). The report drafts (home's line-status sheet per line, spotting's report form in one slot) live in `sessionStorage`, and the status-report outbox (`core/offline/`) and this browser's line alerts (`core/push/`) live in `localStorage`, all through `core/util/web-storage.util.ts`. The only other persistence is the upload queue's upload-specific IndexedDB.

- **tracker** — save/favorite layer presets; the `LayerSelectionService` draft/applied/undo signal triplet is the seam (otherwise state resets to `layer-config.ts` defaults on reload).
- **profile** — store settings for the proposed settings sub-page.

**Prevention**: extend `PreferencesService` (validate each stored field independently) rather than adding another storage wrapper, and keep its SSR rules (read in `afterNextRender`, gate writes on hydration); optional Firestore sync is still unbuilt.

### 4. Shared AI / LLM gateway — `AiGatewayService` (`core/ai`) — 9 features

Every feature doc independently proposes an LLM-/embedding-based feature (captioning, summarization, anomaly detection, NL query parsing, conversational form-fill), but there is no AI infrastructure — no `core/ai` service, no LLM API client, no embeddings store (still true 2026-10-21).
**Prevention**: establish a provider-agnostic gateway (auth, rate-limiting, caching, streaming) before any AI feature; all features inject the same gateway — no bespoke integrations.

## Prevention Checklist for Future Work

- [ ] **Security** — never leave guards in pass-through state; track as a blocking issue.
- [ ] **Error handling** — every async subscription needs an error signal + error UI + retry.
- [ ] **Code review** — check for duplicate patterns across features; extract to `core` on the second occurrence.
- [ ] **Documentation** — update component docs when fixing systemic issues so future audits don't re-discover.
